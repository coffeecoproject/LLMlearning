# 单请求效率与资源概览

> [!summary]
> 对一个已经进入模型的请求，输入长度主要增加 Prefill 工作，输出长度直接增加顺序 Decode 轮数；模型权重提供固定基础占用，临时激活服务当前计算，KV Cache 则随可见序列增长。单请求快不快，不能只看参数量或一个“Tokens/s”数字。

> [!phase] 运行阶段：单请求视角
> 本专题假设模型已经训练完成并可以运行，只跟踪一个请求自身的时间和资源。模型怎样加载到设备、多个请求怎样 Batch、队列怎样调度、缓存怎样分页与回收，进入 [[00-推理Runtime与模型服务大纲|推理 Runtime 与模型服务]]。

## 先建立一张时间账本

```text
请求开始
→ 输入准备
→ Prefill：处理已有输入
→ 产生并选出第一个输出 Token
→ Decode 1
→ Decode 2
→ ……
→ 达到停止条件
```

从用户等待体验看，可以先分成两段：

```text
等待第一个 Token
→ TTFT（Time To First Token）

第一个 Token 之后继续生成
→ 主要由后续 Decode 轮数和每轮时间决定
```

## 再建立一张资源账本

| 资源 | 直白理解 | 在单请求期间怎样变化 |
|---|---|---|
| 模型权重 | 模型训练后留下的大量参数 | 通常已经加载并保持不变 |
| 临时激活与工作区 | 当前这一层计算时使用的中间结果和临时空间 | 随阶段、形状和实现变化，可被复用或释放 |
| KV Cache | Attention 为已处理位置保留的 K、V 状态 | Prefill 建立，Decode 继续增长 |
| 计算量 | 矩阵运算等需要做多少工作 | 输入越长、模型越大、输出轮数越多通常越高 |
| 内存带宽 | 单位时间能从显存等位置搬运多少数据 | Decode 反复读取权重和历史状态时尤其重要 |

这里的“资源占用”不只是显存容量，也包括计算能力、数据搬运能力和实际耗时。

## 四条最重要的因果关系

```text
输入更长
→ Prefill 要处理更多已有位置
→ 首 Token 通常更晚

输出更长
→ 必须执行更多顺序 Decode 轮次
→ 完整回答通常更晚

可见序列更长
→ KV Cache 更大
→ 后续 Token 需要读取的历史也更多

模型更大
→ 权重更多、每层计算通常更重
→ 但真实性能仍受结构、精度、硬件和 Runtime 影响
```

“输入长度主要影响 Prefill”并不等于输入只影响 Prefill。更长的输入也会让 Decode 一开始就面对更长的历史 KV Cache。

## 本专题不展开什么

- Batch Size、Continuous Batching 和请求队列；
- 多用户并发下的调度公平性；
- Paged KV Cache 和跨请求 Prefix Cache；
- 张量并行、流水线并行和多机部署；
- 量化内核、编译器和硬件算子优化；
- API 计费与特定厂商的服务指标口径。

这些内容会改变真实测量值，但不改变本专题先要掌握的请求内因果关系。
