# 一个单请求的时间与资源账本

> [!summary]
> 一次请求可以同时用两条线追踪：时间线上先付出输入 Prefill 的首 Token 成本，再按输出长度重复 Decode；资源线上权重保持固定，临时激活随计算阶段变化，KV Cache 从输入开始并随输出增长。

> [!phase] 运行阶段：串联复习
> 以下数字全部是教学虚构，只用于把因果关系串起来，不能用来推断任何真实模型、GPU 或 API 的性能。

## 场景设定

假设一个请求经过 Tokenizer 后得到：

```text
输入：8 Token
最终输出：4 Token
```

为了便于计算，再假设：

```text
输入准备：20 ms
Prefill：180 ms
第一次Token选择与返回：20 ms
后续每轮Decode平均：50 ms
```

## 第一阶段：输入准备

```text
Messages
→ Chat Template
→ Tokenizer
→ 8个输入Token ID
```

此时：

| 项目 | 状态 |
|---|---|
| 模型权重 | 已加载，保持不变 |
| 输入 Token | 8 个 |
| KV Cache | 尚未由本次 Prefill 完整建立 |
| 输出 Token | 0 个 |

输入准备位于模型前向计算之前，但属于完整请求路径的一部分。

## 第二阶段：Prefill并产生首Token

模型处理 8 个已有输入位置：

```text
8个Token经过全部Transformer层
→ 各层建立8个位置的KV Cache
→ 最后有效位置产生Logits
→ 选择输出Token 1
```

首 Token 延迟近似为：

```text
TTFT
≈ 输入准备20 ms
 + Prefill 180 ms
 + 首次选择与返回20 ms
= 220 ms
```

此时：

```text
已经显示：输出Token 1
模型下一步可见前缀：8个输入 + Token 1
```

## 第三阶段：三轮后续Decode

最终输出总数是 4；第一个已经在 TTFT 中产生，所以还需约 3 轮：

```text
Decode Token 1 → 选Token 2
Decode Token 2 → 选Token 3
Decode Token 3 → 选Token 4
```

如果 Token 4 同时触发停止条件，那么后续近似耗时：

```text
3轮 × 50 ms
= 150 ms
```

总延迟近似：

```text
220 ms + 150 ms
= 370 ms
```

## KV Cache怎样增长

用“位置数量”而不是字节数观察：

```text
Prefill后：缓存8个输入位置的状态
继续生成：逐步加入输出位置的状态
```

为了计算第 4 个输出 Token，模型已经需要利用：

```text
8个输入位置
+ 前3个输出位置
= 11个已知位置
```

第 4 个 Token 被选出后是否还需要执行下一轮来预测 EOS，取决于实际停止协议。教学中常把“生成 N 个可见 Token”与“内部一共执行多少次模型步骤”简化对应；真实系统还要考虑 EOS、停止序列和接口实现。

## 三类内存此时分别怎样

| 内存对象 | 本次过程中的变化 |
|---|---|
| 模型权重 | 从开始到结束保持同一份参数主体 |
| 临时激活/工作区 | Prefill和每轮Decode按当前计算需要产生、复用或释放 |
| KV Cache | Prefill建立，并随已处理输出位置增长 |

如果请求结束且 Runtime 不再保留这段会话状态，KV Cache 可以释放；模型权重通常继续留在设备上等待其他请求。

## 如果只改变输入长度

保持输出仍为 4 Token，把输入从 8 增加到 80：

```text
主要变化
→ Prefill处理更多位置
→ TTFT通常增加
→ 初始KV Cache变大
→ Decode从更长历史开始

基本不变
→ 仍需产生4个输出Token
→ 普通输出链仍有相应顺序依赖
```

## 如果只改变输出长度

保持输入仍为 8 Token，把输出从 4 增加到 40：

```text
主要变化
→ TTFT未必有同等幅度变化
→ 后续Decode轮数显著增加
→ 总延迟增加
→ KV Cache继续增长更久
```

## 一张最终因果图

```text
模型大小、结构、精度、硬件与实现
             ↓
      每一步计算有多重

输入Token数 ─→ Prefill工作 ─→ TTFT
     │
     └──────→ 初始KV Cache大小

输出Token数 ─→ Decode轮数 ─→ 完整回答时间
     │
     └──────→ KV Cache继续增长
```

## 最容易混淆的五句话

```text
长输入主要拖慢Prefill，但也影响后续历史长度。
长输出直接增加顺序Decode轮数。
KV Cache减少重复计算，不消除历史读取和顺序依赖。
权重是固定基础，KV Cache是请求状态。
单请求更快，不等于服务总吞吐更高。
```

## 理解检查

1. 为什么总输出 4 Token 时，教学公式使用 `TTFT + 3 × TPOT`？
2. 输入从 8 增加到 80，哪几部分最先发生变化？
3. 输出从 4 增加到 40，为什么权重不变但 KV Cache 会继续增长？
4. 请求结束后，哪些资源通常可以释放，哪些通常继续保留？
