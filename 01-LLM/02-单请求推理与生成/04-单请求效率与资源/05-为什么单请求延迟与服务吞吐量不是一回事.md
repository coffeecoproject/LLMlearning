# 为什么单请求延迟与服务吞吐量不是一回事

> [!summary]
> 单请求延迟回答“这个用户要等多久”，服务吞吐量回答“整个系统单位时间完成多少工作”；Runtime 可以通过批处理提高硬件总利用率，却可能让某个请求多等待，因此两者不能用同一个数字替代。

> [!phase] 本篇只建立边界
> 为了说明为什么指标不同，本篇会使用两个请求的简单例子；Batch、Continuous Batching、队列与调度算法的真实机制统一留给 [[00-批处理与调度概览|批处理与调度]]。

## 单请求延迟问什么

从请求 A 自己的视角：

```text
A发送请求
→ A看到首Token
→ A看到后续Token
→ A的回答结束
```

它关心：

- TTFT 多长；
- TPOT 多长；
- 完整回答何时结束；
- 本次请求占用了多少 KV Cache 等状态。

## 服务吞吐量问什么

从整个服务视角：

```text
一秒钟内
→ 总共处理多少输入Token
→ 总共生成多少输出Token
→ 或完成多少请求
```

它关心整体工作量，而不是某一个用户单独等待多久。

## 一个两请求例子

假设硬件可以：

```text
单独处理A：A用1秒完成
单独处理B：B用1秒完成
```

### 方案一：严格串行

```text
第0～1秒：处理A
第1～2秒：处理B
```

结果：

```text
A延迟：1秒
B延迟：2秒（包含等待）
2秒完成2个请求
```

### 方案二：合并利用硬件

假设某种批处理能让 A、B 在 1.4 秒左右都完成：

```text
A延迟：1.4秒
B延迟：1.4秒
1.4秒完成2个请求
```

系统总吞吐提高了，但 A 相比独占运行的 1 秒反而更晚完成。这说明：

```text
整体效率更高
≠ 每个请求一定更快
```

数字只是教学假设，不代表任何真实 Runtime。

## 为什么会有这种取舍

现代加速硬件擅长较大的并行计算。单个 Decode 步骤形状较小，未必充分使用硬件；把多个请求的当前步骤组织在一起，可能提升总利用率。

但合并和调度也可能带来：

- 等待其他请求形成批次；
- 多个请求争用计算和内存带宽；
- 更复杂的 KV Cache 管理；
- 长短请求之间的公平性问题。

这些都属于 Runtime 层，而不是某一个 Transformer Block 自己决定的行为。

## 四个容易混在一起的指标

| 指标 | 主要回答 |
|---|---|
| 单请求 TTFT | 这个请求多久看见第一个 Token |
| 单请求 TPOT / 输出 Tokens/s | 这个请求后续生成速度怎样 |
| 服务总 Tokens/s | 所有并发请求合计每秒产生多少 Token |
| 请求吞吐量 | 单位时间完成多少请求 |

请求吞吐量还会受到每个请求输入、输出长短影响，所以“每秒请求数”也不能脱离测试负载比较。

## 为什么本专题仍然要提到吞吐量

如果完全不说明这条边界，看到以下说法时很容易误解：

> Batch Size 增大后 Tokens/s 提升，所以每个用户都变快了。

正确理解应是：

```text
可能提高系统总吞吐
但单请求TTFT、TPOT和总延迟要分别测量
```

本篇到这里停止，不继续展开怎样 Batch。

## 常见误解

1. **“总Tokens/s越高，每个用户就越快。”** 总吞吐可能通过并行合并提高，个体仍可能多等待。
2. **“单请求测速能代表线上服务。”** 线上还有排队、并发和资源争用。
3. **“批处理是模型训练才有的概念。”** 推理服务也会批处理多个请求，但目的和调度方式可以不同。
4. **“一个推理请求会为了并行，把自己未来的Token组成Batch。”** 普通自回归未来步骤依赖尚未选出的前缀；服务 Batch 通常是组织多个请求或其他可并行工作。
