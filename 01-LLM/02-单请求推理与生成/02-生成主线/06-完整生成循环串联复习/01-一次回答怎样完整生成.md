# 一次回答怎样完整生成

> [!summary]
> 运行时，系统先把消息变成 Token IDs，通过 Prefill 得到首次 Logits；此后生成控制器反复选择一个 Token，模型再用增量 Decode 产生下一轮 Logits，直到停止并由 Tokenizer 恢复文本。

> [!phase] 运行阶段
> 本篇只讨论训练完成、模型参数保持固定时的一条普通自回归请求。训练、跨请求调度和 Agent 任务循环不在这条主线中。

## 先看完整路径

```text
用户消息
↓
【模型外：输入准备】
Messages → Chat Template → Tokenizer → input_ids
↓
【模型内：Prefill】
Embedding 与位置机制
→ 全部 Transformer Blocks
→ 建立 Prompt 的 KV Cache
→ Output Layer
→ 首次 Logits
↓
【模型外：生成控制】
处理 Logits → 选择 Token 1 → 检查停止
↓ 若继续
【模型内：增量 Decode】
Token 1 → Embedding 与位置机制
→ 全部 Transformer Blocks
   └─ Attention 读取历史 KV Cache
   └─ 加入 Token 1 的新 K、V
→ Output Layer
→ 下一轮 Logits
↓
再次选择 Token → 检查停止 → 继续循环
↓
【模型外：文本恢复】
生成 Token IDs → Tokenizer Decode → 用户可读文本
```

这里的“模型外”表示它不是模型权重中的网络层，不表示它可以被省略。

## 用同一个例子走完整条链

用户输入：

```text
法国的首都是哪里？
```

以下 Token 切分、特殊标记、Token ID 和 Logits 数值全部是**教学化虚构示例**，不代表任何真实模型的输出。

### 第一步：消息协议整理

聊天应用先把角色和内容组织成 Messages，再用配套 Chat Template 加入模型训练时熟悉的角色边界：

```text
Messages
[
  { role: "user", content: "法国的首都是哪里？" }
]

教学化格式
<user>法国的首都是哪里？<assistant>
```

Chat Template 决定“谁说了什么、接下来轮到谁说”，但还没有把文字变成模型能读取的数字。

### 第二步：Tokenizer 产生输入 Token IDs

Tokenizer 使用与模型配套的词表和切分规则，把格式化序列变成 Token IDs。为了看清流程，假设得到：

```text
[<user>] [法国] [的] [首都] [是] [哪里] [？] [<assistant>]
    101     235   47    816   52   903   66       102
```

模型真正接收的是这些 ID，而不是界面中的原始字符串。实际 Token 边界和 ID 会因 Tokenizer 不同而变化。

### 第三步：Prefill 读取已有输入

整个输入序列进入模型：

```text
input_ids
→ Token Embedding 与位置机制
→ Transformer Block 1
→ Transformer Block 2
→ ……
→ 最后一个 Transformer Block
→ Final Norm 与 Output Layer
```

这次 Prefill 同时形成两个重要结果：

1. Prompt 各位置在每层 Attention 中可复用的 K、V，被保存为 [[01-KV-Cache保存什么|KV Cache]]；
2. 最后一个有效输入位置经过 Output Layer，得到预测第一个回答 Token 的 Logits。

此时 KV Cache 只对应已经被模型处理过的 Prompt；回答 Token 还没有被选择，因此当然也不在 Cache 中。

### 第四步：从首次 Logits 选择第一个 Token

为了演示，假设首次 Logits 中部分候选为：

| 候选 Token | 虚构 Logit |
|---|---:|
| `[巴黎]` | 5.2 |
| `[伦敦]` | 1.4 |
| `[北京]` | 0.8 |

生成控制器可以应用 Temperature、Top-k、Top-p 等规则，再通过 Greedy 或 Sampling 选出一个 Token。假设选中了：

```text
Token 1 = [巴黎]
```

这是模型外对 Logits 的使用结果。Output Layer 负责产生候选分数，但不独自决定最终采用哪种选择策略。

### 第五步：检查是否应当停止

生成控制器检查 `[巴黎]` 是否满足停止条件：

- 它不是 EOS；
- 尚未达到最大输出长度；
- 没有命中其他停止规则。

因此生成继续。注意，`[巴黎]` 虽然已经被选出，但此刻还没有经过下一轮 Transformer 计算，它自己的 K、V 也还没有加入 Cache。

### 第六步：增量 Decode 处理刚选出的 Token

`[巴黎]` 作为下一轮模型输入，仍然会经过完整模型路径。以标准 Attention 为例：

```text
[巴黎] 的 Token ID
→ Embedding 与当前位置处理
→ 全部 Transformer Blocks
   ├─ 当前 Token 形成当前层的 Q、K、V
   ├─ 当前 Q 读取 Prompt 的历史 K、V
   └─ 当前 K、V 加入这一层的 KV Cache
→ Output Layer
→ 下一轮 Logits
```

KV Cache 只让历史 K、V 不必重新计算；它不会代替 Embedding、Transformer 的其他计算或 Output Layer。

假设这轮 Logits 最终让生成控制器选出：

```text
Token 2 = [。]
```

控制器再次检查停止条件。`[。]` 不是 EOS，因此它也要作为下一轮输入经过增量 Decode。

### 第七步：继续循环，直到选出 EOS

模型处理 `[。]`，把它的新 K、V 加入 Cache，再由 Output Layer 产生下一轮 Logits。假设控制器这次选出：

```text
Token 3 = [<EOS>]
```

EOS 表示模型认为序列可以结束。控制器检测到 EOS 后停止循环，不再为了产生后续文字而继续运行模型。

最终生成的 Token 序列可以概念化表示为：

```text
[巴黎] [。] [<EOS>]
```

### 第八步：Tokenizer Decode 恢复文本

Tokenizer Decode 根据同一套词表和字节规则恢复文字，并通常按配置隐藏 EOS 等特殊 Token：

```text
[巴黎] [。] [<EOS>]
→ “巴黎。”
```

到这里，一次普通单请求生成才算完整结束。网络服务是否分段发送这段文字，属于 [[01-Streaming为什么逐步显示|Streaming 与接口层]]。

## 第一个 Token 和后续 Token 有什么不同

它们最终都来自 Output Layer 的 Logits，但得到 Logits 的起点不同：

| 对比 | 第一个回答 Token | 后续回答 Token |
|---|---|---|
| Logits 来自 | Prefill 最后一个有效输入位置 | 每轮增量 Decode 的当前新位置 |
| 模型本轮通常处理 | 整段已有输入 | 一个刚选出的新 Token |
| KV Cache | 为 Prompt 建立初始 Cache | 读取历史 Cache，并追加当前 Token 的新状态 |
| 下一步 | 选择 Token 1 | 继续选择 Token 2、3…… |

“通常处理一个新 Token”描述的是普通自回归单序列的逻辑路径；实现优化可能改变一次物理调用处理的数量，但不能取消未来 Token 对已选前缀的因果依赖。

## 生成期间哪些东西改变

| 对象 | 是否随本次生成改变 | 原因 |
|---|---|---|
| 模型参数 | 通常不变 | 当前是运行，不是训练 |
| 输入和生成 Token IDs | 持续增长 | 每轮把选出的 Token 接到序列后面 |
| Hidden State | 每轮重新形成当前计算所需表示 | 它取决于当前输入和上下文 |
| Logits | 每轮更新 | 上下文新增了已选择的 Token |
| KV Cache | 在 Token 真正经过 Prefill 或 Decode 后增长 | 保存已经计算完成的 Attention 状态 |
| 停止状态 | 每轮检查 | 决定继续还是结束 |

## “一轮生成一个 Token”应怎样准确理解

> [!important]
> 对普通自回归的一条序列，一个**逻辑生成步骤**根据当前前缀确定一个下一个 Token；这不表示 Runtime 的一次调度或网络的一次发送只能包含一个 Token。

- Runtime 可以在一个 Batch 中让多个请求各推进一步；
- Speculative Decoding 可以先提出多个候选，再由目标模型验证并一次接受若干连续 Token；
- Streaming 可以把多个已生成 Token 对应的文本合并成一个网络事件。

这些方式改变执行和传输组织，但没有允许后面的 Token 脱离已确认前缀随意产生。

## 四个容易混淆的职责

| 系统部分 | 主要职责 | 不负责什么 |
|---|---|---|
| 模型 | 根据当前输入与历史状态产生 Logits | 不直接决定 UI 怎样显示 |
| 生成控制器 | 处理 Logits、选择 Token、检查停止并组织循环 | 不学习或永久修改模型参数 |
| Tokenizer | 在文字、字节与 Token IDs 之间转换 | 不执行 Transformer 推理 |
| Runtime 与模型服务器 | 加载模型、调度计算、管理资源并提供接口 | 不改变单请求自回归因果关系 |

## 常见误解

1. **“Prefill 已经生成了完整答案。”** 不是。它通常只提供首次下一 Token 的 Logits 和 Prompt 的缓存状态。
2. **“KV Cache 直接处理新 Token。”** 不是。新 Token 经过完整模型路径，KV Cache 只在 Attention 中提供历史状态。
3. **“Output Layer 完成整个 Decode。”** 不是。它只把本轮最终 Hidden State 转换成 Logits。
4. **“Token 一选出来就已经在 Cache 中。”** 不是。它要真正经过下一轮模型计算后，自己的可缓存状态才会形成。
5. **“Tokenizer Decode 就是模型的 Decode 阶段。”** 不是。前者恢复文本，后者是增量模型计算。

## 理解检查

1. 第一个回答 Token 的 Logits 为什么来自 Prefill，而不是增量 Decode？
2. `[巴黎]` 被选中以后，为什么还要再经过一次模型计算？
3. `[巴黎]` 的 K、V 在选择之前、选择之后，还是经过 Decode 时进入 Cache？
4. Output Layer 和生成控制器分别负责什么？
5. 为什么一次 Streaming 事件可能包含多个 Token，却不违反自回归依赖？
