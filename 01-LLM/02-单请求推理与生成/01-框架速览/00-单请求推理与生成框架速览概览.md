# 单请求推理与生成框架速览

> [!summary]
> 一个请求的回答不是一次性吐出，而是固定参数模型先读取现有输入，再反复产生一组 Logits、选择一个 Token、把它接回上下文，直到停止。

## 一次请求的五步

| 步骤 | 直白理解 | 主要结果 |
|---|---|---|
| 1. 输入准备 | 把角色消息整理成模型约定的 Token 序列 | `input_ids` 等输入 |
| 2. Prefill | 一次处理当前可见输入 | 首次 Logits、历史 KV 状态 |
| 3. Token 选择 | 根据 Logits 和生成规则选一个 Token | 新 Token ID |
| 4. 增量 Decode | 把刚选出的 Token 送入模型；各层 Attention 复用历史 KV Cache | 经 Output Layer 得到下一轮 Logits |
| 5. 停止与恢复 | 满足 EOS 等条件后恢复成文字 | 输出文本 |

完整回答来自第 3、4 步的循环：

```text
Logits → 选择 Token 1
→ Token 1 经过 Embedding、Transformer 和 Output Layer → 新 Logits
→ 选择 Token 2 → 再完成一轮增量 Decode → ……
```

KV Cache 只在 Transformer 各层的 Attention 中提供历史 K、V；它不会代替 Embedding、其余 Transformer 计算或 Output Layer。

## 为什么这不是训练

```text
通常不变：Embedding、Attention、FFN、LM Head 等模型参数
随请求变化：Token、Hidden States、Logits、KV Cache、停止状态
```

模型能够按照当前对话改变回答，是因为临时上下文状态不同，不代表一次聊天自动修改了长期参数。

## 为什么输出方向具有先后依赖

第 2 个新 Token 的分布取决于第 1 个 Token 实际选了什么，第 3 个又依赖前两个。因此普通自回归生成必须按逻辑顺序推进。硬件可以并行完成一轮内部计算，但不能在不知道前一个结果时直接确定所有未来 Token。

## 这一页暂时忽略什么

假设只有一个请求独占所需资源，不讨论：

- 其他请求怎样排队或插入 Batch；
- GPU 内存怎样给不同请求分配缓存块；
- 结果怎样封装成网络 Streaming 事件；
- 模型怎样跨设备部署。

这些属于下一大部分 [[00-推理Runtime与模型服务大纲|推理 Runtime 与模型服务]]。
