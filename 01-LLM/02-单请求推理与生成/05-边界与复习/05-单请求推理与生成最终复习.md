# 单请求推理与生成最终复习

> [!summary]
> 一个普通单请求的核心是：外部系统组织输入，固定参数模型通过 Prefill 和顺序 Decode 反复产生 Logits，生成控制器选 Token 并判断停止；上下文和 KV Cache 会变化，但模型参数通常不变。

> [!phase] 运行阶段总复习
> 本篇不增加新机制，而是检查能否把已经学习的对象、顺序、状态和系统边界重新组合起来。

## 第一张图：完整因果链

```text
用户当前输入与候选历史
→ 应用选择本次Messages
→ Chat Template组织角色协议
→ Tokenizer得到Token IDs
→ Embedding与Position形成初始表示
→ Prefill处理全部已知输入
→ 建立输入位置的KV Cache
→ 最后有效位置经过Output Layer得到Logits
→ 生成控制器选择Token 1
→ 若未停止，将Token 1送入增量Decode
→ 读取历史KV并追加新K、V
→ 得到新Logits并选择Token 2
→ 重复直到EOS、Stop或长度限制
→ Tokenizer Decode恢复可显示文本
```

如果无法解释其中任何一个箭头，应回到对应的原子笔记，而不是记住整段口号。

## 第二张图：时间和并行边界

```text
Prefill
输入Token全部已知
→ 可以利用大规模矩阵并行
→ 但信息可见性仍受Causal Mask限制

Decode
未来输出尚未确定
→ Token轮次之间存在顺序依赖
→ 每一轮内部仍有大量并行计算
```

所以准确表述是：

> 普通单序列生成是“输出轮次之间串行、每轮内部并行”，不是“整个模型只能串行计算”。

## 第三张图：哪些东西改变

| 对象 | 本次请求中是否变化 | 是否是长期模型参数 |
|---|---:|---:|
| 输入与输出 Token IDs | 是 | 否 |
| Hidden States | 是 | 否 |
| Logits | 是 | 否 |
| KV Cache | 是 | 否 |
| 停止状态 | 是 | 否 |
| Embedding、Attention、FFN等权重 | 普通运行中通常不变 | 是 |

模型能根据当前对话改变回答，主要因为输入和临时状态变了，不表示普通请求自动训练了模型。

## 第四张图：系统职责

| 层次 | 核心职责 |
|---|---|
| 客户端/应用 | 保存候选历史、组织交互、展示结果 |
| API | 定义请求、响应、错误和流式事件协议 |
| Runtime | 加载模型、执行计算、管理设备与请求资源 |
| 生成控制器 | 处理Logits、选择Token、检查停止、组织循环 |
| 模型 | 根据当前输入与状态产生Logits |
| Agent | 跨多次请求和工具执行维护目标、状态与闭环 |

真实软件可以合并多个角色，但不能因此把概念混为一层。

## 五组必须能区分的概念

### 1. Tokenizer Encode 与模型 Decode

```text
Tokenizer Encode：文字/字节 → Token IDs
模型 Decode：利用前缀和KV Cache继续模型计算
Tokenizer Decode：Token IDs → 文字/字节
```

### 2. 上下文与KV Cache

```text
上下文：模型本次可依据的信息内容
KV Cache：对已处理位置Attention状态的计算复用
```

Cache 不会让窗口外的信息自动重新出现。

### 3. 上下文适应与参数学习

```text
上下文适应：当前请求行为变化，参数通常不变
参数学习：存在Loss、反向传播或其他明确更新过程
```

### 4. 单请求速度与服务吞吐

```text
单请求延迟：这个用户等待多久
服务吞吐：整个系统单位时间完成多少工作
```

多请求 Batch 可能提高总吞吐，但不保证每个请求更快。

### 5. 一次LLM请求与Agent任务

```text
一次LLM请求：一次输入到一次输出序列
Agent任务：可能包含多次LLM请求、工具执行、状态更新与验证
```

## 用反事实检查是否真正理解

### 如果没有Tokenizer

文字无法按照模型约定稳定变成 Token IDs，Embedding 也就没有正确的查表入口。

### 如果没有Causal约束

模型训练和运行时可能读取本应未知的未来输出，无法保持“根据已知前缀预测下一 Token”的生成关系。

### 如果没有KV Cache

自回归生成仍然可以进行，但每轮可能需要重复计算更多历史状态，效率明显下降。

### 如果没有生成控制器

模型可以给出 Logits，却没有组件负责按规则选 Token、检查停止并组织下一轮。

### 如果不重新发送历史

固定参数模型不会仅因为过去聊过，就自动在全新请求中拥有那段对话内容。

## 最终理解检查

1. 第一个输出 Token 和第二个输出 Token 的 Logits 分别怎样产生？
2. 为什么 Prefill 能并行处理很多已知位置，Decode 的未来轮次却不能普通地全部并行？
3. Token 被选中以后，为什么还要经过下一轮模型计算才形成自己的 K、V？
4. Temperature 和 Top-p 改变模型权重了吗？
5. 为什么 Session 中保存了内容，不代表本次模型一定看到？
6. 输入更长和输出更长分别主要增加什么工作？
7. 模型、生成控制器、Runtime 和 Agent 分别负责什么？
8. 什么证据才能说明模型参数真的发生了学习更新？
