# 单次 LLM 请求与 Agent 执行循环有什么区别

> [!summary]
> 一次 LLM 请求在给定上下文中生成一条输出序列；Agent 则在模型外维护目标和状态，可能多次调用 LLM、工具与验证器，直到完成、失败或请求人工处理。

> [!phase] 从 LLM 过渡到 Agent
> 本篇只建立接口边界，Agent 的规划、工具、记忆、工作图和治理机制将在后续 Agent 模块展开。

## 一次LLM请求是什么

从本部分已经学过的路径看：

```text
本次输入Messages
→ Token序列
→ Prefill
→ 逐Token生成
→ 满足停止条件
→ 得到一次模型输出
```

这次输出可以是一段自然语言，也可以是符合某种协议的结构化内容。无论输出多长，它仍然属于一次请求内部的自回归生成。

## Agent循环又增加了什么

一个最小 Agent 循环可能是：

```text
读取目标与当前状态
→ 调用LLM决定下一步
→ 执行工具
→ 读取真实结果
→ 更新状态
→ 再次调用LLM
→ 验证是否达到完成条件
```

因此：

```text
一次LLM请求
是Agent循环中的一个可重复步骤

Agent
不是Transformer内部多加了一个Block
```

## 一个代码任务例子

用户目标：

```text
修复登录失败问题并确认测试通过。
```

只调用一次 LLM，可能得到：

```text
“问题可能出在Token过期判断，建议修改……”
```

Agent 则可能组织：

```text
第1次LLM请求：分析日志和代码，提出修改
→ 工具：读取文件并修改代码
→ 工具：运行测试
→ 测试失败，获得真实错误
→ 第2次LLM请求：根据错误修正
→ 工具：再次测试
→ 验证器：对照验收条件
→ 记录结果和证据
```

这里的“多步”发生在外部执行循环，不是同一次 Decode 在系统里自动运行测试。

## 模型输出工具调用时发生了什么

模型可以生成类似下面的结构化意图：

```text
调用：run_tests
参数：登录模块
```

但通常仍然需要外部程序：

```text
解析模型输出
→ 检查权限与参数
→ 真正执行工具
→ 把结果作为新消息加入上下文
→ 发起下一次模型请求
```

模型生成“调用工具”不等于工具已经执行成功。

## Agent为什么不自动等于准确

Agent 可以获得外部反馈，但如果没有可靠验证，也可能把一次错误扩大成多步错误：

```text
误解目标
→ 调用错误工具
→ 错误解释工具结果
→ 自己宣布完成
```

更可靠的闭环需要：

- 明确目标、约束和完成条件；
- 真实工具执行结果；
- 可重复的测试或证据；
- 失败后的恢复路径；
- 必要时的人工确认。

这也是 CodeClosure 一类系统长期有价值的原因：它不是让模型“多想几次”而已，而是把概率性行动放进可追踪、可验证的过程。

## 单请求上下文与Agent状态的区别

| 对象 | 作用范围 | 典型内容 |
|---|---|---|
| LLM上下文 | 当前一次模型请求 | 系统指令、历史摘要、当前问题、工具结果 |
| KV Cache | 当前模型生成计算 | 已处理位置的Attention状态 |
| Agent状态 | 跨多个步骤或请求 | 目标、事实、决定、约束、未决问题、工具结果 |
| 外部项目状态 | 真实世界 | 文件、数据库、测试、部署状态 |

Agent 状态不会自动进入模型。每次调用前，系统仍要选择哪些内容进入本次上下文。

## 与CoT的区别

CoT 主要讨论模型怎样通过中间推理步骤形成答案；Agent 讨论怎样在模型外循环调用、行动和验证。

```text
CoT：一次请求内部可以包含多步推理Token
Agent：一次任务可以包含多次LLM请求和工具执行
```

两者可以组合，但不是同一个层次。

## 常见误解

1. **“模型输出了工具调用，所以工具已经运行。”** 输出通常只是待执行的结构化请求。
2. **“Agent多调用几次模型，结果就一定正确。”** 没有独立证据时，多轮也可能重复同一错误。
3. **“KV Cache保存Agent任务状态。”** KV Cache 保存 Attention 计算状态，不是目标与验收记录。
4. **“一段很长的推理输出就是Agent。”** 它仍可能只是一次 LLM 请求中的 Token 序列。
5. **“Agent必须修改模型参数。”** 普通 Agent 可以始终调用固定参数模型。
