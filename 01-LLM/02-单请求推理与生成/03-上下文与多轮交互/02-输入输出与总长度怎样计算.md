# 输入、输出与总长度怎样计算

> [!summary]
> 对普通 Decoder-only 生成，输入 Token 和随后生成的 Token 位于同一条不断增长的序列中；规划一次请求时既要容纳现有输入，也要为输出预留位置。

> [!phase] 运行阶段
> 本篇使用简化预算解释因果关系。具体 API 可能另外规定最大输入或最大输出，并采用自己的计费和统计口径。

## 最简单的预算关系

在不考虑产品特殊规则时，可以先记住：

```text
本次输入 Token 数
+ 本次已生成 Token 数
≤ 模型或服务允许的上下文容量
```

输入包括 Chat Template 和特殊 Token 产生的实际序列，不只是用户肉眼输入的文字。

在生成开始前，这段已有输入常被称为 Prompt 或输入上下文；生成开始后，新 Token 会接到同一序列后面，所以“当前上下文”会随 Decode 继续增长。

## 一个小数字例子

假设教学模型的窗口容量为 16：

```text
格式化后的输入：10 Token
希望最多生成： 6 Token
总预算：        16 Token
```

如果输入增长到 13 Token，那么在同一个 16 Token 容量中，最多只剩约 3 个位置。系统可以选择：

- 减少允许输出长度；
- 压缩或截断输入；
- 拒绝请求并提示超长；
- 改用支持更长窗口的模型。

采用哪种方式是应用或服务策略，不是 Tokenizer 或模型自动理解内容后必然做出的决定。

## 为什么输出也占窗口

生成的每个新 Token 都会成为后续 Token 的已知前缀：

```text
输入序列
→ 生成 Token 1
→ 输入序列 + Token 1
→ 生成 Token 2
→ 输入序列 + Token 1 + Token 2
```

因此，输出越长，当前序列占用的位置越多，Decode 轮数和 KV Cache 通常也会继续增加。

## 三个数字不要混淆

| 名称 | 回答的问题 |
|---|---|
| 上下文窗口 | 一次生成中整条可处理序列的容量边界是什么 |
| 输入 Token 数 | 开始生成前已经送入请求多少 Token |
| 最大输出 Token 数 | 本次最多允许新生成多少 Token |

最大输出限制可能比窗口剩余空间更小。例如窗口尚有 8 个位置，但应用只允许生成 4 个 Token，回答仍会在达到 4 个后停止。

## 为什么客户端估算可能不完全准确

客户端若不知道实际 Chat Template、特殊 Token 或配套 Tokenizer，就可能漏算：

```text
用户文字
+ 角色标记
+ 系统指令
+ 工具定义或结果
+ 历史消息
= 真实输入序列
```

闭源 API 还可能采用未完全暴露的内部组织方式。因此，本地计数适合做预算，最终限制与统计应以对应模型和服务的正式接口为准。

## 常见误解

1. **“上下文窗口全部都能留给输入。”** 如果还要生成回答，就必须考虑输出增长。
2. **“最大输出 Token 等于一定会生成这么多。”** 它是上限；EOS 等条件可能更早停止。
3. **“输入只有当前用户这句话。”** 系统指令、历史和协议标记都可能占用输入。
4. **“达到窗口后模型会继续算，只是看不清。”** 合法请求通常要先被拒绝、截断或重新组织，不能假设模型无限扩展位置。

## 理解检查

1. 为什么生成 Token 也会占用上下文位置？
2. 窗口还剩 8 个位置，为什么应用仍可能只允许输出 4 个 Token？
3. Chat Template 为什么会影响长度预算？
