# 一次多轮对话怎样受到窗口限制

> [!summary]
> 多轮对话的连续感来自外部系统不断保存、选择和重新提交历史；当候选历史超过窗口预算时，上层系统必须取舍，而模型只能依据取舍后的最终上下文回答。

> [!phase] 运行阶段串联复习
> 以下 Token 数全部是教学化虚构数据，只用于连接窗口预算、多轮历史、Truncation 和缓存边界。

## 场景设定

假设一个教学模型：

```text
上下文容量：30 Token
每次希望预留输出：最多 6 Token
因此输入预算：约 24 Token
```

真实服务还可能有独立输入、输出和协议限制，这里只看最简单关系。

## 第一轮：用户提供姓名

应用准备：

```text
System：你是一个简洁的助手。       5 Token
User：我叫小林，请记住。           6 Token
角色和协议标记                     3 Token
-----------------------------------------
输入合计                          14 Token
```

14 小于输入预算 24，因此能够进入 Prefill。模型回答“好的，小林”，假设产生 4 个 Token。应用把 User 和 Assistant 消息保存进会话历史。

模型参数没有因为这一轮自动更新；当前请求的 KV Cache 则包含这次序列已经处理过的计算状态。

## 第二轮：用户询问姓名

用户问“我叫什么？”。应用从历史中重新组织：

```text
System：你是一个简洁的助手。
User：我叫小林，请记住。
Assistant：好的，小林。
User：我叫什么？
Assistant：
```

假设 Tokenize 后合计 22 Token，仍在 24 Token 输入预算内。模型这轮看得到第一轮的“小林”，所以可以回答。

```text
模型看起来记得姓名
← 历史被保存并重新加入了本次上下文
```

若 Runtime 还保留相同前缀的 Cache，它可能少做部分重复计算；即使没有 Cache，只要文字历史仍被重新提交，模型也可以重新 Prefill 后回答。

## 第三轮：历史超过输入预算

之后用户粘贴了一段长资料。应用准备的候选输入达到 38 Token，超过 24 Token 输入预算：

```text
候选输入 38
> 输入预算 24
→ 不能原样全部进入本次请求
```

此时有几种可能。

### 方案 A：直接删除最旧消息

如果第一轮姓名信息被删：

```text
本次模型输入中没有“小林”
→ 模型不再有可靠依据回答用户姓名
```

应用数据库可能仍保存第一轮，但没有选择它进入本次上下文，对模型而言仍然不可见。

### 方案 B：先摘要旧历史

应用把旧对话压缩为：

```text
对话摘要：用户名叫小林；偏好简洁回答。
```

摘要占用更少 Token，再和最新问题一起进入窗口。模型可能继续使用姓名，但原始措辞和其他未进入摘要的细节已经丢失。

### 方案 C：按当前问题检索相关信息

如果用户再次问姓名，系统可以从历史或长期记忆中检索“用户名叫小林”，只把相关片段放入请求。这样节省窗口，但检索错误或漏召回会直接影响回答。

## 这条链中每层做了什么

| 环节 | 作用 |
|---|---|
| 会话存储 | 保存全部候选历史，不受单次模型窗口直接等同限制 |
| 上下文管理 | 根据任务和预算选择、摘要、检索或删除内容 |
| Chat Template 与 Tokenizer | 把最终选择转换为实际 Token 序列并计算长度 |
| 模型上下文 | 只包含最终成功进入请求的 Token |
| KV / Prompt Cache | 复用其中某些相同前缀的计算，不选择新知识 |
| 模型生成 | 根据本次可见上下文逐 Token 产生回答 |

## 从 Agent 设计角度得到什么

LLM 的上下文窗口只是有限工作空间。要让 Agent 跨长任务或跨会话保持连续性，需要在模型外设计：

- 保存什么；
- 什么时候摘要；
- 怎样检索；
- 哪些指令绝不能丢；
- 如何验证取回的信息仍然正确；
- 怎样把选中的内容重新放入有限上下文。

这些属于后续 Agent 与持续学习模块。本篇只建立它们为什么必要的 LLM 基础。
