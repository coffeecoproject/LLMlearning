# 上下文进入窗口后，模型为什么仍可能无法正确利用

> [!summary]
> 信息进入上下文，只表示它能够参与本次模型计算；模型还必须识别哪些信息相关、找到正确位置、整合多处关系并生成正确答案，任何一步失败都可能造成“明明给了资料却答错”。

> [!phase] 运行阶段
> 本篇讨论训练完成后的模型怎样使用本次输入。模型为什么具有某种长上下文能力，见 [[01-上下文窗口长度与长上下文能力为什么不是一回事|上下文窗口长度与长上下文能力为什么不是一回事]]；这里不重讲长上下文训练。

## 先看一个直白例子

用户把一份很长的项目资料交给模型，其中包含：

```text
第 2 页：旧版本要求数据库使用 MySQL
第 18 页：大量无关会议记录
第 46 页：正式决定改用 PostgreSQL，以本页为准
第 73 页：部署日志中再次出现旧的 MySQL 示例
第 90 页：问题：最终应该使用哪个数据库？
```

所有内容都进入窗口后，模型仍然需要：

1. 找到与问题相关的几处内容；
2. 区分旧要求、正式决定和历史日志；
3. 理解“以本页为准”的优先级；
4. 生成 `PostgreSQL`，而不是被重复出现的 `MySQL` 干扰。

所以：

```text
信息存在
≠ 信息相关性被正确识别
≠ 多处信息被正确整合
≠ 最终 Token 一定正确
```

## 四个不同层次

### 第一层：信息是否真正进入窗口

先检查资料是否在 Truncation、摘要或检索过程中被删除。

如果“改用 PostgreSQL”根本没有进入最终输入，模型就没有这条证据。

这是 **可见性问题**，主要由应用的上下文管理决定。

### 第二层：模型能否找到相关信息

即使资料存在，模型仍要在大量 Token 中识别哪些位置与当前问题相关。

```text
问题：最终使用哪个数据库？
→ 应重点关联“正式决定”“以本页为准”“PostgreSQL”
```

这是 **检索与注意问题**。

### 第三层：模型能否正确整合

找到 `MySQL` 和 `PostgreSQL` 两个词还不够。模型需要理解：

```text
MySQL = 旧版本与历史日志
PostgreSQL = 后续正式决定
后续正式决定优先
```

这是 **关系整合问题**。

### 第四层：模型能否正确生成答案

即使内部已经形成较正确的表示，输出仍然经过 Logits 和 Decoding 逐 Token 产生。生成过程可能：

- 选择错误名称；
- 混合两个版本；
- 添加资料中没有的细节；
- 在较长回答中偏离原始问题。

这是 **输出可靠性问题**。

## Attention 可以读取，不等于必然正确使用

在 Decoder-only 模型中，生成位置可以通过 Causal Self-Attention 读取 Prompt 中此前的 Token。

但 Attention 不是关键词数据库查询：

```text
Query、Key 计算关联
→ 对 Value 进行加权组合
→ 经过多层 Attention、FFN、Residual
→ 形成当前 Hidden State
```

关联权重由训练形成，会受到措辞、位置、周围内容和任务模式影响。“理论上可读取”只是信息路径存在，不代表模型一定赋予正确内容足够影响。

## 为什么内容越多，任务可能反而更难

### 无关信息增加选择难度

假设回答只需要 3 句话，却输入了 300 页材料。模型必须从更多候选关系中识别真正相关的部分。

长上下文扩大了可用信息，也扩大了干扰来源。

### 重复信息可能压过较新的决定

旧规则重复十次，新规则只出现一次，不代表旧规则有效；但重复表达可能让错误候选在模型表示中变得更显眼。

### 冲突信息需要额外优先级规则

如果上下文同时包含多个答案，却没有日期、版本或权威来源，模型可能无法知道该相信哪一个。

```text
资料冲突
+ 没有明确优先级
→ 模型不是缺少窗口，而是缺少判定依据
```

### 位置可能影响使用效果

研究发现，一些受测长上下文模型在相关信息位于开头或结尾时表现较好，位于长输入中间时表现会下降。这常被称为 **Lost in the Middle**。

它不是所有模型、所有任务都必然遵循的固定定律，而是提醒我们：标称窗口长度不能代替位置敏感性测试。

> [!source]
> 来源：[Lost in the Middle: How Language Models Use Long Contexts](https://arxiv.org/abs/2307.03172)，Liu 等，2023。研究比较了多文档问答和 Key-Value Retrieval 等任务。核对日期：2026-07-29。

## “找到一句话”与“理解整份材料”不是同一能力

可以把运行时长上下文任务分为几层：

| 层次 | 示例 | 主要难点 |
|---|---|---|
| 单点检索 | 找出合同编号 | 定位一处明确内容 |
| 多点检索 | 找出三次版本变更 | 找到多处相关内容 |
| 信息整合 | 判断哪个版本最终有效 | 比较时间和优先级 |
| 摘要 | 概括整份报告 | 保留重点并避免遗漏 |
| 长距离推理 | 综合多份证据判断根因 | 建立跨段因果关系 |
| 代码理解 | 追踪定义、调用与测试失败 | 跨文件连接结构与行为 |

模型通过 Needle-in-a-Haystack 测试，只能说明它在该测试条件下能找回一条信息，不能证明它同样擅长多文档整合、长代码分析或复杂推理。

LongBench 等评测因此会把单文档问答、多文档问答、摘要、Few-Shot Learning、合成任务和代码等任务分开测试。

> [!source]
> 来源：[LongBench: A Bilingual, Multitask Benchmark for Long Context Understanding](https://arxiv.org/abs/2308.14508)，Bai 等，2023。核对日期：2026-07-29。

## 上下文组织为什么会影响结果

同一批信息可以用不同方式进入 Prompt。

### 混乱组织

```text
旧日志
新规则
无关聊天
旧规则
问题
更多无关日志
```

### 结构化组织

```text
任务：判断最终数据库

权威规则：
- 2026-07-01：改用 PostgreSQL，本决定覆盖旧版本

历史信息：
- 旧版本使用 MySQL

问题：最终使用哪个数据库？
要求：说明所依据的版本和日期
```

结构化输入没有改变模型 Weight，但减少了模型需要自己猜测的关系，通常更有利于正确利用上下文。

## Runtime 或 Agent 可以改善什么

### 选择相关内容

使用检索或规则，减少与当前任务无关的信息。

### 保留明确来源和版本

为资料加入：

```text
来源
日期
版本
是否已废弃
优先级
```

这为冲突判断提供模型能够使用的依据。

### 把关键约束放在清晰位置

不要让核心目标、不可违反的规则和验收条件埋在大量日志中。可以单独整理为结构化区域。

### 分块处理再汇总

```text
长文档
→ 多个片段分别提取事实
→ 保存来源位置
→ 汇总候选证据
→ 再让模型综合判断
```

这样能减少一次调用中的信息竞争，但跨块关系可能丢失，因此汇总时仍需保留必要联系。

### 多次调用并外部验证

对复杂任务，可以将“查找证据”“形成结论”“核验结论”拆成多次模型调用，并使用数据库、测试或规则验证结果。

这正是 Agent 循环相对“一次长 Prompt 直接给答案”的价值之一。

## Runtime 与 Agent 不能自动解决什么

它们可以改善输入质量和工作流程，但不能保证：

- 被检索遗漏的信息自动回来；
- 错误摘要恢复为原文细节；
- 模型获得训练中没有形成的长距离能力；
- 冲突资料在没有判定依据时自动产生唯一真相；
- 最终生成绝对不会出错。

所以：

```text
模型训练形成的上下文能力
× 本次上下文组织质量
× 任务本身难度
× 验证与纠错机制
→ 最终运行效果
```

这不是数学乘法公式，只用于说明任何一层明显薄弱，都可能影响最终结果。

## 与 Truncation 的区别

| 情况 | 问题发生在哪里 |
|---|---|
| 关键信息被截掉 | 没有进入模型 |
| 关键信息进入但被忽略 | 模型没有充分利用 |
| 找到多处信息但关系判断错误 | 整合失败 |
| 内部判断较对但输出写错 | 生成失败 |

看到错误答案时，需要先判断属于哪一层，不能全部归因于“窗口太小”。

## 常见误解

1. **“资料在 Prompt 里，模型就应该百分之百知道。”** 信息可见只是必要条件，不是正确使用的充分条件。
2. **“Attention 能看全部历史，所以不会漏信息。”** 能建立计算路径不代表相关性判断一定正确。
3. **“上下文越长，模型效果一定越好。”** 更多相关信息可能有帮助，更多噪声和冲突也可能造成干扰。
4. **“把关键资料重复很多遍一定更可靠。”** 重复会占用窗口，也可能放大过时或错误内容。
5. **“RAG 能突破模型的上下文能力上限。”** RAG 能筛选资料，但最终仍由模型在有限上下文中理解和生成。

## 理解检查

1. “信息进入窗口”和“模型正确使用信息”之间还需要哪几步？
2. 为什么旧规则重复多次可能干扰新规则？
3. 单点检索成功为什么不能证明复杂长文档推理可靠？
4. Runtime 或 Agent 能改善上下文利用的哪些环节，又不能改变什么？
