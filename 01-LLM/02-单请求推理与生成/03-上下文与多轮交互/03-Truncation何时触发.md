# Truncation 何时触发

> [!summary]
> Truncation（截断）是在候选输入超过允许预算时删除一部分 Token；它可能由应用、Tokenizer 工具或模型服务执行，但被删内容不会进入本次模型计算。

> [!phase] 运行阶段
> 本篇讨论请求输入的截断，不讨论因为 EOS 或最大输出长度而结束生成。

## 什么情况下需要处理超长输入

应用通常会先确定：

```text
允许的总容量
− 希望预留的输出空间
= 当前可使用的输入预算
```

如果格式化并 Tokenize 后的输入超过该预算，就必须采取某种处理。Truncation 是其中一种选择，但不是唯一选择。

## 谁可能执行 Truncation

| 所在层 | 可能做什么 |
|---|---|
| 应用或 Agent | 选择保留哪些消息、删除哪些附件、先摘要还是检索 |
| Tokenizer 工具 | 按配置从左侧、右侧或指定序列截掉 Token |
| 模型服务器或 API | 按接口规则拒绝超长请求，或执行已声明的自动截断策略 |
| 模型本身 | 只处理最终收到的 Token，通常不知道哪些内容此前被删掉 |

所以“Tokenizer 支持 `truncation=true`”只表示工具能执行机械截断，不表示它理解哪些内容最重要。

Tokenizer 工具为什么会附带这项输入整理能力，见 [[06-Vocabulary-Lookup与输入整理边界|Vocabulary Lookup 与输入整理边界]]；本篇继续讨论谁应该决定保留什么内容。

## 一个机械截断例子

假设输入预算只能容纳 8 个 Token：

```text
原序列：[A] [B] [C] [D] [E] [F] [G] [H] [I] [J]
```

从右侧截断可能得到：

```text
[A] [B] [C] [D] [E] [F] [G] [H]
```

从左侧截断可能得到：

```text
[C] [D] [E] [F] [G] [H] [I] [J]
```

两者都满足长度，但保留的信息完全不同。真实聊天还包含角色边界，粗暴切在消息中间可能破坏协议结构。

## 超长时不只有“删最旧消息”

常见策略包括：

- **拒绝**：不隐式丢信息，让调用方重新处理；
- **删除旧内容**：适合近期消息最重要的简单对话；
- **保留关键指令和最新问题**：避免系统规则或当前任务被删；
- **摘要压缩**：减少长度，但摘要可能遗漏细节或引入偏差；
- **检索相关片段**：只放入当前问题需要的内容，但检索可能漏召回；
- **分块处理**：分别处理长文，再汇总；跨块关系可能变弱。

没有一种策略对所有任务都最优。法律条款、代码上下文、闲聊和文档问答需要保留的内容不同。

## Truncation 与回答被截断不是同一件事

| 现象 | 发生位置 | 结果 |
|---|---|---|
| 输入 Truncation | Prefill 之前 | 被删 Token 从未进入本次模型上下文 |
| 达到最大输出长度 | 生成循环中 | 回答可能尚未自然结束就停止 |
| Streaming 显示不完整 | 网络或客户端层 | 模型可能已经生成，但传输或显示没有完成 |

看到回答突然结束，不能直接断定是输入 Truncation。

## 常见误解

1. **“模型会自动挑最不重要的内容删除。”** 通常是上层策略或机械规则在决定。
2. **“被截断内容仍藏在 KV Cache 里。”** 如果它根本没进入本次 Prefill，就不会形成本次 Cache。
3. **“保留最新消息永远最合理。”** 旧消息可能包含关键约束、定义或用户身份信息。
4. **“摘要不会丢信息。”** 摘要本身就是有损压缩。
