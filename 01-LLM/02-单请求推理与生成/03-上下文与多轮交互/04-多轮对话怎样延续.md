# 多轮对话怎样延续

> [!summary]
> 多轮对话通常由应用保存前面的消息，并在下一次请求中重新组织相关历史；模型之所以“记得上一轮”，首先是因为那段内容再次成为了本次可见上下文。

> [!phase] 运行阶段
> 这里讨论普通多轮交互，不表示聊天会自动训练或更新模型参数。

## 第一轮发生什么

用户说：

```text
我叫小林，请记住。
```

应用构造第一轮请求：

```text
System：你是一个助手。
User：我叫小林，请记住。
```

模型生成：

```text
Assistant：好的，小林。
```

请求结束后，模型参数通常没有改变。应用可以把 User 和 Assistant 消息保存到会话记录中。

## 第二轮为什么能回答“我叫什么”

用户接着问：

```text
我叫什么？
```

应用不是只把这四个字交给模型，而是可能重新构造：

```text
System：你是一个助手。
User：我叫小林，请记住。
Assistant：好的，小林。
User：我叫什么？
Assistant：
```

[[01-Prompt-Messages与Chat-Template|Chat Template]] 和 Tokenizer 再把整段内容变成新的输入序列。模型在 Prefill 中实际看见了“小林”，因此可以回答。

```text
应用保存历史
→ 下一轮选择相关历史
→ 重新形成模型输入
→ 模型依据当前可见上下文生成
```

## “重新发送”是逻辑概念

有些接口要求客户端每次显式提交完整消息列表；有些服务允许客户端只提交会话标识或上一响应标识，由服务端保存并恢复历史。两种形式的客户端请求不同，但对模型计算而言，相关内容仍必须以某种方式成为本次有效上下文，或者由等价的已缓存计算状态表示。

所以：

```text
客户端没有重复发送全部文字
≠ 模型可以在没有任何上下文状态时凭空记住
```

服务端是否保留历史、保留多久、能否跨设备或跨会话使用，属于具体产品和 Runtime 的实现约定。

## KV Cache 可以让多轮更快吗

如果下一轮输入完整保留上一轮前缀，并且服务系统仍保存可复用状态，Runtime 可能复用部分 KV Cache 或 Prefix Cache，减少重复 Prefill 计算。

但这是效率优化：

- 历史内容在逻辑上仍属于当前上下文；
- 修改前面的消息可能使旧缓存无法直接复用；
- Cache 被释放不等于聊天记录从数据库消失；
- 有聊天记录也不保证服务一定保留对应 Cache。

## 多轮历史为什么会越来越长

每一轮通常增加一条 User 消息和一条 Assistant 消息。若每次都重新加入全部历史：

```text
第 1 轮：System + User 1
第 2 轮：System + User 1 + Assistant 1 + User 2
第 3 轮：再加入 Assistant 2 + User 3
……
```

Token 数会持续增长，最终可能接近上下文窗口。这时应用需要删除、摘要、检索或拒绝，而不能假设所有历史永远都能同时进入模型。

## 模型回答正确不等于形成永久记忆

当前上下文可以让模型临时适应定义、格式和用户信息，但这种影响通常随本次输入结束：

```text
本次上下文改变
→ 当前 Hidden States、Logits 和回答改变

模型参数没有更新
→ 不表示下一个无历史的新会话仍然记得“小林”
```

## 常见误解

1. **“对话界面有历史，所以模型一定能看到全部历史。”** 应用可能只选择其中一部分进入请求。
2. **“第二轮记得名字，说明模型已经学习了用户资料。”** 更常见的原因是历史被重新加入了上下文。
3. **“有状态 API 一定修改了模型参数。”** 服务保存会话状态和模型训练是不同机制。
4. **“KV Cache 就是聊天数据库。”** 前者是计算状态，后者保存消息或业务数据。
