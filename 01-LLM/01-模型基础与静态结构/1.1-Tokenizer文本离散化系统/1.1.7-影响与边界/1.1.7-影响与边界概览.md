# 1.1.7 Tokenizer 的影响与边界

> [!summary]
> Tokenizer 决定模型以怎样的离散单位接收文本，因此会影响序列长度、表示效率和学习难度；但它不负责理解、推理或生成答案。

## 本节在回答什么

前面已经解释：

```text
文本怎样变成 Token ID？
```

本节进一步解释：

```text
为什么“怎样切”会影响后面的模型？
这些影响到哪里为止？
```

## 边界声明

本节只研究 Tokenizer 造成的直接后果：

- Token 数量与序列长度；
- 不同文本类型的表示效率；
- 对 LLM 学习难度的影响；
- 开放文本覆盖方式；
- Tokenizer 自身的能力边界。

本节不会展开模型服务、Runtime、KV Cache、请求路由、Agent 上下文管理或推理优化。提到“计算量”和“上下文”时，只建立必要的因果连接。

## 总体因果链

```text
Tokenizer 的词表与规则
→ 决定文本怎样被切分
→ 决定 Token ID 序列
→ 影响序列长度与基本表示单位
→ 影响后续模型面对的学习和计算问题
```

注意最后两步的措辞是“影响”，不是“决定全部结果”。LLM 的最终能力还取决于模型架构、参数规模、训练数据、训练方法和运行方式等因素。

## 完成标准

读完后应当能够：

1. 解释为什么字符数不能直接代表 Token 数；
2. 说明词表大小与序列长度之间的基本权衡；
3. 判断“中文一定比英文消耗更多 Token”为什么不严谨；
4. 解释“可以编码”和“模型理解”之间的区别；
5. 说明 Tokenizer 对模型学习的影响，但不夸大它的作用；
6. 清楚指出 Tokenizer 在 Token ID 处结束，下一步属于 Embedding。
