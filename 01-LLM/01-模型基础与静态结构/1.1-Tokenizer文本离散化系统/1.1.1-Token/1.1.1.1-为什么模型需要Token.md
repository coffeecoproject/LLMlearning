# 为什么模型需要 Token

## 一句话理解

> Token 是把开放、可变的文本世界转换成有限、稳定、可编号输入的中间单位，使神经网络能够用数值张量处理语言。

这句话包含三个关键词：

- **开放**：人可以不断创造新句子、新名字、新代码和新符号；
- **有限**：模型的输入参数必须具有预先确定的尺寸；
- **可编号**：神经网络最终接收的是数值张量，而不是字符串对象。

## 1. 计算机明明能保存文字，为什么模型不能直接读取？

计算机当然能保存文字。例如汉字“猫”可以通过 Unicode 编码保存，文件系统、数据库和程序都能处理字符串。

但“能够保存文字”和“神经网络能够对文字进行矩阵计算”是两件事。

```text
字符串系统关心：
这个字符怎样编码、保存、复制和显示？

神经网络关心：
输入怎样变成固定形状的数值张量，并参与乘法、加法和梯度更新？
```

神经网络中的基本计算类似：

$$
y = Wx + b
$$

这里的 $x$、$W$、$b$ 和 $y$ 都必须是数值。不能直接把字符串“猫”代入矩阵乘法：

```text
矩阵 × "猫"
```

这个表达式没有定义。

所以模型需要一个接口，把文本转换成数值计算可以接收的形式。

## 2. 为什么不直接给每一整句话分配一个编号？

假设建立一个“句子词表”：

```text
0 → 今天天气很好
1 → 我喜欢吃苹果
2 → 明天可能下雨
```

这看起来可以把句子转换成数字，但很快就会失败。

### 原因一：句子组合近乎无限

只要替换一个词、数字或名字，就会得到新句子：

```text
我喜欢吃苹果
我喜欢吃香蕉
小明喜欢吃苹果
小红昨天喜欢吃苹果
```

语言不是一个可以提前枚举完的有限句子表。

### 原因二：无法复用局部规律

如果每句话只有一个完全独立的 ID，模型很难复用其中的共同结构：

```text
我喜欢吃苹果
我喜欢吃香蕉
```

两句话明明共享“我喜欢吃”这一部分，但句子级编号把它们当成两个互不相关的原子对象。

### 原因三：遇到新句子就没有编号

用户输入一句训练词表中没有完整收录的新句子时，系统无法表示它。

因此，文本必须被拆成可以重复组合的更小单位。

## 3. 为什么需要“有限词表 + 可组合单元”

理想的文本接口需要同时满足几项要求：

### 3.1 输入集合必须有限

模型需要一张有限大小的 Embedding Matrix。假设词表有 $V$ 个 Token，每个 Token 的初始向量维度是 $d$，Embedding Matrix 的形状就是：

$$
V \times d
$$

如果输入单位的集合无限增长，这张参数矩阵就无法在训练前确定形状。

### 3.2 单元必须能够重新组合

有限单元应该能组合成大量文本：

```text
有限字母
→ 组合成大量单词

有限汉字和子词片段
→ 组合成大量句子

有限字节值
→ 原则上表示任意数字文本
```

### 3.3 每个单元必须能稳定映射成编号

模型不能把“苹果”直接当作矩阵索引，需要先得到类似下面的编号：

```text
"苹果" → Token ID 4281
```

这里的 `4281` 只是某个假想词表中的索引，不是“苹果”的通用编号。

### 3.4 序列不能过长

如果把所有文字都拆成极小单位，覆盖能力会很好，但序列可能非常长。序列越长，通常需要处理的位置越多，Attention 和其他计算的成本也越高。

因此需要在两端之间折中：

```text
单位很大
→ 序列较短
→ 词表巨大
→ 新文本难覆盖

单位很小
→ 词表较小
→ 新文本容易覆盖
→ 序列很长
```

现代 Tokenizer 经常采用子词和字节相关方案，就是在有限词表、开放文本覆盖和序列长度之间寻找折中。

## 4. Token 在整条链路中的位置

先看一个简化示例。以下切分只是教学假设，不代表某个真实 Tokenizer：

```text
原始文本：我喜欢学习大模型

Token：
["我", "喜欢", "学习", "大模型"]

Token ID：
[105, 832, 2047, 9184]
```

接下来模型不会直接计算字符串，而是使用这些 ID 查找向量：

```text
Token ID 105
→ 在 Embedding Matrix 中取第 105 行
→ 得到一个初始向量
```

完整关系是：

```text
文本
→ Tokenizer 决定如何表示
→ Token 序列
→ Vocabulary 提供 Token 与 ID 的对应关系
→ Token ID 序列
→ Embedding Lookup
→ 数值向量序列
```

Token 的作用不是“理解文字”，而是建立文本与模型参数之间稳定、可组合的接口。

## 5. 为什么不能直接使用 Unicode 编号？

这是一个很好的追问。

Unicode 已经给字符分配了编号，理论上确实可以把字符或字节作为模型输入单位。有些模型路线也大量依赖字节级表示。

但直接使用 Unicode 编号仍然没有解决全部问题。

### Unicode 编号只是字符编码

Unicode 编号表达的是“这是哪个字符”，不表达模型需要的可学习向量，也不自动表达字符在语言中的用法。

Unicode 数值大小没有自然语义：

```text
编号相近
不代表语义相近
```

### 字符级序列可能太长

常见片段如果每次都拆成单字符或多个字节，模型必须在更长序列中反复学习它们的组合。

例如一个常见英文单词，可以：

```text
整体或子词表示：1～2 个 Token
字符表示：多个 Token
UTF-8 字节表示：可能更多字节单位
```

所以问题不是“Unicode 能不能表示文本”，而是：

> 什么样的离散单位能以合理的词表规模和序列长度，让模型高效学习语言规律？

## 6. Token 是自然语言本来就有的吗？

不是。

自然语言中确实存在字、词、词根、词缀等结构，但模型使用的 Token 边界是 Tokenizer 设计和训练的结果。

```text
语言中的词语边界
≠ Tokenizer 的 Token 边界
```

同一段文本交给不同 Tokenizer，可能得到不同切分。原因包括：

- 使用不同训练语料；
- 采用不同词表大小；
- 使用不同算法；
- 对空格、Unicode 和字节采取不同处理方式；
- 为不同语言和任务做不同权衡。

所以 Token 不是自然界唯一正确的文本切分，而是模型系统选择的一种离散表示协议。

## 7. 如果没有 Token，会发生什么？

可以从几个失败方案反过来理解。

### 方案一：每个完整句子一个编号

失败原因：组合无限、无法覆盖新句子、局部结构不能复用。

### 方案二：每个单词一个编号

失败原因：新词、人名、拼写变化、代码和不同语言会让词表急剧膨胀，并产生未知词问题。

### 方案三：直接把 Unicode 数值大小当语义

失败原因：字符编码只负责标识字符，编号距离不代表语义关系。

### 方案四：每次运行临时创建新编号

失败原因：模型参数是按照训练时固定词表学习的。运行时随意增加或交换 ID，原有 Embedding 对应关系就会失效。

这也解释了为什么模型与 Tokenizer 必须配套：

```text
训练时：ID 4281 → 某一行 Embedding 参数

运行时如果换了词表：ID 4281 → 另一个文本片段

结果：模型取到的向量含义完全错位
```

## 8. 一个更准确的类比

可以暂时把 Tokenizer 想成模型专用的“零件分类和编号系统”。

```text
开放文本
→ 拆成有限种零件
→ 每种零件有稳定编号
→ 模型根据编号取出相应参数
```

### 类比有效的地方

- 单元集合有限；
- 单元可以重复组合；
- 每个单元有稳定编号；
- 模型依赖编号查找对应参数。

### 类比失效的地方

- Token 不一定是人能直观看懂的完整零件；
- 同一文本可能有不同合法切分；
- Token 边界由算法、语料和配置共同决定；
- 模型对 Token 的上下文表示会在每一层继续变化。

因此，类比只能帮助理解“有限单元和稳定编号”，不能代替真实 Tokenization 机制。

## 9. 开放模型观察：Qwen3-32B

### 官方公开设定

Qwen3-32B 对应版本的官方 `config.json` 声明：

```json
{
  "vocab_size": 151936,
  "bos_token_id": 151643,
  "eos_token_id": 151645,
  "hidden_size": 5120
}
```

来源：[Qwen/Qwen3-32B 官方配置](https://huggingface.co/Qwen/Qwen3-32B/blob/e3a3f59b0423be17f9582d1755fd3d5449b31a1f/config.json)，核对日期：2026-07-24。

### 它如何对应本节概念

`vocab_size = 151936` 表明模型输入协议使用一个有限规模的 Token 词表。普通文本经过配套 Tokenizer 后，必须变成这个体系中的 Token ID。

`bos_token_id` 和 `eos_token_id` 表明词表不仅包含普通文本片段，还包含表示序列边界的特殊 Token。bos = Beginning of Sequence序列开始，eos = End of Sequence序列结束

`hidden_size = 5120` 为下一专题提供接口：每个 Token ID 会被映射到对应维度的初始向量。这里暂不展开 Embedding 的具体矩阵计算。

### 它不能说明什么

仅看 `config.json` 不能知道：

- 一段具体中文会被切成几个 Token；
- 词表中每个 Token 的实际文本内容；
- Tokenizer 使用了哪些规范化和切分规则；
- 词表为什么最终选择这些片段；
- 更大的词表是否必然带来更强能力。

这些问题需要继续查看对应版本的 Tokenizer 文件和官方说明，不能从 `vocab_size` 单独推断。

## 10. 常见误解

### 误解一：Token 就是单词

错误。Token 可以是字、子词、标点、空格组合、字节或特殊标记。

### 误解二：Token ID 的数字大小代表语义

错误。ID 主要是查表索引，`1000` 不比 `10` 表达更多语义。

### 误解三：Tokenizer 已经理解了句子的含义

不准确。Tokenizer 主要按既定规则把文本映射成离散单元。上下文相关语义主要由后续 Transformer 计算形成。

### 误解四：词表越大，模型一定越聪明

错误。词表大小影响表示效率、参数量和序列长度，但模型能力还受到架构、数据、训练、参数规模和后训练等多方面影响。

### 误解五：模型运行时可以随便换 Tokenizer

通常不可以。模型的 Embedding 参数和输出层已经与训练时的 Token ID 体系绑定。

## 11. 必须掌握与可选深入

### 必须掌握

- 神经网络需要数值张量，而不是字符串；
- 开放文本需要被转换成有限、稳定、可组合的离散单元；
- Token 是文本与模型参数之间的接口；
- Token ID 是对应词表中的索引；
- 模型必须使用与训练时匹配的 Tokenizer。

### 暂时可以不掌握

- BPE 的具体合并算法；
- Unigram 的概率模型；
- Unicode Normalization 的全部形式；
- Tokenizer 训练代码；
- Embedding 参数如何通过梯度更新。

这些将在后续原子笔记中逐步展开。
