# Token 到底是什么

## 一句话理解

> Token 是某个具体 Tokenizer 的词表中可以被当作一个整体编号的离散符号；它可能对应一个字、一个词、词的一部分、标点、空白、字节片段或特殊控制标记。

定义中的每个限定词都很重要：

- **某个具体 Tokenizer**：不存在跨所有模型统一的 Token 集合；
- **词表中**：Token 必须属于有限的 Vocabulary；
- **整体编号**：一次编码结果中，它对应一个 Token ID；
- **离散符号**：Token 本身不是连续向量；
- **可能对应**：Token 不等于固定的自然语言单位。

## 1. Token 不是“词”的英文翻译

Token 常被译为“词元”，这容易让人误以为：

```text
一个 Token = 一个单词
```

实际模型中，下面这些都可能成为一个 Token：

```text
猫
苹果
ing
un
 hello
。
202
<|end_of_text|>
某个 UTF-8 字节片段
```

注意 ` hello` 可能连同前面的空格成为一个 Token。某些 Tokenizer 会把空白信息编码进文本片段，而不是永远把空格独立处理。

更准确的说法是：

> Token 是 Tokenizer 选择的机器处理单元，不是语言学预先规定的“词”。

## 2. 从三个层次理解 Token

### 2.1 表面层：一段可观察的文本片段

最直观的 Token 可能显示为：

```text
"我"
"喜欢"
"learn"
"ing"
"。"
```

但这只是表面层。某些 Token 对应字节序列、不可见空白或控制标记，未必能显示成自然、完整的字符串。

### 2.2 符号层：词表中的一个成员

可以把词表写成有限集合：

$$
V = \{t_0,t_1,t_2,\ldots,t_{|V|-1}\}
$$

其中每个 $t_i$ 是一种 Token，$|V|$ 是词表大小。

Tokenizer 把文本 $s$ 转换成 Token 序列：

$$
T(s)=(t_{i_1},t_{i_2},\ldots,t_{i_n})
$$

Token 来自有限词表，但序列长度和组合方式可以变化，所以有限词表仍能表达极其丰富的文本。

### 2.3 计算接口层：可以映射成 ID 的离散类别

模型真正接收的通常不是 Token 的表面字符串，而是 ID：

```text
Token "喜欢"
→ Token ID 832
→ Embedding Matrix 的第 832 行
```

因此，Token 在模型接口中更接近“离散类别”。Token ID 是它在具体词表中的索引，Embedding 才是模型用于计算的连续向量。

## 3. Token、Token ID、Embedding 和 Hidden State

| 对象 | 假想例子 | 本质 |
|---|---|---|
| Token | `"苹果"` | 词表中的离散符号 |
| Token ID | `4281` | 该符号在具体词表中的编号 |
| Token Embedding | `[0.12, -0.37, ...]` | 根据 ID 查到的初始可训练向量 |
| Hidden State | 随层和上下文变化的向量 | 当前 Token 位置的动态上下文表示 |

因果链是：

```text
Token
→ 映射成 Token ID
→ 根据 ID 查找 Token Embedding
→ 经过 Transformer 形成 Hidden State
```

所以不能直接说：

```text
Token 本身就是向量
```

口语中人们有时会把整条链路简称为“Token 表示”，但学习机制时必须分开。

## 4. Token type 与 Token occurrence

“同一个 Token”存在两种含义。

### Token type：词表中的类别

如果 `"苹果"` 是词表中的一个 Token，那么它是一种 Token type，并有固定 ID。

### Token occurrence：序列中的一次出现

句子：

```text
苹果公司不卖苹果。
```

假设两个“苹果”都编码为相同 Token ID，它们仍是序列中两个不同位置的 occurrence：

```text
位置 0：苹果
位置 5：苹果
```

它们查到的初始 Token Embedding 可以相同，但位置和上下文不同，经过 Transformer 后的 Hidden State 通常不同：

```text
第一个“苹果”更接近公司名称
第二个“苹果”更接近水果
```

因此：

```text
同一个 Token type
≠ 每次出现都有相同的上下文表示
```

这也是为什么静态 Token Embedding 不能直接等同于完整词义。

## 5. Token 可能有哪些形态

### 5.1 完整单词或常见词

高频片段可能作为整体：

```text
apple
模型
because
```

是否真是单个 Token，必须查看具体 Tokenizer，不能凭肉眼确定。

### 5.2 子词片段

单词可以拆成可复用部分：

```text
unbelievable
→ un + believ + able
```

这里只是示意。真实切分由具体词表和算法决定。子词让有限词表能够组合出没有完整收录的新词。

### 5.3 单个字符或多字符片段

一个汉字、字母或标点可能独立成 Token；常见的多字符组合也可能整体成 Token：

```text
猫
。
人工智能
tion
https
```

一个 Unicode 字符不保证对应一个 Token，一个 Token 也不保证只含一个字符。

### 5.4 空白相关片段

空格、换行和缩进可能：

- 独立成 Token；
- 与后面的文字合并；
- 多个连续空白组合成 Token；
- 在预处理阶段以特定方式编码。

所以：

```text
"hello"
" hello"
```

可能产生不同 Token。

### 5.5 数字片段

数字不一定按完整数值切分。`20260724` 可能被拆成多个数字片段。Token 边界本身不保证模型理解十进制位值关系。

### 5.6 字节或字节片段

Byte-level 路线可以回退到字节单位，从而覆盖罕见字符、混合语言、代码和异常字符串。

```text
字符：Unicode 层面的抽象
字节：文本编码后的存储单位
Token：具体词表中的符号
```

三者可能重合，也可能完全不重合。

### 5.7 特殊 Token

特殊 Token 主要表达模型协议结构：

```text
序列开始
序列结束
消息角色边界
填充位置
一轮对话结束
```

特殊 Token 仍属于 Token：它们有词表条目和 ID，也可以拥有 Embedding，只是功能主要是控制结构而非表示普通文本。

## 6. Token 与自然语言单位的区别

| 单位                 | 定义依据                | 是否一定等于一个 Token |
| ------------------ | ------------------- | -------------: |
| Unicode Code Point | Unicode 字符编码标准      |              否 |
| Grapheme Cluster   | 人眼感知的一个书写字符         |              否 |
| Byte               | 文本编码后的存储单位          |              否 |
| 汉字                 | 汉语书写单位              |              否 |
| Word               | 语言学或书写规则中的词         |              否 |
| Morpheme           | 最小有意义语言单位           |              否 |
| Token              | 具体 Tokenizer 词表中的符号 |              — |

例如一个看起来像单个 emoji 的图形，可能由多个 Unicode Code Point 组合，编码成多个字节，再被切成一个或多个 Token。

因此，字符数、字数、单词数和 Token 数不能简单互换。

## 7. Token 边界由什么决定

Token 边界通常受以下因素共同影响：

1. 基础表示，例如字符或字节；
2. Tokenizer 的训练语料；
3. 词表大小；
4. BPE、WordPiece、Unigram 等方法；
5. 文本规范化规则；
6. Pre-tokenization 规则；
7. 空格、标点和数字的处理；
8. 特殊 Token 配置。

Token 边界不是唯一的自然答案，而是工程和统计选择。

### 相同文本，不同模型

```text
相同字符串
→ 不同 Tokenizer
→ 不同 Token 序列
→ 不同 Token ID
→ 不同序列长度
```

### 相同片段，不同周围文本

空格、前后字符和预切分规则可能参与编码，因此同一个可见片段处于不同位置时可能出现不同切分。

不过，对确定版本和配置的 Tokenizer 来说，编码通常是确定性的：相同的精确输入与相同配置应产生相同 ID 序列。这与“换 Tokenizer 或改变上下文后切分可能不同”并不矛盾。

## 8. Token 有语义吗

需要分层回答。

### 从 Tokenizer 角度

Tokenizer 主要依据文本统计、算法和规则建立词表，不需要先像人一样理解每个片段。

### 从模型训练角度

Token 对应的 Embedding 和网络参数在大量上下文中被训练，会逐渐编码有助于预测的语言和语义规律。

### 从当前上下文角度

完整语义还取决于位置、上下文和 Transformer 各层计算。

更准确的结论是：

> Token 是离散符号；语义相关结构主要体现在训练得到的参数与上下文相关 Hidden State 中。

## 9. Tokenization 一定可逆吗

理想情况下：

```text
decode(encode(text)) = text
```

许多现代 Tokenizer 会尽量支持恢复原始文本，字节级方案尤其利于覆盖任意有效字节序列。

但不能把“逐字节完全可逆”当成所有 Tokenizer 的普遍定律。如果编码前进行了会改变文本的规范化，例如统一 Unicode 形式、大小写或空白，解码可能恢复规范化后的文本，而不是原始输入的每个细节。

需要分别检查：

```text
原始文本
→ 是否规范化
→ 怎样切分
→ 怎样编码
→ 解码恢复哪一层文本
```

## 10. 一个完整的假想例子

下面不是任何真实模型的结果，只用于区分概念。

```text
ID 0   → <bos>
ID 17  → "我"
ID 52  → "喜欢"
ID 91  → "苹果"
ID 203 → "公司"
ID 8   → "。"
```

文本 `我喜欢苹果公司。` 可能编码为：

```text
Token type：
[<bos>, "我", "喜欢", "苹果", "公司", "。"]

Token ID：
[0, 17, 52, 91, 203, 8]

Token occurrence：
位置 0 的 <bos>
位置 1 的 "我"
位置 2 的 "喜欢"
……
```

模型随后根据每个 ID 查找初始向量。即使一个 Token 在句中出现两次，它们也是两个位置上的 occurrence，并会形成各自的 Hidden State。

## 11. 开放模型观察：Meta Llama 3 Tokenizer

### 官方代码公开了什么

Meta 的 Llama 3 官方 Tokenizer 实现使用 TikToken 模型，并声明 `256` 个预留特殊 Token。代码列出的特殊 Token 包括：

```text
<|begin_of_text|>
<|end_of_text|>
<|start_header_id|>
<|end_header_id|>
<|eot_id|>
```

对话编码代码会把角色名称、消息内容和消息结束边界共同编码成 Token ID 序列。`<|eot_id|>` 在代码中被标注为 `end of turn`。

来源：[Meta Llama 3 官方 `tokenizer.py`](https://github.com/meta-llama/llama3/blob/main/llama/tokenizer.py)，核对日期：2026-07-24。该仓库已于 2026-03-01 归档为只读，因此这里明确观察的是 **Llama 3**，不推断后续所有 Llama 版本完全相同。

### 它如何对应本节概念

这说明真实模型词表不只包含普通文本片段，还包含协议符号。表面字符串 `<|eot_id|>` 在被允许作为特殊 Token 时，可以整体映射成特殊 ID；如果不允许，也可以被当作普通字符文本编码。

所以，“看起来相同的字符串”和“是否被解释为特殊 Token”属于两个层次。具体行为还取决于 `allowed_special`、`disallowed_special` 等编码配置。

### 它不能说明什么

仅看这份实现，不能确定：

- 任意中文句子的具体切分结果；
- 每个普通 Token 的词表内容；
- Token 在模型内部具有怎样的语义；
- 后续 Llama 版本的特殊 Token 完全一致；
- 特殊 Token 本身足以保证模型稳定遵循角色。

模型版本和 Prompt Format 必须分别核对。

## 12. 常见误解

### 中文一个字就是一个 Token

不一定。一个字可能独立成 Token，也可能与其他字组合，或拆成字节片段。

### 英文一个单词就是一个 Token

不一定。常见词可能整体表示，罕见词可能拆成多个子词，空格也可能影响结果。

### Token 是向量

不准确。Token 是离散符号，Token ID 是编号，Embedding 才是向量。

### 一个 Token 永远有固定含义

不准确。Token type 的 ID 固定，但每次出现的上下文、位置和 Hidden State 不同。

### Token 边界就是语义边界

错误。切分服务于有限词表和计算效率，不保证符合人类语义边界。

### 特殊 Token 就是普通字符串

不完整。它有可读名称，但是否编码成特殊 ID 取决于 Tokenizer 配置和调用方式。

### Token 越长越高级

错误。较大片段可能减少序列长度，但增加词表规模并影响罕见文本覆盖。这是权衡，不是能力等级。

## 13. 必须掌握与可选深入

### 必须掌握

- Token 是具体词表中的离散符号；
- Token 不固定等于字符、字或单词；
- Token、Token ID、Embedding 和 Hidden State 是不同对象；
- Token type 与序列中的 occurrence 不同；
- Token 边界由具体 Tokenizer 决定；
- 特殊 Token 也是词表协议的一部分。

### 可选深入

- Unicode Code Point 与 Grapheme Cluster；
- UTF-8 字节结构；
- Tokenizer 正则预切分规则；
- Tokenization 的形式化唯一性；
- 规范化规则对可逆性的影响。
