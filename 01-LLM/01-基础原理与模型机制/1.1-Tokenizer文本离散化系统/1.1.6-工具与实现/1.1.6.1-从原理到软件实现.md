# 1.1.6.1 从原理到软件实现

> [!summary]
> 一个可工作的 Tokenizer 不是单独一个 BPE 算法，而是“处理流程 + 已学规则 + 词表 + 特殊 Token 配置 + 执行这些内容的软件”。

## 先分清四个层次

以导航为类比：

| Tokenizer 世界 | 导航类比 | 含义 |
|---|---|---|
| BPE / WordPiece / Unigram | 路线规划方法 | 用什么原则建立词表、选择切分 |
| SentencePiece / tiktoken / HF Tokenizers | 导航软件 | 执行规则的程序 |
| 词表、Merge Rules、配置文件 | 地图数据 | 程序真正读取的数据 |
| 某模型的 Tokenizer | 某地区某版本地图 | 工具加载一组确定文件后的具体实例 |

类比的边界是：Tokenizer 并不是在运行时寻找现实道路，它是在一套有限的、已经确定的规则中把文本映射为 ID。

## 【训练阶段】软件学习什么

以 BPE 为例：

```text
准备训练语料
→ 规范化与预处理
→ 统计相邻单位
→ 反复选出合并项
→ 得到 Vocabulary 与 Merge Rules
→ 保存为可复用文件
```

这里“软件训练”与“机器训练”并不矛盾：人编写训练程序、选择语料和参数，计算机自动统计和执行算法。它不是人逐条手写所有合并规则，也不一定是神经网络在学习。

## 【运行阶段】软件执行什么

```text
加载某模型的 Tokenizer 文件
→ 接收一段新文本
→ 按固定流程处理
→ 按已学规则切分
→ 查词表得到 Token ID
→ 交给模型
```

例如用户输入“我喜欢苹果”，`encode()` 不会重新分析全世界语料，也不会修改词表。它只在现有规则中确定结果。

## 【两阶段共同】为什么文件必须一致

假设 LLM 训练时，ID `10001` 对应“苹果”；运行时却换了词表，让 `10001` 对应“汽车”。Embedding 层仍会取第 `10001` 行，但这行参数是在“苹果”的训练样本中学到的，含义便完全错位。

因此模型权重和 Tokenizer 是配套资产：

```text
同一个 ID
必须在 LLM 训练和运行时指向同一个 Token
```

## 常见误解

- **“知道用了 BPE，就能复现 Token 结果。”** 不能。还需要具体词表、合并规则、规范化和特殊 Token 配置。
- **“同一个库的 Token ID 都一样。”** 不一样。ID 由加载的具体词表决定。
- **“每次聊天都在训练 Tokenizer。”** 通常没有，聊天时主要是在运行已固定的 Tokenizer。
- **“Tokenizer 文件只是辅助文件，换掉没关系。”** 换错会让 ID 与模型参数错位。
