# 1.2.2.1 Token ID 为什么不能直接计算语义

> [!summary]
> Token ID 的职责是唯一定位词表项，而不是表达大小、方向和语义关系；Embedding 的第一项任务，就是把这种离散索引转换成可学习、可连续计算的向量。

## ID 是名称，不是测量值

假设某个示意词表是：

```text
10001 → 苹果
10002 → 汽车
10003 → 香蕉
```

这些编号只能说明查表位置。不能推出：

```text
香蕉比苹果“大 2”
汽车位于苹果和香蕉的语义中间
ID 相近的 Token 含义也相近
```

> [!note]
> 上述 Token 与 ID 映射完全是教学示意，不来自真实模型。

这与电话号码类似：两个号码相差 1，不代表两个人只相差一种性格。号码的功能是找到对象，不是描述对象。

## 如果直接使用 ID，会引入错误关系

假设模型把 ID 当作普通数值：

```text
苹果 = 10001
汽车 = 10002
香蕉 = 10003
```

那么数值计算天然会认为：

```text
苹果与汽车的距离 = 1
汽车与香蕉的距离 = 1
苹果与香蕉的距离 = 2
```

但这些距离只是词表编号造成的偶然结果，与真实语言关系无关。改变词表排列，所有这种“关系”都会变化。

因此，ID 可以作为查询地址，却不适合直接作为模型理解 Token 的内部表示。

## One-hot 能解决编号大小，但仍不够实用

一种中间想法是 One-hot（独热向量）。假设词表只有四项：

```text
Token A → [1, 0, 0, 0]
Token B → [0, 1, 0, 0]
Token C → [0, 0, 1, 0]
Token D → [0, 0, 0, 1]
```

它消除了“编号越近，语义越近”的错误暗示，也能唯一表示每个 Token。

但大型词表可能有十几万项，于是每个 One-hot 向量也要十几万维，而且绝大多数位置都是 0。更重要的是，不同 Token 的 One-hot 向量彼此正交，本身没有可学习的紧凑关系。

## Embedding 的解决思路

模型为每个 Token ID 准备一个固定宽度、可训练的向量：

```text
Token ID
→ 定位该 Token 的参数行
→ 取出 hidden_size 个浮点数
→ 得到初始 Token Embedding
```

例如示意模型可能把三个 Token 映射为：

```text
苹果 → [ 0.2, -0.7,  0.4, 0.9]
汽车 → [-0.8,  0.1, -0.5, 0.3]
香蕉 → [ 0.3, -0.6,  0.5, 0.8]
```

这些数不是由 Token ID 的大小计算出来的，而是对应参数在 LLM 训练中被逐步调整的结果。

## “不能直接计算”不代表 ID 没用

ID 非常重要，它完成了两个系统之间的契约：

```text
Tokenizer：输出 Token ID
LLM：使用相同 ID 找到对应 Embedding 行
```

问题不在于 ID 是整数，而在于不能把整数的大小和差值当成语义。它应该作为索引使用。

## 阶段边界

- **【模型运行阶段】**：输入 ID 用于查找 Embedding，不会先根据 ID 大小推导语义。
- **【模型训练阶段】**：被查出的 Embedding 参与计算，其参数通过训练逐渐更新。

本篇只解释为什么需要映射；参数怎样学习放在 [[1.2.3-Embedding参数与学习概览|Embedding 参数与学习]]。

## 常见误解

- **“Token ID 是数字，所以神经网络已经可以直接理解。”** 可存入张量不等于具有合理语义结构。
- **“相邻 ID 对应相近含义。”** ID 排列由词表决定，不保证语义邻近。
- **“Embedding 是把 ID 除以某个数。”** 它通常是用 ID 查找一行可训练参数。
- **“ID 没有语义，所以没有作用。”** 它是 Tokenizer 与模型参数之间的稳定索引。
