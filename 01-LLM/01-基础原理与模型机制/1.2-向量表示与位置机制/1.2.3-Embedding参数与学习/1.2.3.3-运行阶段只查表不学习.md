# 1.2.3.3 运行阶段只查表、不学习

> [!summary]
> 普通模型运行时仍会执行 Embedding Lookup，但通常只读取训练好的权重并完成前向计算，不计算训练 Loss、反向传播或更新参数。

## 运行时发生的主线

用户输入：

```text
我喜欢苹果
```

模型运行过程中的输入部分是：

```text
文本
→ 固定 Tokenizer
→ Token ID
→ 读取固定 Embedding Matrix
→ Embedding Lookup
→ 初始 Token Embedding
→ 后续 Transformer 前向计算
```

这条链路与训练阶段都包含 Lookup，因为无论是否训练，Token ID 都必须先变成模型向量。

## 运行时省掉了什么

普通推理通常没有：

```text
与训练标签比较
→ 计算训练 Loss
→ 反向传播
→ 计算梯度
→ Optimizer 更新参数
```

因此同一个模型、同一个 Token ID 在普通运行开始时会读取同一行 Embedding 参数。

## 新对话会改变 Embedding 吗

通常不会。即使你告诉模型一个新事实：

```text
请记住，我把项目代号改成 Aurora。
```

这段文字会进入当前上下文，影响本次或后续仍保留该上下文的前向计算，但不会自动把新事实写入 Embedding Matrix。

```text
上下文中暂时可用
≠ 模型参数已经更新
```

如果新开对话且没有外部记忆再次提供信息，模型不一定还能使用这个事实。

## 上下文适应为什么看起来像学习

模型可以根据当前提示临时改变回答方式：

```text
“接下来把 Aurora 理解为我的项目名称。”
```

后续 Token 的 Hidden State 会结合这条上下文，所以模型可能正确使用新定义。这叫上下文内适应或 In-context Learning。

但在普通推理中：

```text
Embedding 权重没变
Transformer 权重没变
变化的是当前请求中的激活值与 Hidden State
```

所以“表现得像学会了”和“参数真的被训练更新”必须区分。

## 推理 Runtime 与模型机制的边界

Runtime 可能负责：

- 将多个请求组成 Batch；
- 管理模型权重所在设备；
- 缓存中间计算；
- 调度生成请求。

这些不会自动把推理变成训练。只要没有启用梯度计算、反向传播和优化器更新，Embedding 参数通常保持固定。

## 什么时候运行过程中可能更新参数

如果系统明确执行以下工作，情况才不同：

- 在线训练或持续训练；
- 用户触发微调；
- 测试时训练或特定适应算法；
- 某些实验性持续学习系统。

这些属于额外训练流程，不是普通 LLM 推理的默认行为。后续“持续学习”和“自我改进”模块会专门讨论。

## 模型生成的新 Token 也要 Lookup 吗

模型每次选择出新的 Token ID 后，为了继续预测下一个 Token，该新 Token 也必须作为后续输入表示的一部分。

概念上仍然需要获得它对应的 Embedding。实际高效推理会复用缓存，避免重复计算此前所有位置，但这属于推理优化，不在本节展开。

## 常见误解

- **“运行时不训练，所以不需要 Embedding。”** 不训练只是不更新参数，ID 仍必须查表成向量。
- **“模型记住当前提示，说明 Embedding 已被修改。”** 可能只是上下文中的 Hidden State 在发挥作用。
- **“多个用户组成 Batch 会让模型互相学习。”** Batch 是并行组织方式，独立请求不会因此更新权重或共享语义上下文。
- **“推理模型会在思考过程中训练自己。”** 默认仍是固定参数的前向生成。
