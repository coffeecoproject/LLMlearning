# 注意力结构怎样改变缓存形态

> [!summary]
> Runtime管理的是模型实际产生的缓存状态；KV Head数量、MLA潜在表示和可见范围不同，都会改变每个位置需要保存什么以及缓存怎样增长。

> [!phase] 两阶段共同：结构在训练前确定，影响运行缓存
> 本篇只连接架构与Runtime资源，不重复推导Attention计算，也不计算真实字节数。

## Runtime不能随意选择缓存形态

模型采用什么 Attention 结构，通常已经由架构和训练后的权重确定。Runtime 必须按照对应结构保存可复用状态：

```text
模型结构决定产生什么状态
→ Runtime决定怎样高效存放和访问
```

Runtime 可以改变布局、精度或放置方式，但不能把 MHA 模型直接当作 MLA 模型运行。

## MHA、GQA与MQA主要改变KV Head数量

假设都有多个 Query Head：

```text
MHA：每个Query Head通常有对应KV Head
GQA：一组Query Head共享较少的KV Head
MQA：多个Query Head共享一组KV Head
```

KV Head 更少，通常意味着每个 Token 位置要保存的 K/V 路径更少，因此为降低运行缓存规模提供条件。

但不能直接推出固定节省倍数或速度倍数，真实性能还受层数、Head Dimension、精度、序列长度、内核和硬件影响。

机制复习：[[05-MHA-GQA与MQA完整对比|MHA、GQA 与 MQA 完整对比]]。

## MLA改变的是表示方式

以 DeepSeek 的 MLA 为例，核心不只是减少 KV Head，而是把 K/V 内容组织到更紧凑的潜在表示中，并处理位置相关分支。

因此运行时保存的内容可能更接近：

```text
紧凑KV潜在表示
+ 必要的位置相关状态
```

不能只看到“KV Cache”这个通用名称，就断言所有模型都保存形状相同的完整 K、V。

机制复习：[[05-MLA与MHA-GQA-MQA有什么不同|MLA 与 MHA、GQA、MQA 有什么不同]]。

## 可见范围也会影响增长

标准全局 Causal Attention 通常需要访问此前所有可见位置。某些模型层采用 Sliding Window 或其他局部可见策略后，只需维持一定范围内的历史状态，相应层的缓存增长方式可能不同。

这并不表示整个模型一定只看局部范围；具体模型可能混合多种层结构，需要根据官方配置和实现判断。

## 开放模型观察

- `Qwen/Qwen3-8B` 官方配置公开 `num_attention_heads: 32`、`num_key_value_heads: 8`，属于 GQA 结构观察；
- DeepSeek-V3 官方技术报告说明其延续 MLA，需要结合潜在表示相关配置理解缓存，而不能只比较 KV Head 数量。

来源：[Qwen3-8B官方配置](https://huggingface.co/Qwen/Qwen3-8B/blob/main/config.json)、[DeepSeek-V3技术报告](https://arxiv.org/abs/2412.19437)，核对日期：2026-07-28。

## 常见误解

1. **“Runtime可以随意把MHA缓存改成MQA缓存。”** 结构必须与模型权重和计算路径匹配。
2. **“KV Head减半，真实速度必然翻倍。”** 真实瓶颈由多项因素共同决定。
3. **“MLA只是更少的KV Head。”** 它还改变K/V内容的中间表示方式。
4. **“局部Attention说明整个模型永远看不到更早内容。”** 模型可能混合不同可见范围的层。
