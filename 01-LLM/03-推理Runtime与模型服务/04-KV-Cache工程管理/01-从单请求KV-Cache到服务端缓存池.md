# 从单请求 KV Cache 到服务端缓存池

> [!summary]
> 每个请求都有自己的逻辑 KV Cache；Runtime 把有限的物理缓存空间组织成共享资源池，再记录每个请求当前占用了哪些空间。

> [!phase] 运行阶段：多请求服务

## 先连接单请求机制

单个请求生成时：

```text
Prefill建立历史缓存
→ Decode读取历史并追加当前位置
→ 序列越长，缓存记录的位置越多
```

如果只有一个请求，只需关注它自己的缓存怎样增长。在线服务同时处理很多请求后，问题变成：

```text
同一份模型权重
+ 多个独立请求
+ 每个请求自己的KV Cache
+ 有限的GPU显存
```

## 逻辑缓存与物理缓存池

可以先区分两层：

| 层 | 表示什么 |
|---|---|
| 请求的逻辑KV Cache | 这个请求从第一个位置到当前位置的历史状态 |
| Runtime的物理缓存池 | 实际可分配给所有请求的设备内存空间 |

请求 A 和请求 B 都从共享缓存池取得空间，但 Runtime 必须保存各自的归属关系：

```text
请求A → 自己的一组缓存位置
请求B → 自己的另一组缓存位置
```

共享的是资源池，不是历史内容。

## Runtime至少要记录什么

概念上需要知道：

- 哪些空间空闲；
- 哪些空间属于请求 A、B 或 C；
- 每个请求目前保存到哪个位置；
- Decode 时应该读取哪些历史块；
- 请求结束后哪些空间可以释放；
- 哪些已计算前缀允许继续复用。

具体 Runtime 可以使用不同类名和数据结构，但这些职责不能凭空消失。

## 一个小例子

假设缓存池只有 8 个教学用 Block：

```text
A使用：Block 1、Block 4
B使用：Block 2
空闲：Block 3、5、6、7、8
```

A 继续生成时可能再申请一个 Block；B 完成后，它使用的空间可以解除占用。Runtime 根据映射找到正确历史，而不是要求 A 和 B 的空间彼此相邻。

> [!warning] 示例边界
> Block 数字是教学虚构，不代表真实 vLLM 配置或显存地址。

## 与调度器怎样连接

调度器想让某个请求进入本轮计算时，还要确认它有足够的缓存空间：

```text
有计算机会但没有缓存空间
→ 请求仍可能无法安全推进
```

因此 [[00-批处理与调度概览|批处理与调度]]决定“谁获得执行机会”，KV Cache Manager决定“它的运行状态放在哪里”。

## 常见误解

1. **“缓存池是所有请求共同的一份上下文。”** 它是共享物理资源，逻辑内容按请求隔离。
2. **“每个请求都复制一份模型权重。”** 权重通常共享，请求主要拥有各自的动态状态。
3. **“请求ID就是缓存内容。”** 请求ID只是建立归属和查找关系的标识之一。
