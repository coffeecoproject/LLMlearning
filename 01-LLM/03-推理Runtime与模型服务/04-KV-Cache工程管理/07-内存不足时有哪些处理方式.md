# 内存不足时有哪些处理方式

> [!summary]
> 当缓存空间不足时，Runtime不能无代价地继续接纳请求；它只能在等待、拒绝、释放复用缓存、暂停重算、搬运数据或降低缓存精度之间取舍。

> [!phase] 运行阶段：资源权衡
> 本篇只理解方案与代价，不学习配置命令和数据传输公式。

## 先明确：空间不足必须付出代价

如果缓存池已被活跃请求占满，新请求和正在增长的旧请求会争夺同一资源。Runtime 没有“凭空增加显存”的选项，只能改变时间、位置、精度或接纳策略。

## 1. 等待或限制新请求

```text
空间不足
→ 新请求留在队列
→ 等旧请求完成后再进入
```

优点是不会破坏现有缓存；代价是排队时间增加。服务也可以在超过限制时直接拒绝，以保护已经接纳的请求。

## 2. 驱逐未被活动请求占用的Prefix Cache

```text
保留的旧前缀目前无人使用
→ 放弃未来复用机会
→ 把Block交给新请求
```

这换回空间，但以后再次遇到相同前缀时需要重新 Prefill。

## 3. 暂停或抢占请求

Runtime 可以暂时让某个请求退出活跃集合，把资源让给其他请求。恢复时可能：

- 重新计算已丢弃的缓存；
- 从其他位置取回缓存；
- 等待足够空间后继续。

这会影响延迟和公平性，因此必须由调度策略决定，而不是随意覆盖活动缓存。

## 4. Offload：把缓存搬到较慢的存储层

Offload 可以把部分 KV Cache 从 GPU 移到 CPU 内存或其他存储位置，腾出宝贵的设备空间。代价是之后使用时需要传输回来，可能增加延迟并占用带宽。

```text
节省GPU空间
↔ 增加数据搬运
```

## 5. 量化：用更低精度保存缓存

KV Cache Quantization 用更少位数表示缓存，从而降低容量占用。代价可能包括额外转换工作、速度变化，以及近似误差带来的质量风险；具体影响必须由对应模型、实现和任务测量。

```text
更省空间
↔ 额外处理与潜在近似误差
```

## 一张权衡表

| 方案 | 主要换回什么 | 主要付出什么 |
|---|---|---|
| 等待 | 保护已有请求状态 | 排队延迟 |
| 拒绝或限制 | 保持服务稳定 | 新请求无法立即服务 |
| 驱逐Prefix Cache | 释放可复用块 | 未来重复Prefill |
| 暂停并重算 | 释放活动资源 | 恢复时间和重复计算 |
| Offload | 节省GPU空间 | 数据传输和延迟 |
| 量化缓存 | 降低缓存占用 | 转换成本和潜在误差 |

## 开放实现观察

Hugging Face Transformers 当前官方缓存策略文档公开了 Offloaded Cache 和 Quantized Cache，并明确把它们描述为内存与速度之间的权衡。服务型 Runtime 的具体支持方式和行为应以对应实现为准。

来源：[Hugging Face Cache Strategies](https://huggingface.co/docs/transformers/en/kv_cache)，核对日期：2026-07-28。

## 常见误解

1. **“内存不够时Runtime总能自动解决且没有影响。”** 任何方案都会牺牲等待、计算、传输、精度或接纳能力中的一项。
2. **“Offload等于删除缓存。”** 它主要改变存放位置。
3. **“量化KV Cache和量化模型权重完全相同。”** 两者针对不同对象，也可能采用不同配置和误差权衡。

2. Offload 用什么代价换取 GPU 空间？
3. 为什么不能只凭“更省显存”判断量化缓存一定更好？
