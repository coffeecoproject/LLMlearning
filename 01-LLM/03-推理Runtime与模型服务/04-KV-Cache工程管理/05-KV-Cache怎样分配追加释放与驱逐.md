# KV Cache 怎样分配、追加、释放与驱逐

> [!summary]
> 请求运行时需要取得并追加缓存空间；请求完成后会解除占用，而保留下来的可复用缓存还可能在空间紧张时被驱逐。四个动作含义不同。

> [!phase] 运行阶段：缓存生命周期

## 1. 分配：为请求准备空间

请求进入 Prefill 前，Runtime 要确认缓存池能否容纳它当前需要的状态：

```text
请求进入
→ 查找可用Block
→ 建立“请求ID到Block”的映射
→ 模型计算结果写入这些Block
```

如果没有足够空间，请求可能等待，而不是直接开始后再无处保存状态。

## 2. 追加：序列增长时继续取得空间

Prefill 写入输入位置，Decode 又不断产生新位置：

```text
当前Block还有空位
→ 继续写入

当前Block已满
→ 申请新Block
→ 更新请求的Block映射
```

追加的是当前请求的新缓存状态，不是修改模型权重。

## 3. 释放：请求不再占用空间

请求遇到 EOS、长度限制、取消或错误后，不再需要继续生成。Runtime 会解除请求与其缓存空间的活动占用关系。

```text
请求结束
→ 请求状态完成
→ 缓存空间可以重新进入资源管理流程
```

具体系统可能立即清空，也可能暂时保留可复用前缀信息。释放请求占用不一定等于所有相关数据立刻被物理覆盖。

## 4. 驱逐：放弃已保留的可复用内容

如果某些缓存块为了 Prefix Cache 被暂时保留，空间紧张时 Runtime 可以取消它们的复用资格，把物理块交给新请求：

```text
旧前缀目前没有活动请求使用
→ 缓存池需要空间
→ 驱逐旧缓存记录
→ Block重新分配
```

驱逐主要意味着未来无法继续命中这份缓存，需要重新 Prefill；它不等于删除模型权重或用户数据库中的原始对话。

## 四个动作放在一起

| 动作 | 直白含义 | 发生后主要变化 |
|---|---|---|
| 分配 | 给请求空间 | 请求获得可写缓存位置 |
| 追加 | 序列继续增长 | 请求得到更多位置 |
| 释放 | 请求不再活动占用 | 空间可以被回收或保留复用 |
| 驱逐 | 放弃某份可复用缓存 | 物理块可交给其他内容 |

## 与引用关系的直觉

如果一个缓存块正被活动请求使用，就不能随意交给别人覆盖。只有当系统确认没有仍需读取它的请求，才可以安全释放或驱逐。

真实 Runtime 可能使用引用计数、状态表或其他机制；概览阶段只需理解“先确认归属与使用状态，再回收”。

## 开放实现观察：vLLM

vLLM 当前 Prefix Caching 设计公开了 Block Allocation、Free 和 Eviction 等操作，并为 Block 记录请求使用关系。这里借它说明生命周期概念，不要求学习其队列和数据结构代码。

来源：[vLLM Automatic Prefix Caching](https://docs.vllm.ai/en/stable/design/prefix_caching/)，核对日期：2026-07-28。

## 常见误解

1. **“请求结束就一定把所有字节立即清零。”** 解除逻辑占用、保留复用和物理覆盖是不同动作。
2. **“驱逐KV Cache会删除模型知识。”** 模型参数不因此改变。
3. **“释放和驱逐是同义词。”** 释放活动请求占用；驱逐通常针对已保留的可复用内容。
