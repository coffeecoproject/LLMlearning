# KV Cache 工程管理概览

> [!summary]
> 单请求机制说明为什么可以缓存历史 K、V；Runtime 工程则负责为许多长度不断变化的请求分配、定位、复用和释放缓存内存。

> [!phase] 运行阶段：模型服务
> 本专题研究训练完成后，Runtime 怎样管理多请求产生的缓存；不讨论训练缓存，也不重新推导 Q、K、V 的计算公式。

## 从已经学过的内容继续

[[01-KV-Cache保存什么|KV Cache 保存什么]]已经解释：每个请求会保存此前位置在各 Attention 层形成的可复用状态，让后续 Decode 不必重复生成历史 K、V。

现在把一个请求扩展成模型服务：

```text
请求A有自己的KV Cache
请求B有自己的KV Cache
请求C有自己的KV Cache
        ↓
它们共同使用有限的GPU显存
        ↓
Runtime必须统一管理
```

这就是本专题的新问题。不是“缓存里算什么”，而是“许多不断增长和结束的缓存怎样共享物理资源”。

## 一条工程管理主线

```text
请求进入
→ 检查是否有可复用前缀
→ 分配缓存空间
→ Prefill写入历史状态
→ Decode不断追加新位置
→ 请求结束或被暂停
→ 释放、保留复用或驱逐缓存块
→ 空间交给其他请求
```

Runtime 的调度器决定谁获得计算机会；KV Cache Manager 则保证相应请求有空间保存和读取自己的历史状态。两者必须协同，但职责不同。

## 为什么不能给每个请求简单准备一个大箱子

请求刚到来时，Runtime 通常不知道它最终会生成多长：

```text
提前准备很大的连续空间
→ 很多请求实际用不完
→ 产生预留浪费

只准备很小的空间
→ 请求继续生成时还要扩展
→ 连续空间不一定容易找到
```

同时，请求会在不同时间开始和结束，显存中容易留下大小不一的空位。这推动 Runtime 使用更灵活的分块与分页管理。

## 分页思路的直白理解

分页管理把 KV Cache 空间拆成许多固定大小的 Block：

```text
请求A的逻辑历史：第1段 → 第2段 → 第3段

物理缓存块：Block 7 → Block 2 → Block 9
```

这些块在物理位置上不必连续，只要 Runtime 保存正确映射，Attention 仍能按请求的逻辑顺序读取。

这类似一本书的内容分散存放在不同书架位置，同时有一张目录告诉系统正确阅读顺序。类比的边界是：真实系统管理的是各层张量块，不是文字页面。

## Prefix Cache又在复用什么

如果两个请求拥有完全匹配的输入前缀，第二个请求可能复用第一个请求已经计算出的前缀缓存块：

```text
相同系统提示词 + 相同文档前缀
→ 前缀Token完全匹配
→ 找到可复用的KV Cache块
→ 只计算后面不同的部分
```

它主要减少重复 Prefill，不等于长期记忆，也不是“意思相近”就能复用。跨用户复用还必须考虑隔离与安全。

## 这个专题与相邻概念的边界

| 概念 | 研究的问题 |
|---|---|
| 单请求KV Cache机制 | 为什么历史K、V可以复用 |
| Batch与调度 | 本轮哪些请求获得计算机会 |
| KV Cache工程管理 | 每个请求的缓存空间怎样分配、定位和回收 |
| 上下文管理 | 哪些信息应该成为模型输入 |
| Session或长期记忆 | 产品如何保存跨请求的历史与状态 |

KV Cache 是由实际 Token 计算产生的临时运行状态，不等于原始文字记录，也不等于 Agent 的 Session。

## 学习尺度

必修部分只要求理解：

- 缓存属于哪个请求；
- 为什么会增长；
- 为什么要分块；
- 什么时候可以复用；
- 请求结束后怎样处理；
- 资源不足时必须牺牲什么。

不要求计算真实模型的缓存字节数，也不要求学习显存地址、哈希函数、页表代码或驱逐算法证明。

## 开放实现观察

PagedAttention 论文说明，vLLM 使用受操作系统分页启发的方式管理动态增长的 KV Cache，以减少碎片和冗余。vLLM 当前公开的 Prefix Caching 设计还展示了缓存块的分配、引用、释放和驱逐流程。

这些是 vLLM 的公开实现证据，不代表所有 Runtime 必须采用相同 Block 大小、表结构或策略。

来源：[PagedAttention论文](https://arxiv.org/abs/2309.06180)、[vLLM Automatic Prefix Caching](https://docs.vllm.ai/en/stable/design/prefix_caching/)，核对日期：2026-07-28。
