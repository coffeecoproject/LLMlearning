# 连续内存分配为什么产生浪费与碎片

> [!summary]
> 请求最终长度事先未知，而且开始和结束时间不同；如果每个请求都依赖一整块预留的连续空间，就容易出现“预留但未使用”和“空闲但难组合”的内存浪费。

> [!phase] 运行阶段：缓存分配

## 为什么长度不可预测会造成问题

请求进入时，Runtime 知道输入长度和最大输出限制，却通常不知道模型会在第几个 Token 真正结束。

如果提前按最大可能长度预留：

```text
为A预留100份空间
→ A只生成10个Token就结束
→ 其余空间在运行期间没有被有效使用
```

这可以称为预留浪费。它安全但降低可同时服务的请求数。

## 空闲总量足够为什么仍可能放不下

请求不断进入和结束后，内存中可能形成分散空位：

```text
[A占用][空2格][B占用][空3格][C占用]
```

总共有 5 格空闲，但如果新请求要求一块连续的 5 格空间，分散空位可能无法直接满足。这种“有空闲却不在合适位置”的现象可以直观理解为碎片化。

## KV Cache为什么特别容易遇到

KV Cache 具有三个特点：

- 请求长度不同；
- Decode 期间不断增长；
- 请求在不同时间结束和释放。

它不像模型权重那样在服务启动后保持相对稳定，因此更需要动态管理。

## 分页思路怎样回应问题

如果把大空间拆成固定大小的小 Block，请求可以按需要逐步领取：

```text
A先领2块
→ 继续生成时再领1块
→ 不要求3块物理相邻
```

请求结束后，小块也更容易回到公共池供其他请求使用。分页不会让所有浪费归零，例如最后一个 Block 可能没有填满，但它通常让增长和回收更加灵活。

## 类比边界

可以把连续分配想成“必须预订一整排相邻座位”，分页想成“按需领取编号座位并用清单记录顺序”。

真实系统还要考虑张量布局、Attention读取效率和硬件实现，不能从座位类比推导具体性能数字。

## 常见误解

1. **“只要总空闲内存足够，就一定能分配连续空间。”** 空闲位置分散时未必成立。
2. **“分页完全没有浪费。”** 最后一个块和管理元数据仍可能带来开销。
3. **“碎片化是模型参数错误。”** 它是动态内存组织问题，不是模型学错了知识。
