# KV Cache 为什么会限制并发容量

> [!summary]
> 模型权重可以被多个请求共享，但每个活跃请求都会产生随已处理位置增长的缓存状态；有限显存因此限制了能同时容纳多少请求和多长序列。

> [!phase] 运行阶段：服务容量

## 权重放得下不等于服务容量足够

模型启动后，权重通常形成一份较稳定的基础占用。请求到来后，还会新增各自的 KV Cache：

```text
固定基础：模型权重
动态增长：请求A缓存 + 请求B缓存 + 请求C缓存……
```

所以即使模型本身已经放入 GPU，剩余空间仍决定了能承载多少正在生成的序列。

## 哪些变化会让缓存压力增加

在相同模型和缓存表示方式下，通常有三条直觉关系：

```text
单个请求已处理Token越多
→ 它需要记录的历史位置通常越多

同时活跃请求越多
→ 多份请求缓存相加越大

模型需要保存的层与KV表示越多
→ 每个位置对应的缓存通常越大
```

这里不需要先计算字节数，只需理解“位置数量 × 请求数量 × 每个位置的缓存内容”共同形成压力。

## 一个不使用字节公式的例子

假设教学缓存池只有 12 个 Block：

```text
请求A需要5块
请求B需要4块
请求C当前需要3块
→ 缓存池暂时已满
```

此时请求 D 即使已经排队，也不能无条件开始。Runtime 可能等待旧请求完成、回收可用空间，或者采用其他资源处理策略。

如果 A 还要继续生成，它也可能需要新的 Block。因此服务不仅要看“当前是否放得下”，还要考虑正在运行的请求是否需要继续增长。

## 上下文上限与服务容量不是一回事

模型支持较长上下文，只说明结构和服务配置允许处理相应长度，不代表许多用户都能同时用满这个长度：

```text
单请求最大长度
≠ 所有并发请求都能同时达到最大长度
```

真实并发容量还取决于模型结构、缓存精度、硬件、Runtime布局和请求长度分布。

## 它为什么与Batch有关

KV Cache 空间不足时，调度器不能无限增加活跃请求。缓存管理越有效，通常越有机会容纳更多序列共同参与 Batch；但 Batch 能否提高真实性能，还要结合计算能力和调度策略测量。

## 常见误解

1. **“模型权重占用固定，所以并发请求几乎不增加显存。”** 每个请求还会增加动态缓存状态。
2. **“模型支持128K，就能同时服务任意多个128K请求。”** 单请求长度能力不等于多请求服务容量。
3. **“KV Cache越省，回答质量一定越高。”** 缓存规模主要影响容量与效率，质量要由模型和具体近似方式判断。
