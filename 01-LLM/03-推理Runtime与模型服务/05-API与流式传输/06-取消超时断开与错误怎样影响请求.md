# 取消、超时、断开与错误怎样影响请求

> [!summary]
> 客户端不再等待，不等于模型计算已经自动停止；完整的模型服务需要把取消或失败信号传到服务器和 Runtime，并回收该请求占用的资源。

## 四个相近但不同的情况

| 情况 | 直白含义 | Runtime可能怎样处理 |
|---|---|---|
| 取消 | 用户或上层主动要求停止 | 标记请求终止并从后续调度中移出 |
| 超时 | 某一层等待超过约定时间 | 返回超时；是否取消底层任务取决于实现 |
| 断开 | 网络连接消失 | 服务可检测断开并尝试终止任务 |
| 错误 | 输入、服务、资源或模型执行失败 | 返回错误并清理请求状态 |

## 为什么“关掉页面”不一定立即停止计算

信号要经过多层：

```text
客户端停止等待
→ API服务器检测或接收取消
→ Runtime把请求标记为取消
→ 调度器不再选择它
→ 释放KV Cache等状态
```

如果其中某层没有传播取消，服务器可能暂时继续生成，只是结果无人接收。因此客户端超时与服务端停止是两个事件。

## 已经收到的部分输出怎么办

流式请求失败前，用户可能已经看到半段文本。这段文本是“部分结果”，不应冒充完整答案。上层应用需要同时记录完成状态，例如成功、取消、超时或失败。

## 与模型正确性的边界

重试可以解决偶发网络或服务错误，却不能自动修正模型的事实错误。反过来，回答内容正确也不代表请求完成状态和资源清理一定正确。
