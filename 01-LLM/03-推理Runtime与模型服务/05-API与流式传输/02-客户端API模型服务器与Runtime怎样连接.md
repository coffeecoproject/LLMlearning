# 客户端、API、模型服务器与 Runtime 怎样连接

> [!summary]
> 客户端负责提出调用，API 规定双方怎样表达请求和响应，模型服务器负责接收和管理网络请求，Runtime 再把有效请求变成实际模型计算。

> [!phase] 运行阶段：系统职责

## 四个对象分别回答什么问题

| 对象 | 它回答的问题 |
|---|---|
| 客户端 | 谁在请求模型能力？ |
| API | 请求和响应使用什么共同格式？ |
| 模型服务器 | 谁接收、校验并维持这些网络请求？ |
| Runtime | 谁加载模型并组织真实计算？ |

API 不是单独运行的一台机器。它更像一份双方遵守的接口约定，例如请求里怎样表示 `messages`、模型名称和 Streaming 选项。

## 一条完整路径

```text
1. 客户端建立请求
2. 按API格式发送messages和生成选项
3. 模型服务器完成认证、校验和路由
4. 输入处理把messages变成模型可用输入
5. Runtime调度Prefill和Decode
6. 输出处理得到文字或结构化结果
7. 模型服务器按API格式返回
8. 客户端显示、保存或继续使用结果
```

如果客户端是 Agent，模型结果还可能成为下一次工具调用或模型请求的输入；这属于 Agent 循环，不是 Runtime 自动完成的步骤。

## vLLM为什么看起来同时是Runtime和服务器

一些软件只实现其中一层，一些软件会把多层能力一起提供。vLLM 既有负责调度和模型执行的引擎，也可以启动兼容 API 的服务端。

因此可以说：

```text
vLLM实现了Runtime核心职责
并提供了部分模型服务器能力
```

但职责打包在一个项目里，不表示概念上只有一层。生产系统仍可能在 vLLM 前面增加网关、认证、限流和业务服务。

## 简单类比以及边界

可以暂时把 API 看成“点单格式”，模型服务器看成“接单与分发系统”，Runtime 看成“组织后厨实际制作”。

类比的边界是：真实 Runtime 不是人在做菜，而是在管理张量计算、设备、Batch 和 Cache；API 也不仅是文字菜单，还包含可校验的字段、事件和错误协议。

## 常见误解

1. **“API就是模型。”** API 只是访问能力的接口。
2. **“用了OpenAI兼容API，底层就是OpenAI模型。”** 兼容只说明接口格式相近。
3. **“vLLM负责所有业务安全。”** 业务用户、租户权限和工具权限通常仍由上层系统负责。
4. **“Agent和Runtime是一层。”** Agent组织任务与工具，Runtime组织模型计算。
