# 本地 Runtime 与托管模型服务能观察到什么

> [!summary]
> 本地开放实现可以检查模型文件、配置、源码、日志和运行测量；托管 API 通常只能确认官方公开接口和可观察行为。客户端看不到的内部结构，应明确标为未知，而不是从响应现象反推。

## 为什么这也是Runtime基础知识

学习模型服务时很容易看到一个现象，就直接推断内部原因：

```text
首Token很快
→ 一定使用了某种Prefix Cache？

一次返回多个文字片段
→ 模型一定并行生成了多个未来Token？

客户端有Session文件
→ 服务端一定按同样结构保存上下文？
```

这些推断都可能成立，也可能不成立。必须先知道自己能观察哪一层。

## 本地开放Runtime通常能观察什么

如果模型和 Runtime 都在自己的环境中，可以检查：

- 模型仓库中的配置、Tokenizer 和权重组织；
- Runtime 官方文档与源码；
- 启动配置、模型版本和设备放置；
- 请求日志、队列状态和错误；
- 实际显存、延迟和吞吐测量；
- 某项优化开启或关闭后的对比。

即使是本地系统，也不能只凭文件名断言运行行为；仍要结合版本、配置和实际测量。

## 托管API通常能确认什么

依据公开接口，客户端通常可以确认：

- 可用的模型标识；
- 请求允许提交哪些字段；
- 返回对象和 Streaming 事件类型；
- 使用量、状态、错误和公开限制；
- 自己测到的端到端延迟与输出行为。

但这些信息通常不足以确认：

- 模型真实参数量和未公开结构；
- 权重具体放在多少设备；
- 内部 Batch、调度和队列算法；
- KV Cache 的布局、分页和复用策略；
- 请求实际被路由到哪种硬件；
- 服务端是否使用某个特定开源 Runtime。

## Codex或其他客户端源码能证明什么

客户端源码可以证明：

```text
本地怎样保存Thread
怎样组织请求
怎样调用API
怎样处理Streaming事件
怎样把工具结果放回后续请求
```

它不能单独证明托管服务端的模型结构、调度算法和缓存布局。客户端与服务器之间隔着 API 边界。

## 一条证据等级

从强到弱可以先这样排序：

```text
公开配置、源码和可重复实验
→ 官方接口与技术文档
→ 明确测试条件下的行为测量
→ 根据现象作出的工程推断
→ 没有证据的猜测
```

这不是说官方文档永远没有错误，而是要求把“发布事实”“自己的测量”“合理推断”和“未知”分开写。

## 开放模型不能替闭源模型作证

例如，Qwen3-8B 的公开配置可以说明 Qwen3-8B；OpenAI `gpt-oss` 的开放资料可以说明相应 `gpt-oss` 版本。它们都不能证明某个未公开 GPT、Kimi 或 DeepSeek 托管版本采用相同内部结构。

相同 API 也只说明调用方式相似：

```text
请求字段相同
≠ Runtime相同
≠ 模型结构相同
≠ 调度和缓存策略相同
```

## 一个OpenAI接口例子

OpenAI Responses API 的公开参考说明了模型标识、响应状态、Token 使用量和 Streaming 事件等可观察协议。它能支持“客户端会收到哪些接口对象”的结论，但不能据此得出服务端具体使用哪种 KV Cache 布局或并行策略。

来源：[OpenAI Models API](https://platform.openai.com/docs/api-reference/models/object)、[OpenAI Responses Streaming Events](https://platform.openai.com/docs/api-reference/responses-streaming)、[vLLM Architecture Overview](https://docs.vllm.ai/en/latest/design/arch_overview/)，核对日期：2026-07-27。

## 常见误解

1. **“API兼容，所以底层Runtime相同。”** 接口兼容不要求内部实现相同。
2. **“客户端代码开源，所以整套服务都开源。”** 开源范围可能只覆盖客户端。
3. **“测到速度提高，就能确定使用了哪项优化。”** 多种因素可能产生相似现象。
4. **“开放模型的配置可以代表同公司的闭源模型。”** 只能把公开证据用于对应版本。
