# 服务启动与请求运行为什么是两个阶段

> [!summary]
> 模型服务通常先完成一次较重的启动准备，把模型变成可执行状态；之后到来的每个请求复用这份已加载模型，只创建自己的输入、缓存和生成状态。

> [!phase] 运行阶段中的两个时间尺度
> 两者都属于模型运行系统，但“启动服务”和“处理一条请求”不是同一件事。

## 先看用户看不到的阶段

用户打开聊天界面时，常会产生一种直觉：

```text
我发送一句话
→ 服务器临时打开一个模型文件
→ 模型回答
```

真实服务通常更接近：

```text
服务提前启动
→ 模型长期保持可运行
→ 请求不断到达
→ 多个请求复用同一份模型主体
```

如果每个用户问题都重新读取全部模型权重，等待和资源开销会非常大。

## 第一条时间线：服务启动

启动阶段大致要完成：

```text
选择模型版本和运行配置
→ 找到模型资产
→ 根据配置建立模型结构
→ 读取训练好的权重
→ 准备Tokenizer与生成默认值
→ 把计算和权重放到可用设备
→ 初始化Runtime需要的资源
→ 服务就绪
```

这条时间线的结果不是一段回答，而是：

> 一个能够接收请求的模型执行环境。

不同 Runtime 可能还会进行算子选择、编译、显存规划或预热。这些是实现差异，不改变“先准备服务，再处理请求”的核心关系。

## 第二条时间线：请求运行

模型已经就绪后，一条请求大致经历：

```text
请求到达
→ 检查模型名称、输入和配置
→ 组织Chat Template并Tokenize
→ 创建请求ID和临时状态
→ 等待Runtime调度
→ Prefill
→ 多轮Decode
→ 返回结果
→ 请求结束并清理状态
```

下一条请求通常不必重新学习模型，也不必重新下载全部权重。

## 冷启动与热请求

- **冷启动**：服务还没有准备好模型，需要经历加载和初始化；
- **热请求**：模型已经在运行环境中，请求直接进入接收和调度流程。

所以同样一句 Prompt，服务刚启动时和稳定运行时的等待体验可能不同。

> [!warning] 概念边界
> “热请求”不保证没有排队，也不保证 KV Cache 命中；它这里只表示不需要从零启动整个模型服务。

## 一个餐厅类比

```text
开店前：厨具、食材、人员和工作台准备好
营业中：每张订单复用厨房，但保留自己的菜品状态
```

类比对应：

```text
厨房主体 → 已加载模型和Runtime
一张订单 → 一个请求
订单进度 → 请求状态
```

类比到这里停止：模型计算不是厨师凭经验做菜，Runtime 也不会像人一样理解订单含义。

## 为什么必须分开学习

如果把两阶段混在一起，会产生这些误解：

- 认为每个用户都独占一份模型权重；
- 把模型加载耗时算进每个 Token 的 Decode 时间；
- 把服务级内存池误认为某个请求自己的状态；
- 把重启或扩容问题误认为模型推理机制变化。

## 常见误解

1. **“每次API调用都会重新加载整个模型。”** 长期服务通常复用已加载模型。
2. **“服务显示Ready，就代表每条请求立刻运行。”** Ready 只表示可以接收请求，仍可能排队。
3. **“模型加载完成后就不再分配内存。”** 请求的 KV Cache、输入输出和临时工作区仍会变化。
4. **“模型服务重启等于重新训练。”** 重启通常重新加载已有参数，不产生新的训练参数。

## 理解检查

1. 服务启动阶段的最终产物为什么不是一段回答？
2. 哪些内容可以被多个请求共享，哪些内容必须为请求单独建立？
3. 冷启动慢为什么不等于模型每轮 Decode 都同样慢？
