# 外部请求怎样成为 Runtime 内部请求

> [!summary]
> 用户发送的 JSON、Messages 或文本不能直接进入 GPU；服务端要先校验、选择模型和默认设置、应用输入协议、Tokenize，并建立 Runtime 能调度的请求对象。

## 外部请求和模型输入不是同一个对象

一个外部请求可能包含：

```text
模型名称
Messages
最大输出长度
Temperature等生成选项
是否Streaming
工具定义或输出格式要求
```

模型前向计算最终需要的却更接近：

```text
Token IDs
Attention相关输入
位置与长度信息
当前请求的缓存和生成状态
```

中间需要服务软件完成转换。

## 一条概念化转换路径

```text
1. API或本地调用收到请求
2. 校验身份、模型名称和字段
3. 检查长度、类型和服务限制
4. 合并服务默认值与请求覆盖值
5. 把Messages套入Chat Template
6. Tokenizer转换成Token IDs
7. 建立请求ID、优先级和生成状态
8. 把请求放入等待或调度队列
9. Runtime选择时机执行Prefill
```

如果输入在前几步就无效，服务可以直接报错，模型甚至还没有执行一次前向计算。

## “选择模型”不等于此时加载模型

外部请求中的模型名称可能是：

- 已加载模型实例的名称；
- 服务对外暴露的别名；
- 路由系统用来选择后端的标识。

```text
请求选择某个已准备好的服务
≠ 请求到达后一定从磁盘重新加载模型
```

是否动态加载、维护多少模型实例，是具体服务策略。

## 默认配置怎样与请求配置合并

假设服务或模型仓库提供默认 Temperature，而用户请求又明确给出一个值：

```text
基础默认值
→ 模型或服务默认值
→ 请求允许覆盖的值
→ 得到本请求实际生成配置
```

具体优先级由实现决定，不能假设所有 Runtime 完全相同。重要的是：本次生成使用的是最终合并后的配置，不是“模型权重内部永远固定的 Temperature”。

## Chat Template和Tokenizer在哪一层

从逻辑上看：

```text
Messages
→ Chat Template
→ 文本或结构化序列
→ Tokenizer
→ Token IDs
```

这些步骤位于模型前向计算之前。它们可以由模型服务器、Runtime 输入处理组件或调用方完成；部署位置可以不同，但职责不能消失。

某些本地接口也允许调用方直接传 Token IDs。这时服务端可以跳过文本 Tokenize，但必须确保这些 IDs 与模型词表匹配。

## 工具定义进入请求后发生了什么

工具名称、参数 Schema 或工具结果可能被输入协议转换为模型可见内容或约束。模型可以据此生成结构化工具调用，但实际执行工具仍然属于 Agent 或应用层。

```text
工具定义进入上下文
≠ Runtime自动完成业务工具执行
```

## 开放实现观察：vLLM的职责划分

vLLM 官方架构概览把 LLM Engine 的职责分为输入处理、调度、模型执行和输出处理；其中输入处理包括把文本转换成 Token，调度器决定每一步处理哪些请求，模型执行可以跨设备，输出处理再把 Token ID 转成人类可读内容。

这与本篇路径一致，但其他 Runtime 可以采用不同类名、进程结构和内部接口。

来源：[vLLM Architecture Overview](https://docs.vllm.ai/en/latest/design/arch_overview/)，核对日期：2026-07-27。

## 常见误解

1. **“用户Messages会原样直接进入Transformer。”** 通常还要经过模板、Tokenizer 和输入校验。
2. **“请求中的model字段就是服务器磁盘目录。”** 它也可能只是别名或路由标识。
3. **“API返回输入错误，说明模型拒绝回答。”** 错误可能发生在模型执行前。
4. **“工具Schema进入请求，工具就在模型内部运行。”** 模型通常只生成调用意图，外部系统负责执行。
