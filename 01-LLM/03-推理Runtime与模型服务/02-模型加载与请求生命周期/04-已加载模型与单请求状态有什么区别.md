# 已加载模型与单请求状态有什么区别

> [!summary]
> 已加载模型是多个请求可以共享的执行主体；输入 Token、生成配置、KV Cache、输出进度和停止状态属于各请求自身。Runtime 必须同时管理共享资源与相互隔离的请求状态。

## 先看两个箱子

```text
【服务共享箱】
模型结构、权重、Tokenizer、执行代码、公共资源池

【请求独立箱】
请求ID、输入Token、生成配置、KV内容、输出Token、完成状态
```

如果两个用户同时提问，他们可以使用同一份模型权重，但不能混用彼此的输入和 KV Cache 内容。

## 哪些通常由服务共享

| 对象 | 为什么可以共享 |
|---|---|
| 模型权重 | 普通推理时只读，同一模型请求使用相同参数 |
| 模型结构与执行实现 | 说明相同参数怎样计算 |
| Tokenizer对象 | 多个请求可以使用同一套稳定规则 |
| 已编译算子或执行计划 | 可被后续计算复用 |
| Runtime管理的内存池 | 统一提供空间，但内部块会分配给不同请求 |

“共享内存池”不表示请求可以读取其他请求的数据；Runtime 仍要维护归属和隔离。

## 哪些通常属于单个请求

```text
输入Token IDs
当前已生成Token
Temperature、Top-p、最大长度等请求配置
本请求使用的KV Cache内容或缓存块
当前处于Prefill还是Decode
停止、取消、失败或完成状态
输出缓冲与使用量记录
```

这些内容会随着请求推进而变化。

## KV Cache为什么同时像“请求状态”和“服务资源”

需要分成两层：

```text
KV Cache中的具体K、V内容
→ 由某个请求的Token产生
→ 属于该请求的运行状态

Runtime预留和管理的缓存空间
→ 属于服务级资源池
→ 可以在请求结束后重新分配
```

因此，可以说“请求拥有自己的 KV 状态”，也可以说“Runtime 统一管理 KV Cache 内存”；两句话描述的是不同层次。

## 请求结束后什么会发生

普通情况下：

```text
请求完成
→ 释放或回收请求占用的缓存块
→ 清理输出和调度状态
→ 模型权重继续保留
→ 等待下一批请求
```

如果产品要继续多轮会话，应用可以保存消息；Runtime 也可能按策略短期复用某些前缀缓存。但这不等于模型参数永久记住了用户。

## 多个请求为什么不会复制整个模型

如果每个请求都复制一份完整权重，服务容量会迅速被耗尽。共享只读权重、为请求单独保留必要动态状态，是模型服务能够承载并发的重要基础。

但并发请求越多，请求级缓存和调度状态通常也越多，所以共享权重不代表并发没有成本。

## 可选边界：同一服务不一定只有一种权重状态

某些系统可以加载多个模型、LoRA 适配器或不同版本。这会让“哪些参数共享”更复杂，但基本问题仍然是：

```text
哪些资源属于服务或模型实例
哪些状态属于当前请求
```

本篇不展开适配器调度。

## 常见误解

1. **“100个用户就要复制100份完整模型。”** 同一模型实例通常共享权重。
2. **“所有请求共享KV Cache，所以能看到彼此对话。”** 共享的是管理池，具体缓存内容必须按请求隔离。
3. **“请求结束就要卸载模型。”** 长期服务通常继续保留模型主体。
4. **“Session保存在数据库里，所以是Runtime状态。”** 产品会话状态通常属于应用层，是否进入模型取决于下一次请求组织。
