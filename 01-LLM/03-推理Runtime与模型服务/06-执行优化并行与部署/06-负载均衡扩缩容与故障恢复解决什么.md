# 负载均衡、扩缩容与故障恢复解决什么

> [!summary]
> 模型副本解决“可以有多个处理者”，负载均衡决定请求交给谁，扩缩容调整处理者数量，故障恢复则在部分处理者失效时维持服务。

## 四层职责

```text
请求入口
→ 负载均衡：选择健康且合适的副本
→ 模型副本：排队、调度并运行请求
→ 监控：观察延迟、队列、资源和错误
→ 扩缩容/恢复：增加、减少或替换副本
```

这些是模型服务工程，不是 Transformer 内部新增的能力。

## 为什么不能只看GPU利用率扩容

一个服务是否拥堵，还可能体现在排队时间、首 Token 延迟、KV Cache 容量和错误率。GPU 很忙可能表示资源得到充分利用，也可能表示请求已经过载；需要结合多项指标判断。

## 扩容为什么不是瞬间完成

新副本通常要申请设备、启动进程、下载或读取模型、加载权重并通过健康检查。大模型启动可能耗时，因此流量突然上升时，即使平台支持自动扩容，也可能先出现排队。

## 故障与重试边界

某个副本失败后，请求可以尝试交给其他副本。但生成到一半的请求可能需要重新开始，因为它的 KV Cache 通常属于原副本。重试还可能造成重复工具调用，因此 Agent 层需要考虑操作是否可安全重复。

2. 为什么生成到一半的请求不一定能无缝迁移？
