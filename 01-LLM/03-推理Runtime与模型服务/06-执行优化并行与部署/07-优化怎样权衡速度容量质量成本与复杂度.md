# 优化怎样权衡速度、容量、质量、成本与复杂度

> [!summary]
> Runtime 优化没有单一“更快”答案；每项方法都应先说明目标指标，再检查资源、质量、稳定性和运维代价。

## 五个需要同时看的方向

| 方向 | 典型问题 |
|---|---|
| 速度 | 首 Token 是否更快？后续 Token 是否更连续？ |
| 容量 | 同时能容纳多少请求和多长上下文？ |
| 质量 | 数值变化或模型替换是否影响目标任务？ |
| 成本 | 单次请求与持续占用设备的成本怎样？ |
| 复杂度 | 部署、监控、升级和排错是否更困难？ |

## 三个典型权衡

1. **量化**可能减少显存占用，但需要核对硬件支持与任务质量。
2. **跨设备拆分**能放下大模型，但增加通信和故障复杂度。
3. **增加 Batch**可能提高总吞吐，却可能让部分请求等待更久。

因此“优化前后”必须在相同模型、输入输出长度、并发和硬件条件下比较，否则结论可能只是测试条件不同。

## 用户主线到这里应掌握什么

你不需要会配置 GPU 集群，但应该能追问：

```text
它优化的是哪项指标？
代价转移到了哪里？
是否改变模型数值或回答质量？
证据是在什么条件下测得？
```

## 完整边界

Runtime 可以让模型运行得更快、更省或承载更多请求，却不会自动让模型拥有训练中没有形成的知识，也不会替 Agent 完成目标管理和结果验证。

## 理解检查

1. 为什么“吞吐量提高”不能直接等于“每个用户都更快”？
2. 为什么比较量化方案时还要测回答质量？
