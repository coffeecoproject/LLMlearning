# 批处理与调度概览

> [!summary]
> Batch 把当前可以一起计算的多个序列组织成一轮模型执行；调度器决定哪些请求在这一轮获得计算机会，而 Continuous Batching 允许这个集合随着请求到达、完成和资源变化而持续调整。

> [!phase] 运行阶段：模型服务
> 本专题研究训练完成后，Runtime 怎样让多个请求共享同一份模型和计算设备；不讨论训练数据 Batch，也不改变模型参数。

## 为什么模型服务需要批处理与调度

假设三个用户几乎同时请求同一个模型：

```text
请求A：输入很短，想生成100个Token
请求B：输入很长，只想生成10个Token
请求C：稍晚到达，想生成30个Token
```

如果 Runtime 一次只处理一个完整请求：

```text
A全部完成
→ B才开始
→ C继续等待
```

后面的请求会长时间排队，计算设备也未必在每一步都得到充分利用。

Runtime 因此要同时解决两个问题：

```text
Batch：这一轮把哪些序列放在一起计算？
Scheduling：谁先进入、谁继续、谁暂停、谁退出？
```

## Batch到底是什么

Batch（批次）不是“一次生成多个未来 Token”，而是把多个当前可执行的序列放进同一轮模型计算。

以三个正在 Decode 的请求为例：

```text
请求A当前需要预测下一个Token
请求B当前需要预测下一个Token
请求C当前需要预测下一个Token
                 ↓
Runtime把A、B、C组织成一轮Batch
                 ↓
模型分别为三个序列计算各自的下一步Logits
```

它们共享的是一次硬件执行机会，不共享语义上下文：

- A 看不到 B 的对话；
- B 的 KV Cache 不会变成 C 的历史；
- 每个请求仍有自己的输入、位置、生成设置和完成状态。

## Continuous Batching为什么出现

Continuous Batching 常译为“连续批处理”或“动态批处理”。核心不是让单个请求一次确定很多未来 Token，而是允许每轮重新组织活跃请求：

```text
第1轮：A + B
第2轮：A + B + C
B完成并退出
第3轮：A + C + D
D完成并退出
第4轮：A + C + E
```

因此 Batch 不再是一辆“必须所有乘客一起坐到终点”的车，而更接近每一站都允许乘客上下的运行集合。

这个类比的边界是：真实 Runtime 不是按固定车站运行，而是依据请求状态、Token预算、KV Cache容量和调度策略，在一次次模型执行之间更新集合。

相比成员相对固定的静态 Batch，这更适合请求持续到达、输入长度不同、输出结束时间又不可预知的在线服务。

## Prefill和Decode也要共享执行机会

同一个请求通常先经历 Prefill，再经历多轮 Decode：

| 阶段 | 当前要处理的内容 | 直白特点 |
|---|---|---|
| Prefill | 一段已有输入Token | 一次可能处理很多输入位置 |
| Decode | 当前新位置 | 标准自回归步骤通常每轮为每条活跃序列推进下一位置 |

一个很长的 Prefill 可能占用较多计算时间；Decode 请求则希望持续得到执行机会，否则用户看到的输出会停顿。

调度器需要权衡：

```text
新请求尽快完成Prefill
↔ 已经在生成的请求持续Decode
↔ 整体设备利用率
```

有些 Runtime 会采用 Chunked Prefill，把很长的 Prefill 拆成较小片段，以便与其他请求的 Decode 更灵活地共同调度。这是一种实现策略，不是 Transformer 模型结构新增了一层。

## 一轮调度的主线

概念上，调度器会反复执行：

```text
读取等待队列和运行状态
→ 检查本轮资源预算
→ 选择Prefill、Decode或二者的组合
→ 组成Batch并执行模型
→ 更新每个请求的Token与KV Cache状态
→ 移出已结束请求
→ 下一轮重新决策
```

调度器不负责判断回答在语义上是否正确。它优化的是“谁在什么时候获得计算资源”。

## 一个动态Batch小例子

假设一次执行最多容纳 3 条活跃序列：

| 轮次 | 等待或运行状态 | 本轮Batch | 结束后变化 |
|---|---|---|---|
| 1 | A、B已到达 | A Prefill、B Prefill | A、B进入Decode |
| 2 | C到达 | A Decode、B Decode、C Prefill | B生成EOS |
| 3 | C进入Decode，D到达 | A Decode、C Decode、D Prefill | 三者继续或退出 |

这是为了理解动态成员关系而简化的示意。真实系统还会受到 Token预算、输入长度、KV Cache空间、硬件能力和具体调度策略影响。

## 调度需要权衡什么

批处理通常希望提高单位时间处理的请求或 Token 数，并减少计算设备的空闲。但更大的 Batch 不一定让每个用户都更快：等待、长 Prefill、资源竞争和排队都可能增加单请求延迟。

```text
提高总吞吐量
↔ 降低首Token等待
↔ 保持输出连续
↔ 避免请求长期饥饿
↔ 控制显存与KV Cache压力
```

这些具体权衡会在后续独立笔记中展开。

## 两条不能被Batch打破的边界

多个请求可以在同一轮并行计算，但标准自回归生成中，同一个请求的下一个 Token 仍依赖它此前已经确定的 Token：

```text
A的第11个输出Token确定
→ 才形成A预测第12个Token所需的已知历史
```

Continuous Batching 改变的是“哪些请求一起执行”，不是取消单个请求内部的因果依赖。Speculative Decoding 等优化会在后续单独解释，不能反过来把普通 Batch 理解成一次直接确定整段未来文本。

另一条边界是请求隔离：同一 Batch 中的请求共享计算机会，但上下文、位置、KV Cache 和生成状态仍分别归属于各自请求。不同长度怎样整理成可执行输入，会在后续笔记单独讲解。

## 开放实现观察：vLLM

vLLM 的公开配置区分“单轮最多调度多少序列”和“单轮最多调度多少 Token”等预算。其公开优化说明还描述了 Chunked Prefill：把较长 Prefill 分块，并在资源预算允许时与 Decode 请求共同组织，以权衡首 Token 延迟、Token 间延迟和吞吐量。

这证明 vLLM 存在这些公开调度职责和配置，不代表所有 Runtime 使用完全相同的队列、默认优先级或内部数据结构。

## 常见误解

1. **“Batch等于模型一次生成多个未来Token。”** Batch主要让多个序列共享一轮计算；单序列未来位置仍有因果依赖。
2. **“一个用户请求就是一个固定Batch。”** 服务端可以在不同轮次把它与不同请求共同执行。
3. **“同一Batch中的请求共享上下文。”** 它们共享硬件执行机会，但请求状态和KV Cache相互隔离。
4. **“Batch越大，每个请求一定越快。”** 吞吐量可能提高，单请求排队和延迟也可能增加。
5. **“调度器能让模型回答更正确。”** 调度主要影响速度、容量、公平性和资源使用。
