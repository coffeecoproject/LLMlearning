# 为什么模型服务需要同时管理多个请求

> [!summary]
> 模型通常只加载一份，却要服务许多相互独立的请求；Runtime 必须保存每个请求的状态，并决定它们何时共享计算设备。

> [!phase] 运行阶段：模型服务
> 本篇讨论已经训练完成的模型如何服务用户，不讨论训练 Batch。

## 先看用户能观察到的现象

用户甲刚提交一段很长的文档，用户乙随后只问“1+1 等于几”。如果服务器必须等甲全部生成完才处理乙，乙虽然任务很短，也可能等待很久。

因此生产服务通常不会把“一个请求从头运行到尾”当作不可打断的唯一工作，而会在很多短小的模型执行轮次之间重新安排请求。

## Runtime分别保存什么

每个请求至少有自己的：

- 输入 Token 和已经生成的 Token；
- 当前处于 Prefill、Decode、完成还是取消状态；
- 采样设置、停止条件和剩余生成预算；
- [[00-KV-Cache工程管理概览|KV Cache]] 等运行状态。

请求可以在同一轮使用同一个模型，但这些内容不能相互混合。共享的是设备和模型权重，不是对话历史。

## 为什么不能只靠模型本身

Transformer 接收一批数值并完成计算，却不会自行决定：

```text
谁先运行？
谁可以加入这一轮？
显存不够时谁等待？
谁已经结束，应当释放状态？
```

这些是 Runtime 的调度职责。因此“模型能生成文本”和“模型能稳定服务许多用户”是两个层次的问题。

## 相邻概念

- [[02-模型Batch维度与服务端请求Batch有什么区别|Batch]]回答“哪些序列一起算”；
- Scheduling（调度）回答“这一轮选谁”；
- [[00-KV-Cache工程管理概览|KV Cache Manager]]回答“每个请求的历史计算状态放在哪里”。

## 常见误解

**同一个模型实例只能对应一个用户。** 不对。一个已加载模型可以轮流或成批服务许多请求。

**同时处理会让不同用户看见彼此内容。** 正确实现会隔离每个请求的上下文和缓存；同时处理只表示共享计算机会。
