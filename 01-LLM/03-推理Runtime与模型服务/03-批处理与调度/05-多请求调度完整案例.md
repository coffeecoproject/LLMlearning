# 多请求调度完整案例

> [!summary]
> 调度器持续观察请求状态和资源预算，在每轮选择可执行工作；执行结束后再更新 Token、KV Cache 和完成状态。

## 场景

- A：先到达，输入 4 个 Token，希望输出较长回答；
- B：随后到达，输入 12 个 Token，只需要短回答；
- C：再晚一点到达，输入很长。

为便于理解，假设本轮最多容纳一定数量的 Token 工作。数字只是示意，不代表某个真实 Runtime 的默认配置。

## 一轮轮发生什么

| 轮次 | 调度决定 | 模型执行后 |
|---|---|---|
| 1 | A Prefill | 建立 A 的初始 KV Cache，得到首个输出候选 |
| 2 | A Decode + B Prefill | A 推进一个位置，B 建立初始状态 |
| 3 | A Decode + B Decode + C 的一段 Prefill | B 可能达到停止条件，C 尚未完成 Prefill |
| 4 | A Decode + C 的下一段 Prefill | B 退出并释放请求状态 |
| 5 | A Decode + C Decode | C 开始产生输出 |

每轮可概括为：

```text
查看队列与活跃请求
→ 检查Token预算和KV Cache空间
→ 选择本轮工作
→ 执行模型
→ 更新各请求状态
→ 完成、取消或继续
```

## 用户最终看见什么

用户只看见自己的文本逐渐返回，并不知道每个 Token 之间设备是否还服务了其他请求。调度主要改变等待、输出节奏和系统容量，不改变用户的对话内容归属。

> [!optional] 选读：优先级、暂停与公平性
> - **优先级**：让某些请求更早获得资源；若没有限制，低优先级请求可能长期等不到执行，这叫“饥饿”。
> - **暂停与恢复**：资源紧张时暂时移出某个请求，以便更合适的请求推进；代价可能是重新加载或重算部分状态。
> - **公平性**：避免少数长请求或高优先级请求永久挤占其他请求。
> - **吞吐与延迟权衡**：等待更多请求组成大 Batch 可能提高总吞吐，却增加先到请求的排队时间。
>
> 具体算法属于 Runtime 实现层。现阶段只需知道：调度策略表达了服务希望优先优化什么。

## 不能从案例推出什么

- 不能推出真实服务每轮固定执行几条请求；
- 不能推出闭源 API 使用 vLLM 或某种具体队列；
- 不能推出 Batch 越大，每个用户一定越快；
- 不能把调度优化当作回答质量优化。

## 最终检查

1. 为什么 B 可以在 A 尚未结束时加入？
2. C 的 Prefill 为什么可能被分段？
3. B 完成后，Runtime 为什么要立即更新批次并释放状态？
4. 哪些属于模型计算，哪些属于调度器决策？
