# 服务启动、单请求与多请求服务状态怎样区分

> [!summary]
> 服务启动状态描述模型是否已经可以执行；单请求状态描述某次生成进行到哪里；多请求服务状态描述所有请求怎样排队、共享资源和获得执行机会。

> [!phase] 运行阶段：状态边界复习

## 为什么要分成三层

如果把所有状态都叫“模型状态”，很容易产生错误理解：

```text
请求结束
→ 模型也被删除？

服务重启
→ 模型重新训练？

新用户进入
→ 复制一份完整模型？
```

正确做法是先问：这份状态属于服务启动、某个请求，还是整个多请求服务？

## 第一层：服务启动状态

服务启动时通常完成：

```text
读取模型配置与Tokenizer资产
→ 建立可执行模型结构
→ 加载训练好的权重
→ 准备设备、缓存池和执行组件
→ API服务进入Ready
```

这类状态通常被许多请求共同复用：

- 已加载模型权重；
- Tokenizer与模型配置；
- Runtime执行组件；
- 可用设备和缓存资源池；
- 对外提供服务的接口。

服务启动是“把模型准备好”，不是训练出新参数。

## 第二层：单请求状态

每个请求到达后建立自己的运行状态，例如：

- 请求ID和输入Token；
- 当前处于等待、Prefill、Decode还是完成；
- 已生成Token和停止条件；
- 当前长度与位置；
- 请求自己的KV Cache归属；
- 本次Temperature、最大输出长度等生成设置。

```text
请求A结束
→ A的运行状态可以回收
→ 已加载模型通常继续服务B、C和新请求
```

## 第三层：多请求服务状态

模型服务器和 Runtime 还要维护跨请求的整体状态：

- 等待队列和运行集合；
- 本轮 Batch 成员；
- KV Cache 空闲块与占用关系；
- 并发限制和调度预算；
- 服务负载、错误和健康状态。

这些状态不属于某一个用户，而是服务为了协调所有请求而维护。

## 一张对比表

| 问题 | 服务启动状态 | 单请求状态 | 多请求服务状态 |
|---|---|---|---|
| 典型对象 | 权重、配置、Runtime组件 | 输入、输出、位置、KV Cache | 队列、Batch、缓存池、负载 |
| 是否被多个请求共享 | 通常是 | 通常否 | 用于协调多个请求 |
| 请求结束后是否消失 | 通常不消失 | 通常回收 | 随服务继续变化 |
| 服务重启后是否重建 | 是 | 活跃请求通常受影响 | 是 |

## 与Session的边界

产品 Session 可以在请求完成后继续保存对话或任务记录；单请求状态和 KV Cache 通常更短暂。

```text
Session仍保存历史
≠ 上一次请求的KV Cache一定仍存在
```

是否跨请求保留缓存，是 Runtime 和产品策略，不能只凭“对话还在”推断。

## 常见误解

1. **“用户退出对话，模型权重也会卸载。”** 请求状态与服务启动状态不同。
2. **“服务Ready说明已经产生了某个用户的KV Cache。”** 没有请求时通常还没有对应内容。
3. **“队列属于模型参数。”** 队列是模型服务的运行状态。
4. **“Session存在就说明KV Cache一直保留。”** 两者寿命和职责不同。

## 理解检查

1. 已加载权重属于哪一层状态？
2. 请求 A 的已生成 Token 和 KV Cache 属于哪一层？
3. 等待队列和本轮 Batch 为什么属于多请求服务状态？
