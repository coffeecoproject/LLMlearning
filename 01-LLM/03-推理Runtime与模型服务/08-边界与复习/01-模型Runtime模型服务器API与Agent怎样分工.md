# 模型、Runtime、模型服务器、API 与 Agent 怎样分工

> [!summary]
> 模型负责根据输入计算输出，Runtime 负责执行和调度模型，模型服务器通过 API 提供服务，而 Agent 负责围绕业务目标组织上下文、工具、状态、权限和验证。

> [!phase] 运行阶段：系统边界复习
> 本篇只建立 Agent 的边界，不提前展开 Agent 的规划、记忆和工具协议细节。

## 把整条链路放在一起

```text
用户
→ GUI或CLI
→ Agent或业务服务
→ 模型API客户端
→ API网关或模型服务器
→ 推理Runtime（例如vLLM）
→ Tokenizer、模型权重与计算设备
→ 返回模型结果
→ Agent决定下一步
→ GUI或CLI呈现
```

真实部署可以把若干层放在同一进程，也可以分散在本地和云端。判断边界时要看职责，而不是只看机器数量。

## 各层解决的问题

| 层 | 核心问题 | 典型状态 |
|---|---|---|
| 模型 | 给定Token后怎样产生Logits | 固定参数、Hidden State |
| Runtime | 怎样高效执行许多推理步骤 | 队列、Batch、KV Cache |
| 模型服务器/API | 怎样让外部程序可靠调用 | 请求、认证、事件、错误 |
| Agent | 怎样围绕目标持续采取行动 | Session、任务状态、工具结果、决策 |
| 产品与业务系统 | 谁可以使用、怎样呈现、怎样落入业务 | 用户、租户、权限、数据库记录 |

## 托管模型API替代了什么

如果使用 Hugging Face Inference Endpoint 或其他托管模型 API，平台通常可以接管：

```text
模型服务器的基础能力
Runtime部署与运行
模型和Tokenizer加载
GPU等计算资源
KV Cache与Batch的内部管理
基础健康检查和部分扩缩容
```

因此，本地应用不必自己执行 Tokenizer，也不必直接管理 GPU 显存。

## 托管模型API没有替代什么

它通常不会替你决定：

- 当前用户真正要完成什么目标；
- 哪些历史信息应该进入本次上下文；
- 何时查询业务数据库或知识库；
- 模型是否有权执行某个工具；
- 工具返回的结果是否可信；
- 任务失败后应该重试、换路还是停止；
- 哪些信息可以记录、展示或跨用户共享；
- 最终结果是否达到业务验收条件。

这些主要属于 Agent、产品和业务治理层。

## “只调用API”还要开发多少

### 最小演示

```text
输入框
→ 调用模型API
→ 显示回答
```

通常只需 API 客户端、凭证保护、简单输入输出和错误处理。

### 普通业务应用

还需要用户、数据库、Session、上下文组织、日志、成本控制、超时重试和数据权限。

### 可执行任务的Agent

还需要：

```text
目标与约束
→ 任务状态
→ 上下文选择
→ 模型判断
→ 工具权限与执行
→ 结果验证
→ 更新状态或继续循环
```

模型 API 提供一次推理能力；Agent 把多次推理、外部工具和真实状态组织成闭环。

## 一个具体例子

用户提出：“检查项目中的测试失败并修复。”

模型服务能够根据收到的上下文生成分析或工具调用意图，但它自己不知道本地项目当前有哪些文件，也不会天然拥有执行测试的权限。

```text
Agent读取允许访问的项目状态
→ 选择相关内容进入上下文
→ 调用托管模型API
→ 获得检查或修改建议
→ Agent按权限执行工具
→ 运行测试并取得真实结果
→ 再把必要结果交给模型
→ Agent验证是否完成
```

其中 Runtime 负责每次模型调用的计算；任务闭环由 Agent 和工具系统完成。

## 常见误解

1. **“有了vLLM就有了Agent。”** vLLM 管理模型推理，不管理完整业务目标和工具闭环。
2. **“调用托管API后不用开发后端。”** 简单演示可以直接调用，但正式产品通常仍需要安全的业务后端。
3. **“模型返回答案就说明任务完成。”** 真实任务需要外部状态和验证证据。
4. **“所有上下文管理都由模型Runtime完成。”** Runtime处理收到的模型输入；哪些业务信息应该被送入，通常由上层系统决定。

## 理解检查

1. Runtime 管理的 KV Cache 为什么不等于 Agent 的 Session？
2. 托管模型 API 可以替你管理 GPU，为什么不能替你决定业务工具权限？
3. 从聊天演示升级到可执行 Agent，至少新增了哪些职责？
