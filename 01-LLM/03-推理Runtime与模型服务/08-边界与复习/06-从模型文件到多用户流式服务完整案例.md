# 从模型文件到多用户流式服务完整案例

> [!summary]
> 一个模型服务先把静态模型资产装配成长期运行的执行系统，再把不断到达的独立请求转换为Token、调度Prefill与Decode、管理KV Cache，并通过API持续返回结果。

> [!phase] 运行阶段：端到端概念案例
> 案例使用开放模型和 Runtime 的公开职责帮助理解，不代表所有托管服务内部采用相同进程结构。

## 场景

假设开发者使用：

```text
模型资产：Qwen3-8B
推理Runtime：vLLM
接口：兼容Chat API
客户端：一个网页和一个Agent
```

这里跟踪对象和职责，不学习启动命令、网络字段或硬件配置。

## 阶段一：服务启动

```text
读取模型配置
→ 建立对应模型结构
→ 加载权重和Tokenizer资产
→ 把模型放到可用计算设备
→ 准备调度器和KV Cache资源池
→ API Server进入Ready
```

此时：

- 模型已经能够执行；
- 权重可以被后续请求共享；
- 还没有用户 A、B 的输入 Token；
- 也没有 A、B 内容产生的 KV Cache。

## 阶段二：请求A到达

网页用户发送一条 Messages 请求：

```text
API接收并校验
→ Chat Template整理角色格式
→ Tokenizer转换成Token IDs
→ 建立请求A的状态
→ 进入等待队列
```

调度器为 A 安排 Prefill；KV Cache Manager 为 A 分配缓存空间。Prefill 完成后，A 得到首个新 Token 的 Logits，并开始多轮 Decode。

## 阶段三：请求B和C陆续到达

请求 A 还在生成时，Agent 的请求 B 和另一网页请求 C 到达：

```text
等待和运行集合：A、B、C
→ 调度器按资源预算选择本轮参与者
→ A可能执行Decode
→ B、C可能执行Prefill或等待
```

Continuous Batching 允许后续轮次动态加入和移出请求。它没有让 A、B、C 共享对话内容；三者仍有独立 Token、位置、KV Cache 和停止状态。

## 阶段四：Runtime反复执行

每轮概念主线是：

```text
调度器选择可运行请求
→ Cache Manager确认和分配缓存空间
→ Model Runner执行模型前向计算
→ 生成控制器选择当前Token
→ 更新各请求Token、KV Cache和结束状态
→ 下一轮重新调度
```

某个请求完成后退出，空出的执行机会和缓存空间可以服务后续请求。

## 阶段五：结果怎样流向用户

模型内部产生的是 Token ID 和相关状态。输出处理与模型服务器继续完成：

```text
Token ID
→ Tokenizer Decode得到可显示内容
→ 封装为文本增量或状态事件
→ 通过Streaming API发送
→ 客户端追加显示
```

一个网络事件可以包含多个字符或多个 Token 的可显示片段；客户端刷新次数不能反推模型步数。

## 阶段六：请求结束后的状态

假设 B 先完成：

```text
B遇到EOS
→ 返回完成事件
→ B的活动请求状态结束
→ B的缓存解除占用或按策略保留可复用部分
```

模型权重和服务通常继续存在，A、C 也可以继续生成。B 的 Agent 还可能根据模型结果执行工具并发起下一次请求，那是 Agent 循环的新一步。

## 一张职责表

| 环节 | 主要负责者 |
|---|---|
| 选择业务上下文与工具 | 应用或Agent |
| 接收、认证和校验网络请求 | 模型服务器/API层 |
| Tokenize与请求输入准备 | 服务输入处理组件 |
| Batch、调度和KV Cache | 推理Runtime |
| Hidden State与Logits计算 | 已加载模型 |
| Streaming事件与客户端显示 | 模型服务器和客户端 |
| 工具执行与结果验证 | Agent或业务系统 |

## 托管API会隐藏哪一段

如果改为 Hugging Face Endpoint 或其他托管模型 API：

```text
客户端或Agent
→ 托管API
→ 被隐藏的模型服务器、Runtime、模型和硬件
```

中间职责仍然存在，只是调用方通常无法直接观察内部调度和缓存布局。

## 理解检查

1. 服务 Ready 时已经有什么，还没有什么？
2. A、B、C进入同一Batch时共享什么、隔离什么？
3. B完成后为什么不需要卸载整个模型？
4. Agent收到模型结果后继续执行工具，为什么不属于Runtime职责？
