# API 行为、开源实现与闭源服务的证据边界

> [!summary]
> API可以证明客户端怎样请求和收到什么；开源实现还能证明其公开代码与配置怎样组织；闭源服务未公开的模型结构、调度、缓存和部署方式仍应标记为未知。

> [!phase] 运行阶段：证据边界复习

## 为什么“看到结果”不等于“看到内部”

客户端可以观察：

```text
请求字段
返回状态
Streaming事件
使用量信息
端到端时间
```

但同一种外部行为可能由不同内部实现产生。例如输出变快可能来自排队减少、Prefix Cache、硬件变化或其他优化，不能只凭现象锁定一个原因。

## 第一层：API可以证明什么

公开 API 文档和真实响应可以支持：

- 哪些输入字段被接受；
- 返回对象与错误形式；
- 是否提供流式接口；
- 公开的模型标识和限制；
- 客户端实际测得的端到端表现。

API 兼容主要表示调用格式能够对接：

```text
接口格式相似
≠ 模型相同
≠ Runtime相同
≠ KV Cache策略相同
```

## 第二层：开源实现多提供了什么

对于明确版本的开源 Runtime，可以进一步检查：

- 调度器和 KV Cache Manager 的代码；
- 公开配置与默认策略；
- 支持的模型架构；
- 本地日志、显存和性能测量；
- 开启或关闭某项优化后的实验结果。

例如 vLLM 文档和源码可以支持“vLLM 公开实现了哪些职责”，但不能替另一个闭源服务作证。

## 第三层：托管闭源服务通常看不到什么

如果服务提供方没有公开，客户端通常不能确认：

- 模型真实结构和参数细节；
- 请求被路由到什么硬件；
- 内部 Batch 和调度策略；
- KV Cache 的物理布局与复用范围；
- 是否使用 vLLM、SGLang 或自研 Runtime；
- 服务内部是否拆成哪些进程和机器。

“合理推测”可以提出，但必须标成推测，不能写成已证实事实。

## 客户端源码的证明范围

Codex CLI 或其他客户端源码可以证明：

```text
本地怎样保存Session或Thread
怎样构建请求
怎样处理工具结果和Streaming事件
```

它不能单独证明远端模型服务器的缓存布局、调度算法或模型结构。API 边界把两部分隔开。

## 一条实用证据等级

```text
对应版本的配置、源码和可重复实验
→ 官方技术文档与接口说明
→ 写明条件的行为测量
→ 有依据的工程推断
→ 没有证据的猜测
```

写学习笔记时，应分别标注“公开事实、自己的测量、推断、未知”。

## 常见误解

1. **“OpenAI兼容API说明内部和OpenAI一样。”** 它主要说明接口能够兼容调用。
2. **“客户端开源说明整套云服务开源。”** 开源范围可能只覆盖客户端。
3. **“Qwen的配置可以证明某个闭源GPT怎样实现。”** 公开证据只能用于对应模型和版本。
4. **“测到一次加速就证明命中了Prefix Cache。”** 还需要更直接的配置、日志或对照实验。

## 理解检查

1. API响应可以证明哪些外部事实，不能证明哪些内部事实？
2. 为什么一个开源Runtime不能替另一个闭源服务作证？
3. 客户端源码和服务器源码的证明范围有什么不同？
