# 单请求自回归顺序为什么不被多请求并发改变

> [!summary]
> Runtime 可以把多个请求当前可执行的步骤放进同一轮 Batch，但每个请求的后一个 Token 仍依赖它自己已经确定的前一个 Token；跨请求并行没有取消单请求内部依赖。

> [!phase] 运行阶段：生成顺序与服务并发

## 两个方向同时存在

模型服务既有单请求的时间顺序，也有多个请求之间的并发：

```text
单请求内部：A1 → A2 → A3 → A4
多请求之间：A当前步骤、B当前步骤、C当前步骤可以共同执行
```

不要把这两个方向画成同一条线。

## 为什么A的未来Token仍有顺序

请求 A 预测第 12 个输出 Token 时，输入历史必须包含已经选定的第 11 个 Token：

```text
A11尚未确定
→ A12缺少完整条件
→ 不能按普通自回归过程直接确定A12
```

这来自 Decoder-only Causal LM 的条件生成机制，不是 Runtime 排队规则。

## Batch并行的是什么

假设 A、B、C 都已准备好各自的下一步：

```text
A预测自己的下一Token
B预测自己的下一Token
C预测自己的下一Token
          ↓
Runtime组织成一轮Batch
```

模型同时处理三个序列当前步骤，分别产生各自 Logits。B 完成后可以退出，D 又可以在后续轮次加入，这就是 Continuous Batching 的动态成员关系。

## 请求之间为什么不会互相续写

Runtime 为每个请求保留独立的：

- 输入和已生成 Token；
- 位置与长度信息；
- KV Cache 映射；
- 生成配置和停止状态。

共同进入一次硬件计算，不代表把 A、B、C 拼成同一段上下文。

## Streaming一次出现多字说明什么

客户端一次收到多个字符或一段文本，可能因为 Token Decode、事件缓冲或网络分块。它不能证明模型同时确定了多个依赖未来的 Token。

```text
界面显示粒度
≠ 模型逻辑生成步数
```

## 特殊优化为什么不推翻主线

Speculative Decoding 等方法可以提出多个候选 Token，再由目标模型验证并一次接受其中若干个。但候选和验证仍必须满足目标模型的条件概率与因果约束。

因此不能把特殊优化反推成“普通自回归模型没有顺序依赖”。

## 常见误解

1. **“Batch里有8个序列，所以一个用户一次得到8个未来Token。”** 通常是8条序列各推进当前步骤。
2. **“GPU并行意味着因果关系消失。”** 硬件并行不能取消输入依赖。
3. **“Streaming一次返回一段话，说明模型一轮算完整段。”** 网络事件与模型Token步骤不是一一对应。
4. **“请求同批执行就共享上下文。”** 运行状态仍按请求隔离。
