# 并发、队列时间与服务目标怎样连接

> [!summary]
> 并发请求增加后，超过即时执行容量的请求会排队；服务目标应说明大多数请求和慢尾请求分别允许等待多久，而不只是报告平均值。

## 并发不等于Batch大小

- **并发数**：同一时间仍在等待或运行的请求数量；
- **Batch大小**：某一轮实际一起参与模型执行的序列或 Token 工作量。

100 个请求同时存在，不代表模型一轮就把 100 个请求全部放入 Batch。调度器可能只选择其中一部分，其余继续排队。

## 队列时间怎样进入TTFT

```text
提交请求
→ 队列等待
→ 数据准备与Prefill
→ 首Token
```

所以模型计算本身没有变慢，TTFT 也可能因为排队而上升。这是“低并发测试很快，上线后却慢”的常见原因。

## 为什么平均值不够

九个请求 0.5 秒收到首 Token，一个请求等了 8 秒，平均值会淡化那个严重慢请求。生产报告常同时看中位数、P95 或 P99 等分位数：P99 关注最慢约 1% 请求所在的尾部体验。

## 服务目标是什么

服务目标可以写成：“在约定负载下，至少 99% 的请求 TTFT 不超过某阈值，成功率达到某水平。”它把指标、比例和测试负载连接起来。只写“平均很快”无法说明高峰期是否可靠。
