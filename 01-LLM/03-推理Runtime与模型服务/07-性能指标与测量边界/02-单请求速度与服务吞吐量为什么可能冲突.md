# 单请求速度与服务吞吐量为什么可能冲突

> [!summary]
> 单请求速度关心一个用户等多久；服务吞吐量关心单位时间总共完成多少工作。等待更多请求组成更高效的 Batch，可能提高后者却伤害前者。

## 两个观察视角

- **Latency（延迟）**：某一个请求从提交到某个结果要多久；
- **Throughput（吞吐量）**：整个服务在单位时间处理多少请求或 Token。

## 一个简化例子

策略 A 收到请求就立刻运行，每秒完成 4 个请求；策略 B 等几毫秒组成 Batch，每秒能完成 7 个请求。B 的总产出更高，但最先到达的请求多等了一段组批时间。

因此：

```text
设备更忙、总Token更多
不必然推出
每个用户更早看到首Token
```

## 单请求Tokens/s也不是系统吞吐量

“某个请求后续每秒输出 50 Token”和“服务器所有请求合计每秒输出 500 Token”回答不同问题。报告写 `tokens/s` 时必须说明是单请求、所有并发请求合计，还是输入与输出 Token 的总和。

## 怎样选目标

交互式聊天通常重视 TTFT 和输出平稳；离线批量摘要可能更重视总吞吐量；实时 Agent 还会关心工具调用前的关键步骤能否及时返回。目标不同，合适的调度和 Batch 策略也不同。
