# 为什么 Benchmark 必须写明测试条件

> [!summary]
> 性能数字只有和模型、硬件、Runtime版本、输入输出长度、并发与测量口径一起出现才可解释；缺少条件的排名很容易误导。

## 至少需要哪些条件

| 条件 | 为什么重要 |
|---|---|
| 模型准确版本与精度 | 模型大小和数值格式改变资源与计算量 |
| Runtime及版本 | 调度、Kernel和缓存实现会变化 |
| 硬件数量与型号 | 计算、显存和互联能力不同 |
| 输入长度分布 | 长 Prefill 会改变 TTFT 和计算负载 |
| 输出长度分布 | 长 Decode 会改变总时间和吞吐 |
| 并发或请求到达速率 | 决定是否排队、怎样组 Batch |
| 指标定义和统计区间 | 同名指标可能有不同起点或平均方法 |

## 一个不能直接比较的例子

```text
报告A：短输入、短输出、单请求，100 tokens/s
报告B：长输入、长输出、64并发，总计800 tokens/s
```

不能因为 800 大于 100 就断言 B 的单用户体验更快。两者统计对象和负载完全不同。

> [!optional] 选读：资源构成
> 性能报告若涉及容量，还应说明权重、激活、KV Cache 和 Runtime 工作区各占用什么资源。权重主要随模型资产变化，KV Cache 则会随并发、上下文和注意力结构变化。具体容量公式不属于本阶段必读。

## 冷启动与稳态也要区分

首次请求可能包含模型加载、编译或缓存预热；稳定运行后的请求则处于稳态。若把两者混在一个数字里，无法判断用户日常体验和服务启动成本。

## 阅读报告的最小提问

```text
测了什么模型？
在哪些设备上？
输入输出多长？
多少并发？
统计的是单请求还是全服务？
是否包含排队、网络和冷启动？
```

## 理解检查

1. 为什么不同输出长度下的端到端延迟不能直接排名？
2. 冷启动与稳态混合会掩盖什么？
