# 为什么运行时仍然保持因果可见性

> [!summary]
> 标准 Decoder-only LLM 在运行时仍保持“每个位置只能读取自己和左侧位置”的因果规则，因为这是模型受训和工作的计算结构；Prompt Prefill 时最后一个有效位置已经能利用完整 Prompt，逐 Token Decode 时未来 Token 则尚未存在。

## 先把“向后看”说准确

中文里的“向后看”可能同时表示回头看左边，或者看右边尚未出现的内容。这里统一使用：

```text
向左看、回看
→ 读取自己和更早位置
→ Decoder-only 允许

向右看、看未来
→ 读取当前位置右侧的 Token
→ Causal Attention 禁止
```

真正受限制的是“向右读取未来位置”。

## 完整 Prompt 已经存在，为什么还要限制

假设运行时 Prompt 已经完整给出：

```text
小明 | 把 | 苹果 | 给了 | 小红
  0      1      2      3      4
```

标准 Decoder-only 模型仍按因果方向计算：

```text
位置 0“小明” → 读取 0
位置 1“把”   → 读取 0、1
位置 2“苹果” → 读取 0、1、2
位置 3“给了” → 读取 0、1、2、3
位置 4“小红” → 读取 0、1、2、3、4
```

程序可以并行计算这些位置，不等于它们彼此拥有双向读取权限。并行描述的是“计算怎样同时执行”，Causal Mask 描述的是“信息允许从哪里流向哪里”。

## Prompt Prefill：最后位置已经能够读取完整 Prompt

运行时第一次处理整段 Prompt，通常称为 **Prefill**。虽然前面位置不能读取后面位置，但最后一个有效 Prompt 位置可以读取此前全部内容：

```text
最后位置
← 自己
← 前面所有 Prompt Token
```

Decoder-only LLM 开始生成时，通常使用最后一个有效位置对应的最终表示产生下一 Token 的 Logits。因此，并不要求第一个 Token 反过来读取最后一个 Token：用于继续生成的位置已经具备整个已有前缀的可见范围。

> [!note] 边界
> “最后位置看到了完整 Prompt”表示它可以从全部已有位置汇总信息，不保证模型一定正确理解、记住或使用了其中每个细节。

## 逐 Token Decode：未来 Token 还不存在

Prefill 之后，模型进入逐 Token 生成。假设当前已有：

```text
Prompt + 苹果 | 是 | 一种
```

下一步可能生成“水果”，也可能生成其他候选。在选择完成前，未来 Token 尚不存在：

```text
已有 Token → 可以参与当前计算
未来 Token → 尚未产生，没有对应的 K/V 可供读取
```

所以单 Token Decode 时，某些优化实现不必真的构造完整的三角 Mask；张量范围、缓存范围或因果 Attention 算子已经使 Query 只能接触已有位置。没有显式 Mask 张量，不等于运行变成双向 Attention。

## 为什么不能在运行时临时改成双向 Attention

训练标准 Decoder-only 模型时，位置 `i` 始终只在因果可见范围内形成表示。模型参数由这种计算条件共同塑造。

如果运行时突然允许所有 Prompt 位置双向读取：

```text
原来的位置 0 表示：只依赖位置 0
改动后的位置 0 表示：依赖整段 Prompt

→ Hidden States 改变
→ 后续 Q、K、V 改变
→ Attention 与 FFN 输入改变
→ 整个逐层数据流改变
```

这不是给同一个模型“多看一点”那么简单，而是修改了模型的计算图和内部数据分布。除非模型本来就按这种可见性结构设计和训练，否则不能假设已有参数仍会按预期工作。

## 一组极小的层间示意

Prompt 为 `A | B | C`。第一层后可以抽象为：

```text
h_A¹ = 根据 A 形成
h_B¹ = 根据 A、B 形成
h_C¹ = 根据 A、B、C 形成
```

下一层继续保持相同方向：

```text
h_C² 可以读取 h_A¹、h_B¹、h_C¹
```

因此最后位置可以逐层汇总完整前缀。前面位置不需要先读取未来，再把信息交还给最后位置。

这些式子只表示依赖范围，不是实际模型公式。

## 与 KV Cache 的关系

因果方向还带来一个重要运行性质：更晚 Token 不会反过来改变更早位置已经形成的 K/V。

```text
过去位置只依赖当时已有前缀
→ 新 Token 出现后，过去位置的 K/V 仍然有效
→ 运行时可以缓存旧 K/V
→ 每一步主要计算新增位置
```

如果过去位置允许读取后来新增的 Token，那么每生成一步，旧位置的内部表示和 K/V 都可能需要重算，缓存就无法按同样方式复用。

> [!note] Runtime 边界
> 这里仅说明“因果依赖为什么允许复用旧 K/V”。KV Cache 的张量形状、Prefill/Decode 性能、显存占用、Paged Attention 和请求调度，留到 LLM 普通运行模块。

## 这是不是所有 Transformer 的规则

不是。可见性由模型架构和训练方式决定：

| 架构 | 常见可见范围 |
|---|---|
| Encoder-only | 输入位置通常可以双向读取 |
| Decoder-only | 每个位置通常只读取自己和左侧前缀 |
| Encoder–Decoder | Encoder 通常双向处理输入；Decoder 对输出保持因果限制 |
| Prefix LM 等变体 | 可以为输入前缀和生成部分设计不同可见范围 |

这些都是可以存在的设计，但需要按相应结构训练。不能把已经训练好的标准 Decoder-only 模型在普通运行时随意切换成另一种 Mask，就假设它仍是同一个模型。

`Decoder-only` 也不是“不走 Tokenizer encode”。这里的 Decoder 是 Transformer 架构类型，与 Tokenizer 的 `encode()`、`decode()` 属于不同系统层次。

## 因果链总结

```text
模型按因果可见性训练
→ 运行保持同一计算结构
→ Prefill 最后位置已经可以读取完整 Prompt
→ Decode 时未来 Token 尚不存在
→ 旧位置不受新 Token 反向影响
→ 旧 K/V 可以复用
```

其中前三步解释“为什么运行仍然因果”；KV Cache 是这种依赖方向带来的重要工程收益，不是唯一根本原因。

## 常见误解

- **“完整 Prompt 一次输入，所以 Prompt 内部一定双向 Attention。”** 一次并行计算不等于所有位置互相可见。
- **“前面 Token 看不到后面，模型就无法理解完整 Prompt。”** 用于继续生成的最后有效位置可以读取整个已有前缀。
- **“Decode 没创建三角 Mask，所以不是 Causal Attention。”** 未来位置尚不存在时，因果限制可能由数据范围自然满足。
- **“运行时改成双向只会让模型获得更多信息。”** 它会改变每层内部表示，属于计算结构变化。
- **“因果结构只是为了 KV Cache。”** 根本上它定义自回归信息条件，缓存复用是重要结果之一。
