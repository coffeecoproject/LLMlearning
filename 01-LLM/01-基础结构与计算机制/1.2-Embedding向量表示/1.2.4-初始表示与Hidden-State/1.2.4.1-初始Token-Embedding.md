# 1.2.4.1 初始 Token Embedding

> [!summary]
> 初始 Token Embedding 是模型根据 Token ID 从 Embedding Matrix 中取出的起始向量；它让 Token 可以进入后续计算，但还没有结合当前句子的完整上下文。

## 从上一环节接过来的是什么

Tokenizer 产生一串 Token ID。假设是教学示意：

```text
“我喜欢苹果”
→ [我] [喜欢] [苹果]
→ [17, 86, 205]
```

这些 ID 只是词表索引。模型使用 [[1.2.2.3-Embedding-Lookup|Embedding Lookup]]，从 Embedding Matrix 中分别取出三行：

```text
17  → “我”的初始向量
86  → “喜欢”的初始向量
205 → “苹果”的初始向量
```

如果 `hidden_size = 4`，教学示意结果可能是：

```text
“我”   → [ 0.2,  0.5, -0.1, 0.7]
“喜欢” → [-0.3,  0.6,  0.8, 0.1]
“苹果” → [ 0.4, -0.2,  0.9, 0.3]
```

> [!warning]
> 上面的 Token、ID 和向量都是为了展示形状而虚构的，不属于任何真实模型。

## 为什么称为“初始”表示

此时模型知道的是：

```text
当前位置对应哪个 Token
→ 取出这个 Token 的起始参数向量
```

但“苹果”可能表示水果，也可能出现在公司、品牌或代码变量的上下文中。单独查表时，它还没有充分利用周围 Token 判断本次具体含义。

因此初始 Token Embedding 更像后续计算的统一起点，而不是模型对当前句子的最终理解。

## 一条序列怎样形成初始表示

把每个位置的向量按 Token 顺序排列：

```text
形状：[sequence_length, hidden_size]
```

上例得到：

```text
[3, 4]
= 3 个 Token 位置 × 每个位置 4 个数
```

如果加入 Batch 维度，常写成：

```text
[batch_size, sequence_length, hidden_size]
```

这里仍然只是在描述数据形状；不同长度怎样整理、训练 Batch 怎样更新参数、多用户请求怎样调度，都不属于本篇。

## 位置机制带来的命名边界

“模型第一层接收到的初始表示”不一定永远等于纯 Token Embedding：

- 使用 Absolute Position Embedding 的模型，可能将 Token Embedding 与位置向量相加；
- 使用 RoPE 的模型，位置信息主要在 Attention 的 Q、K 上注入；
- 具体结构由模型架构决定。

因此要区分：

```text
Token Embedding
→ 由 Token ID 查表得到的向量

第一层的输入表示
→ Token Embedding 加上该架构要求的其他处理结果
```

位置机制将在 [[1.3-Position位置机制概览|1.3 Position 位置机制]] 中展开。

## 常见误解

- **“初始 Embedding 已经是 Token 在当前句子里的最终含义。”** 它还没有完成多层上下文计算。
- **“初始表示一定等于 Token Embedding 加 Position Embedding。”** RoPE、ALiBi 等方案并不都采用这种方式。
- **“向量的第 1 行永远对应某个固定 Token。”** 序列张量的行表示当前位置；换一段输入，对应 Token 就会变化。
- **“Token ID 本身经过小数转换就成了 Embedding。”** Lookup 是用 ID 选择参数行，不是把整数编码成一串小数。
