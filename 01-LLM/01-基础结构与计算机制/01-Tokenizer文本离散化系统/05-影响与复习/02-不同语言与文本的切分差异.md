# 不同语言与文本的切分差异

> [!summary]
> 一类文本能否被紧凑表示，取决于具体 Tokenizer 的训练语料、词表、表示路线和切分规则，而不只取决于它属于哪种语言。

## 为什么会有差异

Tokenizer 的有限词表不可能直接保存所有可能字符串，它会优先保留训练语料中有价值的常见片段。

```text
某片段在训练语料中常见
→ 更可能成为可复用 Token
→ 新文本中遇到它时可能切得较紧凑

某片段少见
→ 更可能拆为小单位或字节
→ 可能占用更多 Token
```

这是总体倾向，不是对每个算法和片段的绝对保证。

## 中文与英文不能只比字符数

英文常用空格标记单词边界，但一个长单词仍可能被拆成多个子词。中文没有天然空格分隔，每个 Token 可能是单字、常见词或多字片段。

例如下面只是一种可能性：

```text
unhappiness → [un] [happi] [ness]
人工智能   → [人工] [智能]
```

真实切分必须由具体 Tokenizer 验证。因此：

> “中文一定比英文费 Token”不准确；应该说某段中文和某段英文在某个具体 Tokenizer 下各占多少 Token。

## 代码为什么有独特表现

代码中包含：

- 标识符：`getUserProfile`
- 下划线：`user_id`
- 运算符：`==`、`=>`
- 缩进和换行；
- 路径、版本号和随机字符串。

如果训练语料中代码充足，词表可能保存常见关键字、空格模式或运算符；否则某些标识符可能被拆得更细。代码 Tokenizer 效率还会影响模型能在固定序列长度内看到多少代码。

## 数字为什么值得单独观察

`2026` 可能被表示成：

```text
[2026]
[20] [26]
[2] [0] [2] [6]
```

不同切分会改变数字在序列中的结构。能够编码所有数字，不等于模型天然掌握精确算术；算术能力还需要模型从训练中学习并在推理时正确使用。

## Emoji 和罕见字符

Emoji 的人眼外观不等于底层只有一个简单字符。有些 Emoji 由多个 Unicode 码点组合，字节级 Tokenizer 还可能在 UTF-8 字节层面覆盖它们。因此一个看起来像单个图形的 Emoji 可能占多个 Token。

这不是 Tokenizer “看错了”，而是人类视觉单位、Unicode 序列、字节与 Token 本来就是不同层次。

## 中英文混合与空格

```text
使用 GPT model 处理 user_id
```

这里同时出现中文、英文、下划线和空格。Tokenizer 会按同一套既定规则处理整段文本，而不是先判断语言，再为每一段训练一套新规则。不同片段仍可能因为词表覆盖程度不同而表现不同。

## 常见误解

- **“一种语言天然对应一种固定 Token 效率。”** 效率属于“文本 + 具体 Tokenizer”的组合。
- **“一个 Emoji 看起来是一个图形，所以就是一个 Token。”** 视觉单位与 Token 单位不同。
- **“数字被切成一个 Token，模型就更会算。”** 表示紧凑与推理正确不是同一件事。
- **“遇到中英文混合会自动更换 Tokenizer。”** 具体 Tokenizer 通常用一套既定系统处理整个输入。

## 理解检查

1. 为什么比较语言效率时必须明确具体 Tokenizer？
2. 一个 Emoji 为什么可能占多个 Token？
3. 代码训练语料的覆盖程度为什么可能影响代码的 Token 数量？
