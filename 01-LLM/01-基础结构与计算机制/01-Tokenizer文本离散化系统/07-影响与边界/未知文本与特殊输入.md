# 未知文本与特殊输入

> [!summary]
> 有限词表面对无限新文本时，必须选择“报告未知”或“继续拆成更小单位”；子词、字符和字节路线的核心价值之一，就是减少无法编码的情况。

## 为什么一定会遇到新文本

词表是有限的，现实字符串近乎无限。下面这些内容都可能从未作为完整词表项出现：

```text
新造词
人名与地名
拼写错误
超长代码标识符
随机编号
新 Emoji
罕见文字
```

因此 Tokenizer 不能只会查找完整单词，还需要一种失败后的处理方式。

## Word-level 的未知词问题

如果系统只接受词表中的完整单词：

```text
词表没有 “OpenAI2026X”
→ [UNK]
```

`[UNK]` 是 Unknown Token，表示无法进一步区分的未知输入。许多不同字符串都变成同一个 ID 时，原始差异便丢失了。

## Subword 怎样缓解

子词方法尝试把完整未知词拆成已有片段：

```text
OpenAI2026X
→ [Open] [AI] [20] [26] [X]
```

这是示意切分。真实结果取决于具体词表。

即使完整字符串从未出现，只要组成片段存在，系统仍能编码并保留较多形式信息。但如果最小单位仍无法覆盖某个字符，仍可能需要 Unknown Token 或其他回退方案。

## Character-level 与 Byte-level

字符级词表可以覆盖预先包含的字符集合，但 Unicode 字符范围很大，新的组合也不断出现。

字节级路线把文本先表示为有限的字节值，再用字节或字节组合构成 Token。因为任意数字文本最终都能编码为字节，它可以大幅降低“完全无法表示”的风险。

代价是：罕见字符或 Emoji 可能被拆成多个细小片段，使序列更长。覆盖能力与表示紧凑程度并不是同一个指标。

## “特殊输入”与“特殊 Token”不是一回事

- **特殊输入**：Emoji、罕见字、控制字符、异常拼写等现实文本。
- **Special Token**：由系统人为保留的协议标记，例如 BOS、EOS、PAD、消息边界。

普通文本中出现字符串 `<eos>`，也不一定自动等于真正的 EOS Token。是否按特殊 Token 处理，取决于 Tokenizer API、允许列表和配置。

## 能编码之后还剩什么问题

假设字节回退成功保留了某个罕见字符：

```text
罕见字符
→ 若干合法 Token ID
```

这只证明输入没有丢失。模型能否：

- 正确恢复字符；
- 知道它的读音；
- 理解其含义；
- 在上下文中正确使用；

仍取决于 LLM 的训练经验和能力。

## 常见误解

- **“未知词就是完全不能输入。”** 子词或字节回退通常仍可编码。
- **“没有 `[UNK]` 就表示模型什么都懂。”** 可能只是 Tokenizer 能无损覆盖字节。
- **“Emoji 一定是特殊 Token。”** 大多数 Emoji 只是普通输入文本；Special Token 是协议定义。
- **“拆成字节会丢失原文。”** 设计正确时可以可逆恢复，但序列可能更长。
