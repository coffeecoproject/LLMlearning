# 词表大小、配置与兼容性

> [!summary]
> 模型权重、Tokenizer、词表编号和特殊 Token 配置必须彼此兼容；能产生合法整数，不代表这些整数对模型具有正确含义。

## 为什么映射必须稳定

假设模型建立参数时使用：

```text
ID 4281 → "苹果"
```

若换一套词表后变成：

```text
ID 4281 → "汽车"
```

模型虽然仍能读取第 4281 行，但这行参数是在原来“苹果”的上下文中形成的。程序可能不报错，含义却已经错位。

## 三个“词表大小”不一定相同

真实工具中常见：

```text
基础 Vocabulary size → Tokenization Model 原有词表大小
len(tokenizer)        → 可能还包含 Added Tokens
model vocab_size      → 模型输入和输出参数支持的容量
```

不同库定义存在差异，所以不要只看字段名称。至少要确认：

```text
Tokenizer 可能输出的最大 ID
< 模型支持的参数行数
```

## 新增 Token 为什么不只是改词表

新增一个 Token 通常还涉及：

1. 分配新 ID；
2. 扩展输入参数行；
3. 必要时扩展输出参数行；
4. 通过训练让新参数形成有效用途。

否则新 Token 即使不会越界，也可能只是没有学到稳定含义的新位置。

## 开放模型观察：Qwen3-32B

官方 `config.json` 的相关字段包括：

```json
{
  "vocab_size": 151936,
  "bos_token_id": 151643,
  "eos_token_id": 151645,
  "hidden_size": 5120,
  "tie_word_embeddings": false
}
```

它们可以先这样读：

```text
151936 → 模型配置的词表容量
151643 / 151645 → 两个协议相关 ID
5120 → 每个 Token 位置的模型向量宽度
false → 输入 Embedding 与输出映射不共享参数
```

但字段名不能单独决定完整协议。对应 Tokenizer 配置将 `151643` 映射为 `<|endoftext|>`，并设置 `add_bos_token=false`；生成配置还可以规定多个停止 ID。因此要把模型配置、Tokenizer 配置和对话/生成协议一起核对。

来源：[Qwen3-32B `config.json`](https://huggingface.co/Qwen/Qwen3-32B/blob/e3a3f59b0423be17f9582d1755fd3d5449b31a1f/config.json)、[Tokenizer 配置](https://huggingface.co/Qwen/Qwen3-32B/blob/9216db5781bf21249d130ec9da846c4624c16137/tokenizer_config.json)、[Generation 配置](https://huggingface.co/Qwen/Qwen3-32B/blob/main/generation_config.json)，核对日期：2026-07-24。

> [!note] 阶段边界
> 这里使用配置只为了认识静态结构和兼容性，不展开模型加载、请求处理或生成停止逻辑。

## 一个简单参数量例子

若 `vocab_size=1000`、`hidden_size=64`，输入 Embedding 参数数是：

```text
1000 × 64 = 64000
```

这个乘法只说明“每个 Token 各有一行 64 维参数”；它不表示模型总参数量，也不要求继续学习矩阵计算。

## 常见误解

- **“Tokenizer 能输出某个 ID，模型就一定支持。”** 还要检查范围和含义是否匹配。
- **“`vocab_size` 在所有工具里定义完全相同。”** 基础词表、Added Tokens 和模型容量可能分开统计。
- **“新增 Token 后模型自动理解名称。”** 还需要参数扩展和训练数据。
- **“看到 `bos_token_id` 就表示每次输入都会自动添加它。”** 是否添加取决于具体配置和协议。

## 理解检查

1. 为什么 ID 没越界仍可能产生严重错误？
2. 基础词表大小、Tokenizer 长度和模型容量为什么可能不同？
3. 新增 Token 通常还需要哪些模型侧变化？
