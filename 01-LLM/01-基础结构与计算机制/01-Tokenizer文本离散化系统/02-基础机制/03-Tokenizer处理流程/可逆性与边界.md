# 可逆性与边界

## 一句话理解

> Tokenizer 可以可靠表示文本，不等于 Encode 与 Decode 必然逐字符还原原文；规范化、特殊 Token 处理和截断都可能改变或丢失信息。

## 什么时候可能往返一致？

如果没有破坏性规范化、没有截断，并且字节和边界规则正确：

```text
text
→ encode
→ IDs
→ decode
→ text
```

通常可以较好恢复。

## 哪些步骤会破坏可逆性？

### Normalization

```text
Ａ → A
```

转换后无法知道原来是哪种形式。

### Truncation

被截掉的 Token 已经不在 ID 序列中，Decoder 无法恢复。

### 特殊 Token 跳过

如果解码时隐藏特殊 Token，输出不会保留原始协议边界。

### 错误或宽容的字节处理

不完整字节可能被替换字符代替，导致结果与原字节序列不同。

## Tokenizer 不负责什么？

- 不负责理解句意；
- 不负责生成答案；
- 不负责 Attention；
- 不负责验证事实；
- 不负责把 Token ID 直接变成语义向量。

它的责任边界结束在模型输入准备和文本恢复附近。

## 为什么必须与模型配套？

模型训练时，某个 Token ID 已经绑定到特定 Embedding 参数。如果换用另一套 Tokenizer，相同整数可能代表完全不同的片段，模型接收到的意义就会错位。

## Chat Template 的边界

Chat Template 属于交互协议；Tokenizer 负责把其结果编码。某些库把二者包装在同一对象里，这是 API 便利，不代表概念上完全相同。

## 最终自检

看到一个 Tokenizer API 时，应当分别询问：

1. 是否做 Normalization？
2. 怎样 Pre-tokenize？
3. 核心模型是 BPE、WordPiece 还是 Unigram？
4. 怎样添加特殊 Token？
5. Token 与 ID 的词表是什么？
6. 是否自动截断或补齐？
7. Decoder 怎样处理字节、空格和特殊 Token？
