# 工具边界与选择

> [!summary]
> 使用现成模型时，首要原则不是选择“最强 Tokenizer 工具”，而是加载与目标模型完全配套的 Tokenizer；只有训练新模型时，才需要设计和训练新的 Tokenizer。

## 【运行阶段】按目标模型选择

| 目标 | 通常选择 | 原因 |
|---|---|---|
| 估算 OpenAI 模型 Token | 官方指定方式或匹配的 tiktoken Encoding | 与目标模型计数规则一致 |
| 运行 Hugging Face 模型 | 该模型仓库的 `AutoTokenizer` | 自动读取配套资产与类 |
| 仓库提供 SentencePiece 模型 | 加载仓库指定的 `.model` | 保持词表与切分规则一致 |
| 构建跨模型 Agent | 每个模型各自的 Tokenizer 适配器 | 不存在通用 Token 计数 |

核心不是个人偏好，而是兼容性：

```text
先确定目标模型
→ 查官方 Tokenizer 说明
→ 加载精确版本
→ 用真实样例验证
```

## 【训练阶段】什么时候才需要自己选工具

只有准备训练自己的 Tokenizer 或新 LLM 时，才需要比较：

- 采用 BPE、Unigram 还是其他方法；
- 是否直接处理原始 Unicode；
- 是否需要字节回退；
- 词表规模、特殊 Token 和规范化规则；
- 训练与部署环境支持什么实现；
- 是否需要采样式切分、字符对齐等能力。

此时 Hugging Face Tokenizers 与 SentencePiece 都可能用于训练；最终选择取决于模型需求，而不是库的名气。

## 【两阶段共同】Agent 为什么尤其在意 Tokenizer

Agent 会不断累积系统指令、历史消息、工具结果和文件内容。它必须在调用模型前管理上下文：

```text
收集候选上下文
→ 用目标模型的 Tokenizer 计数
→ 预留输出空间
→ 选择保留、摘要或截断内容
→ 发送请求
```

如果计数器与实际模型不匹配，Agent 的上下文管理便建立在错误预算上。并且 Tokenizer 只负责计数和编码；“删哪段、摘要哪段、保留什么”属于 Agent 或运行框架的上下文策略。

## 工具不能替你解决什么

- Tokenizer 不会判断一段上下文是否重要；
- `encode()` 不会让模型理解事实；
- 更少的 Token 不自动等于更高质量；
- `decode()` 不负责选择模型下一步输出；
- Tokenizer 工具不会替代模型评估和上下文设计。

## 一个实用决策法

```text
只是调用已有模型？
├── 是 → 使用模型官方配套 Tokenizer，不自行训练
└── 否，正在训练新模型
    → 定义语料、语言、代码、特殊 Token 与部署需求
    → 再选择算法和实现工具
```

## 常见误解

- **“tiktoken 比 SentencePiece 好，所以所有模型都该换成 tiktoken。”** 工具不能脱离模型权重随意替换。
- **“Agent 用字符数估算也差不多。”** 中文、英文、代码和 Emoji 的字符到 Token 比例并不固定。
- **“Tokenizer 达到上限会自动聪明地删旧消息。”** Tokenizer 只报告或产生 Token；截断和压缩策略在上层。
- **“换 Tokenizer 可以直接让旧模型支持更多语言。”** 换词表会破坏 ID 与已训练参数的对应关系。

## 理解检查

1. 为什么已有模型的 Tokenizer 选择不是一个自由优化问题？
2. Agent 的 Token 计数与上下文删减分别由哪一层负责？
3. 在什么情况下才应该认真比较 Tokenizer 训练工具？
