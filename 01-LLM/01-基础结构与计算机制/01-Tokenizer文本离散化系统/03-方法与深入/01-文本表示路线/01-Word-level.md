# Word-level：按单词表示

## 一句话理解

> Word-level 把完整单词作为主要 Token 单位，读起来直观，但无法用有限词表优雅覆盖不断出现的新词和不同语言形式。

## 为什么人们会先想到单词？

人阅读英文时很容易看到空格分隔的单词：

```text
I like apples.
```

示意切分：

```text
["I", "like", "apples", "."]
```

单词通常携带较完整的意义，所以这种方式符合人的直觉，也能让一句话只产生少量 Token。

## 真实机制

构建 Word-level Tokenizer 时，需要先从训练语料收集单词，再选出有限数量放进 Vocabulary：

```text
训练文本
→ 按规则识别单词
→ 统计不同单词及频率
→ 选择有限词表
→ 给每个词分配 Token ID
```

编码时，如果输入单词在词表中，就能直接找到 ID；如果不在，就需要使用未知词标记，或者依赖额外回退机制。

## 核心问题：单词世界不是有限的

即使只看英文，也会不断出现：

- 人名、地名和产品名；
- 拼写变化与拼写错误；
- 专业术语；
- 网址、邮箱和代码标识符；
- 数字与日期组合；
- 新造词和词形变化。

假设词表有 `play` 和 `playing`，仍可能遇到 `replaying`、`gameplay`、`playability`。把所有完整形式都加入词表，会让词表迅速膨胀。

## 未登录词 OOV

OOV 是 Out-of-Vocabulary，表示“词表之外的词”。传统做法可能把所有未知词变成同一个特殊 Token：

```text
词表没有：Codexium
编码结果：[UNK]
```

这会丢失信息。`Codexium` 与另一个未知词 `Agentopia` 都可能变成 `[UNK]`，模型无法从输入 ID 看出二者原本不同。

## 中文让“什么是单词”更难

英文空格能提供一部分边界，中文通常没有：

```text
我喜欢苹果
```

可能分析为：

```text
我 | 喜欢 | 苹果
```

但更复杂的句子需要分词系统判断边界，而且不同分词标准可能产生不同结果。因此，“按单词切分”本身就可能依赖另一个复杂系统。

## 优势与代价

优势：

- 对词表内常见词非常直观；
- 一个常见单词通常只占一个 Token；
- 序列可能比字符级更短。

代价：

- 词表需要容纳大量词形；
- OOV 会造成信息损失；
- 多语言中的“单词边界”并不统一；
- 词表越大，Embedding 和输出层参数通常越多。

## 边界情况

`don't` 是一个词，还是 `do`、`n't`？`New York` 是两个词，还是一个名称？`user_id` 在代码中怎样切？这些例子说明“单词”并不是永远清晰、统一的工程单位。

## 常见误解

- Word-level 不等于简单按空格切分；标点、缩写和不同语言仍需要规则。
- 单词具有语义，不代表单词一定是最适合模型计算的单位。
- 序列短并不代表整体成本一定更低，因为巨大词表也会增加参数和输出计算。
