# 文本表示路线

> [!summary]
> 文本表示路线回答“可以把什么粒度作为基本候选单位”：完整词、字符、子词片段或字节；它影响词表规模、序列长度和陌生文本覆盖能力。

## 为什么要比较这些路线

词表必须有限，但人类可以不断创造新词、名字、代码和符号。如果单位太大，新文本难覆盖；如果单位太小，序列会很长。

```text
单位较大 → 序列通常较短，但需要更多词表项
单位较小 → 覆盖通常更稳，但序列通常较长
```

这是总体趋势，不是对每句话都成立的固定公式。

## 同一个文本的四种观察方式

以下全是教学示意，不代表真实模型：

```text
输入：unhappiness

Word-level：     [unhappiness]
Character-level：[u, n, h, a, p, p, i, n, e, s, s]
Subword-level：  [un, happi, ness]
Byte-level：     先转成 UTF-8 字节，再由后续规则形成 Token
```

## 核心对比

| 路线 | 基本想法 | 主要优势 | 主要代价 |
|---|---|---|---|
| [[Word-level|Word-level]] | 完整词作为单位 | 直观，常见文本序列较短 | 词表容易膨胀，陌生词难表示 |
| [[Character-level|Character-level]] | 字符作为单位 | 新词可以由字符组合 | 序列较长，“字符”边界也不总简单 |
| [[Subword-level|Subword-level]] | 常见片段大、罕见内容拆小 | 在词表、长度和覆盖间折中 | 切分未必符合语言学直觉 |
| [[Byte-level|Byte-level]] | UTF-8 字节提供底层单位 | 有限字节值可覆盖任意 UTF-8 文本 | 非 ASCII 文本基础序列可能更长 |

## 四者不是四个互斥开关

真实 Tokenizer 经常组合多层设计。例如 Byte-level BPE：

```text
Byte-level → 规定底层从字节出发，提供覆盖能力
BPE        → 学习哪些相邻片段值得合并
最终 Token → 可能包含一个或多个字节
```

因此要区分：

```text
表示路线：Word / Character / Subword / Byte
构建与切分方法：BPE / WordPiece / Unigram
软件实现：tiktoken / SentencePiece / Hugging Face Tokenizers
```

## 字符、字节和 Token 的简单数字例子

在 UTF-8 中：

```text
A  → 1 个字节
苹 → 3 个字节
🍎 → 4 个字节
```

这不能推出它们分别占 1、3、4 个 Token，因为 Tokenizer 可能把多个字节合并，也可能把一个可见字符拆成多个 Token。
