# 1.1.4.1 Tokenizer 的训练与使用

## 一句话理解

> 训练 Tokenizer 是人设定目标后，由计算机程序从大量文本中自动生成词表和切分所需数据；使用 Tokenizer 则是加载这些固定结果，把新文本转换成 Token ID。

## 1. “训练”这个词为什么容易误解？

LLM 训练通常让人想到神经网络、GPU、反向传播和数十亿参数。但 Tokenizer 训练通常不是这套过程。

```text
Tokenizer 训练：学习怎样切分和编号
LLM 训练：学习怎样根据上下文预测下一个 Token
```

两者都由计算机执行，也都从数据中获得结果，但算法、计算规模和产物不同。

## 2. 人负责什么？

人或模型开发团队通常决定：

- 使用哪些训练文本；
- 选择 BPE、WordPiece、Unigram 或其他方案；
- 使用字符、字节还是带字节回退的基础；
- 目标词表大小；
- 是否规范化大小写或 Unicode 形式；
- 需要哪些特殊 Token；
- 不同语言、代码和符号占多大比例。

这些决策会影响最终 Tokenizer，但人通常不会逐项手写几十万个 Token。

## 3. 程序和计算机负责什么？

程序把算法写成可执行步骤，计算机负责扫描语料、统计、比较候选片段并输出文件。

以 BPE 为例：

```text
读取语料
→ 转成基础单位
→ 统计相邻单位
→ 找到应合并的一对
→ 更新语料表示
→ 重复
→ 输出词表与合并规则
```

如果语料和配置相同，并且实现中的排序与随机性也受控，结果通常可以复现。

## 4. 数据负责什么？

算法不会凭空知道“苹果”或 `function` 是否重要。训练语料中的频率和分布提供证据：

```text
某片段反复出现
→ 更可能值得用一个较大 Token 表示

某语言在语料中很少出现
→ 其文本可能被切得更碎
```

所以 Tokenizer 也会反映训练数据的语言和领域分布。

## 5. 训练产物是什么？

根据方法和工具不同，常见产物包括：

- Vocabulary：Token 与 Token ID 的映射；
- Merge Rules：BPE 学到的合并规则和优先级；
- 片段分数或概率：Unigram 等方法编码时需要；
- Normalization 与 Pre-tokenization 配置；
- 特殊 Token 及其 ID；
- 解码所需配置。

它们共同组成可用的 Tokenizer，而不只是单独一张词表。

## 6. 使用阶段发生什么？

训练完成后，面对：

```text
我喜欢苹果
```

Tokenizer 通常执行：

```text
加载固定配置
→ 规范化与预切分（如果该实现需要）
→ 使用固定词表和规则切分
→ 把 Token 映射为 Token ID
```

它不会因为当前用户说了十次“苹果”就立刻把“苹果”加入词表。那需要重新训练或显式修改 Tokenizer，并处理模型参数兼容问题。

## 7. 为什么通常先训练 Tokenizer？

LLM 的输入 Embedding 通常需要为词表里的每个 ID 准备一行参数，输出层也需要产生对应词表大小的 Logits。

```text
确定 Vocabulary
→ 确定 vocab_size
→ 确定 Embedding 和输出层的相关形状
→ 再训练 LLM
```

如果训练中途随意更换 Token 与 ID 的映射，原来学到的参数就可能指向错误的文本单位。

## 8. Tokenizer 会不会与 LLM 一起训练？

常规主流流程通常先训练并固定 Tokenizer，再训练 LLM。但研究中存在联合学习、动态词表或后续扩展词表等方案。它们需要额外机制处理新 Token 的参数和旧模型兼容性，不能把这些研究路线当成默认流程。

## 9. 常见误解

- “程序训练”不是人手工切词，而是程序从数据自动产生结果。
- Tokenizer 训练通常不等于 Transformer 反向传播训练。
- 训练 Tokenizer 不等于训练它理解语义。
- 固定词表不代表模型永远不能处理新词；新词可以被拆成已有的小片段。
