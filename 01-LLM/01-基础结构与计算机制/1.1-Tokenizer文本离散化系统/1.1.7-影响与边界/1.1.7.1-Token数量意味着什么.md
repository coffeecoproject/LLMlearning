# 1.1.7.1 Token 数量意味着什么

> [!summary]
> Token 数量表示一段文本被转换成了多少个离散位置；它不是字符数，但会直接决定模型接收到的序列有多长。

## 从同一句话开始

假设有两个示意 Tokenizer：

```text
原文：我喜欢苹果

Tokenizer A： [我] [喜欢] [苹果]       → 3 个 Token
Tokenizer B： [我] [喜] [欢] [苹] [果] → 5 个 Token
```

> [!note]
> 这是为了解释机制而设计的示意切分，不代表任何真实模型的结果。

两者保存的文字相同，但交给模型的是不同长度的 ID 序列：

```text
A → [ID, ID, ID]
B → [ID, ID, ID, ID, ID]
```

## 为什么序列长度重要

Transformer 按 Token 位置处理信息。Token 越多：

- 输入序列越长；
- 同一上下文窗口能容纳的原始内容可能越少；
- 后续模型需要处理的位置越多；
- 训练语料中的同一段内容也会占据更多训练位置。

这里暂时不展开具体计算公式。现在只需掌握：

```text
原始文本长度相同
≠ Token 序列长度相同
```

## 字符、单词、字节和 Token 不可互换

观察：

```text
苹果
Apple
2026
🍎
user_id
```

它们的字符数、Unicode 编码、UTF-8 字节数和 Token 数属于不同统计单位。一个 Token 可能覆盖：

- 一个完整词；
- 一个词的一部分；
- 一个汉字；
- 多个汉字；
- 若干字节；
- 空格与后面的文字。

因此不能用“一个 Token 大约等于一个字”作为普遍规则。

## 词表大小与序列长度的基本权衡

如果词表保存更多常见长片段：

```text
“人工智能” → 可能用较少 Token 表示
```

但更大的词表也意味着模型需要为更多 ID 准备对应参数。反过来，词表较小、基础单位较细，覆盖文本更容易，但常见内容可能被拆成更长序列。

这不是简单的“词表越大越好”：

```text
更大的词表
↔ 更短的部分序列，但更多词表项

更小的词表
↔ 更强的组合复用，但部分序列更长
```

## Token 数少是否一定更好

不一定。极端地把整句话作为一个 Token，虽然序列很短，却会产生几乎无法覆盖新句子的巨大词表，也失去子结构复用能力。

好的 Tokenizer 要平衡：

- 覆盖开放文本；
- 复用常见子结构；
- 控制词表规模；
- 避免序列不必要地变长。

## 常见误解

- **“字符越多，Token 一定同比增加。”** 不一定，Token 边界不是固定字符边界。
- **“Token 越少，模型一定越聪明。”** Token 数只反映表示方式，不等同于模型能力。
- **“扩大词表一定能减少所有文本的 Token。”** 词表容量有限，且不同语料受益不同。
- **“上下文长度是按字数计算。”** 模型通常按 Token 位置计算上下文长度。
