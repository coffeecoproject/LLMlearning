# 1.1.5.6 Vocabulary Lookup 与输入整理边界

> [!summary]
> Vocabulary Lookup 把最终 Token 序列映射成 ID；Padding、Truncation 和 Attention Mask 是许多 Tokenizer 工具附带的输入整理能力，但不属于文本切分本身。

## 核心流程：Vocabulary Lookup

假想映射：

```text
<bos> → 1
我    → 105
喜欢  → 8621
苹果  → 12876
<eos> → 2
```

最终得到：

```text
[1, 105, 8621, 12876, 2]
```

这些 ID 都是虚构示意。到这里，Tokenizer 的核心编码任务已经完成。

## 相邻接口：为什么工具还会整理输入

模型接口常希望一次接收规则形状的 Token ID 张量，所以 Tokenizer 软件通常还提供下面三项能力。它们和 Tokenization 经常在同一次 API 调用中出现，但概念职责不同。

### Truncation：超过上限时截断

```text
原序列长度 8，允许长度 5
→ 按指定策略保留 5 个 ID
```

被截掉的信息不会进入模型。何时触发、从哪一侧截以及怎样管理长上下文，属于普通运行模块；本节只识别这个接口行为。

### Padding：把短序列补到共同长度

```text
A：[12, 38, 91, PAD, PAD]
B：[74, 28, 16, 50, 63]
```

这里两条序列都变成长度 5。左侧还是右侧补齐要遵循具体模型配置。

### Attention Mask：标出有效位置

对应上面的输入，可以附带：

```text
A：[1, 1, 1, 0, 0]
B：[1, 1, 1, 1, 1]
```

`1` 表示真实输入位置，`0` 表示 Padding。这里的 Padding Attention Mask 不是 [[1.4.2.3.3-为什么必须排除未来位置|Causal Mask]]：前者排除无效填充，后者限制未来信息可见性。

## 一张职责表

| 操作 | 解决的问题 | 是否决定 Token 边界 |
|---|---|---:|
| Vocabulary Lookup | Token 对应哪个 ID | 否 |
| Truncation | 输入超过长度上限 | 否 |
| Padding | 多条序列长度不同 | 否 |
| Padding Attention Mask | 哪些位置是补齐出来的 | 否 |

## 常见误解

- **“Padding 是 BPE 的一步。”** 它发生在切分和编号之后。
- **“Attention Mask 都是同一种 Mask。”** Padding Mask 和 Causal Mask 解决不同问题。
- **“Tokenizer 截断只是隐藏文字。”** 被截断 Token 不会进入本次模型输入。
