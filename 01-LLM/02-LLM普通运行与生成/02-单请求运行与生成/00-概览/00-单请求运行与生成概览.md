# 单请求运行与生成

> [!summary]
> 本专题跟踪一个请求从消息输入到文本输出的完整因果链，只讨论单请求必须发生的步骤，不把多用户调度和部署系统混进来。

## 系统结构

```text
输入准备
→ Prefill 与首次预测
→ KV Cache 与增量 Decode
→ Token 选择策略
→ 停止、文本恢复与流式输出
```

## 阅读顺序

1. [[00-输入准备概览|输入准备]]：消息怎样成为模型输入；
2. [[00-Prefill与首次预测概览|Prefill 与首次预测]]：模型怎样读完当前上下文并给出第一组候选；
3. [[00-KV-Cache与增量Decode概览|KV Cache 与增量 Decode]]：为什么后续生成不必每次重算全部历史；
4. [[00-Token选择策略概览|Token 选择策略]]：怎样从词表候选中选出一个 Token；
5. [[00-停止恢复与流式输出概览|停止、恢复与流式输出]]：怎样结束循环并让用户看到文字。

## 本专题始终坚持的边界

- “单请求”是为了先看清机制，不代表真实服务一次只能处理一个用户。
- 模型内部产生 Logits；生成控制器使用 Logits；Tokenizer 把 Token ID 恢复成文本。
- KV Cache 依赖模型 Attention 结构，但缓存的分配、分页和跨请求调度属于 Runtime。
- 本专题只研究普通自回归生成。Beam Search、Speculative Decoding 和结构化约束放到后续深入层。

## 一个贯穿示例

后续用同一个简化输入串联：

```text
messages = [{role: "user", content: "请用一句话解释 Token。"}]
```

它会经历：

```text
消息结构
→ Chat Template
→ Token ID 序列
→ Prefill
→ 选择第一个回答 Token
→ Decode 循环
→ EOS 或其他停止条件
→ 可显示文本
```

从 [[00-输入准备概览|输入准备]] 开始。
