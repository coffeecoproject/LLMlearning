# 普通运行与生成框架速览

> [!summary]
> 普通运行不是模型重新学习，而是固定参数模型反复做前向计算：先读完整输入，再一次选出一个新 Token，把它接回上下文，直到停止。

## 先区分“运行”和“生成”

- **Inference（推理运行）**：使用训练好的参数做前向计算。这里的“推理”是工程含义，不等于逻辑思考。
- **Generation（生成）**：把模型的一次次前向输出接成一个逐 Token 循环。

一次前向计算只给出“下一个 Token 的候选分数”，完整回答需要多次运行：

```text
上下文 → 前向计算 → 选 Token 1
上下文 + Token 1 → 前向计算 → 选 Token 2
上下文 + Token 1 + Token 2 → ……
```

## 一次请求的六步

| 步骤 | 直白理解 | 主要输出 |
|---|---|---|
| 1. 输入准备 | 把角色消息整理成模型熟悉的 Token 序列 | `input_ids` 等输入张量 |
| 2. Prefill | 一次处理已有输入，建立各层运行状态 | 首次 Logits、KV Cache |
| 3. Token 选择 | 根据 Logits 和生成规则选一个 Token | 新 Token ID |
| 4. Decode | 把新 Token 接回序列，利用缓存计算下一步 | 新 Logits、扩展后的缓存 |
| 5. 循环与停止 | 重复选择和 Decode，直到 EOS 或其他条件 | 完整 Token ID 序列 |
| 6. 文本恢复 | Tokenizer 把 Token ID 恢复成文字并逐步发送 | 用户看到的文本 |

## 用一个极小例子串起来

用户输入：

```text
中国的首都是
```

教学化流程可能是：

```text
文本 → [Token A, Token B, Token C]
Prefill → “北京”对应 Token 的分数最高
选择“北京”
Decode → 根据“……首都是北京”继续预测
选择“。”
下一步选择 <EOS>
停止并显示“北京。”
```

> [!warning] 示例边界
> 这里省略了真实 Chat Template、实际 Token 切分和大词表中的其他候选。它只用来展示生成循环，不代表某个真实模型的 Token ID。

## 哪些东西会变，哪些通常不变

```text
通常不变：模型权重、Embedding 参数、Attention/FFN 参数
随请求变化：输入 Token、Hidden States、KV Cache、Logits、已生成 Token
```

因此，模型可以根据当前上下文改变回答，但这不等于一次聊天自动修改了它的长期知识。

## 为什么用户看到的是逐步输出

Decoder-only LLM 的下一步依赖此前所有可见 Token。第 2 个新 Token 要等第 1 个新 Token 被选定后才能计算，因此输出方向在逻辑上是串行的。服务端可以做并行计算和批处理，但不能在普通自回归生成中同时确定一串彼此依赖的未来 Token。

## 先不要混入的三件事

- **训练**：会计算 Loss 并更新参数，普通运行不会。
- **Runtime 服务优化**：负责多请求批处理、调度和内存管理，不是模型回答内容的基本原理。
- **Agent**：可能多次调用模型和工具；这里先只看一次模型请求。

## 框架层完成标准

你如果能回答下面四个问题，就可以进入下一部分：

1. 为什么一次前向计算通常不能直接产生整段回答？
2. Prefill 和 Decode 在时间顺序上分别处理什么？
3. KV Cache 为什么是运行状态而不是模型知识？
4. 模型权重不变时，什么仍会随请求改变？
