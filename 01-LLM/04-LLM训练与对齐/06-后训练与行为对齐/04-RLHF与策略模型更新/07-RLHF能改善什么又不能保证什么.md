# RLHF 能改善什么，又不能保证什么

> [!summary] 一句话理解
> RLHF 能把模型行为推向训练反馈更偏好的方向，却不会自动补齐缺失知识、证明事实正确、确保所有价值一致，也不能代替 Agent 的真实执行与验收闭环。

## RLHF 可能改善什么

在数据、Reward Model 和训练稳定性都较好时，RLHF 可能改善：

- 指令遵循；
- 回答相关性和帮助性；
- 简洁与完整之间的平衡；
- 对不确定性的表达；
- 安全与拒绝行为；
- 多个合理答案之间的选择；
- 特定产品所需的对话风格。

它尤其适合那些难以写出唯一标准答案、但人类能够比较“哪个更好”的任务。

## 它不自动增加可靠事实

Policy 可能学会更像一个可靠助手，例如：

```text
结构更清楚
语气更稳健
更愿意说明限制
```

但这不表示参数中突然加入了经过核验的新知识。流畅和有帮助的倾向仍可能包裹事实错误。

```text
更受偏好
≠ 更接近客观事实
```

事实问题仍需检索、工具、数据库和独立评估。

## 它不等于普遍价值对齐

RLHF 所说的 Human Feedback 来自特定：

```text
标注人群
+ 评审说明
+ 候选回答
+ 产品目标
+ 安全政策
```

因此训练得到的是这些条件下的行为偏好，不是所有人、所有文化和所有场景都同意的一套完整价值体系。

## 为什么会出现过度拒绝或迎合

如果 Reward 过度鼓励谨慎，Policy 可能拒绝正常请求；如果过度鼓励帮助性，模型可能在信息不足时编造答案来满足用户。

其他可能的极端包括：

- 回答越来越长；
- 过度使用免责声明；
- 总是顺着用户观点；
- 为获得高分而使用固定套话；
- 牺牲数学、代码或多语言能力。

这说明对齐目标之间存在张力，需要分开评估，而不能只看一个 Reward 指标。

## Alignment Tax 是什么

**Alignment Tax（对齐代价）**指模型在改善目标行为时，某些原有能力可能下降的现象或权衡。

例如：

```text
安全拒绝更稳定
但正常边界问题也更容易被拒绝
```

或者：

```text
默认回答更简洁
但复杂任务中过早结束
```

它不是必然固定发生，也不是一个统一税率；是否存在需要比较训练前后多类评估。

## RLHF 不会改变底层生成事实

训练后的模型仍然是：

```text
上下文
→ Transformer Forward
→ Logits
→ Runtime 选择下一 Token
→ 重复
```

RLHF 改变 Weight 和生成倾向，不会把概率模型变成确定性规则引擎。

所以同一问题仍可能因上下文、采样和模型局限产生不同结果。

## RLHF 与推理模式不是同一件事

RLHF 可以训练模型更愿意展示步骤、检查答案或遵循某种推理格式，但：

```text
RLHF
≠ 运行时自动增加计算轮数
≠ Agent 自动调用工具
≠ 结果必然经过验证
```

推理模型的数据、训练目标和 Runtime 控制属于后续更专门的主题。

## 对 Agent 设计意味着什么

RLHF 可以让模型更倾向：

- 正确解释工具需求；
- 输出符合协议的 Tool Call；
- 根据 Tool Result 继续；
- 承认失败并尝试修正；
- 遵循目标与约束。

但现实完成仍必须由 Agent 系统保证：

```text
模型提出行动
→ Agent 执行工具
→ 保存真实状态
→ 测试或规则验证
→ 不通过则继续循环
→ 证据满足后才完成
```

RLHF 塑造“更可能怎么做”，Agent 闭环证明“实际上做成了什么”。

## 应怎样评估 RLHF

至少分开观察：

1. 人类或独立评审的偏好胜率；
2. 事实正确性；
3. 数学、代码和专业任务能力；
4. 指令与格式遵循；
5. 过度拒绝与过度迎合；
6. 回答长度和风格偏差；
7. 安全红队测试；
8. 未见任务与真实用户分布；
9. Reward 是否升高而真实质量没有提升。

只看训练 Reward 上升，最容易错过 Reward Hacking。

## 常见误解

### RLHF 之后模型就不会幻觉

不会。它可以减少某些行为，却不能保证所有事实正确。

### Reward 越高，模型所有能力都越强

不成立。不同目标可能冲突，过度优化还可能损伤其他能力。

### 做好 RLHF 就不需要 Agent 验证

错误。模型行为倾向和现实完成证据是不同层。
