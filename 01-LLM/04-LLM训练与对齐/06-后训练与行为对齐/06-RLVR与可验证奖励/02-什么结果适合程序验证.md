# 什么结果适合程序验证

> [!summary] 一句话理解
> 最适合 RLVR 的任务具有明确输入、可提取输出和稳定检查规则；如果“好答案”依赖开放事实、主观价值或隐藏现实状态，就很难只靠一个 Verifier 判断。

## 一个任务适合验证的四个条件

### 有明确目标

例如：

```text
求方程的解
让全部测试通过
输出合法 JSON
把对象移动到指定位置
```

### 输出可以被提取

系统能够从模型回答中找到最终答案、代码、工具参数或环境动作。

### 有可执行检查

存在答案比较、编译器、测试、Schema、规则引擎或环境状态查询。

### 检查成本可接受

验证必须足够安全、稳定和便宜，才能对大量 Rollout 重复执行。

## 数学任务

适合验证的例子：

```text
整数答案：136
选择题选项：C
代数表达式：与标准表达式等价
证明：通过形式化证明检查器
```

需要注意：文本字符串不同不一定答案不同，例如：

```text
1/2
0.5
50%
```

如果 Verifier 只做字符串完全匹配，可能误判等价答案。

## 代码任务

可以检查：

- 是否编译；
- 单元测试是否通过；
- 静态检查是否通过；
- 性能是否低于限制；
- 是否产生正确文件或输出；
- 是否满足安全沙箱规则。

但测试覆盖不完整时，模型可能写出“只通过现有测试”的错误实现，甚至利用测试或环境漏洞。

## 结构化输出与指令约束

适合检查：

```text
JSON 能否解析
是否符合 JSON Schema
是否正好列出三项
是否只使用允许字段
是否包含要求的关键词
```

这类检查能训练格式遵循，却不能判断 JSON 中的事实内容一定真实。

## 工具与环境任务

Agent 可以在模拟器或受控环境中执行动作，再读取状态：

```text
任务：创建一条测试订单并取消
→ Agent 调用工具
→ 环境记录订单状态
→ Verifier 检查最终状态是否为 cancelled
```

这比只检查模型说“订单已经取消”可靠得多。

训练环境必须隔离权限和副作用，避免模型在真实生产系统上为了 Reward 执行危险操作。

## 哪些任务不容易只靠程序验证

### 开放写作

文章是否有洞察、叙事是否优美，很难写成唯一程序规则。

### 事实型开放问答

如果事实分散、时间变化或来源冲突，简单答案匹配不足以判断质量。

### 价值与安全判断

很多场景依赖上下文、社会规范和风险权衡，不适合只用几个关键词判定。

### 长期现实任务

“公司三个月后运营更好”很难在训练当下快速验证，且结果受模型之外的许多因素影响。

## 可验证程度是一条连续谱

任务不是只有“可验证/不可验证”两类：

```text
完全确定：整数答案、编译结果
较强验证：高覆盖测试、形式化证明
部分验证：引用存在、格式正确、部分事实匹配
软判断：帮助性、风格、价值取舍
```

现实系统常将多种信号组合，而不是强迫一个 Verifier 解决全部问题。

## 验证器也需要版本与证据

可靠训练记录应保存：

- Verifier 版本；
- 测试或标准答案版本；
- 执行环境；
- 输入和提取后的答案；
- 原始输出；
- 通过、失败和异常原因。

否则以后无法判断 Reward 是由哪套规则产生的。

## 常见误解

### 有标准答案字符串就一定可可靠验证

不一定。需要处理等价表达、单位、精度和答案提取。

### 代码通过测试就证明实现完全正确

只证明通过当前测试和环境，仍受覆盖率与漏洞限制。

### 格式验证通过就等于内容正确

不是。合法 JSON 也可以包含虚假字段值。
