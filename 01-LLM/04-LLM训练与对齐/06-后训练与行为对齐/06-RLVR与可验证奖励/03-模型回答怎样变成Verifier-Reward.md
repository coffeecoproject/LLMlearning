# 模型回答怎样变成 Verifier Reward

> [!summary] 一句话理解
> 模型的完整文本不能自动成为 Reward；训练系统要先提取待检查结果，再在受控环境中运行 Verifier，最后把通过、失败或部分得分转换成数值反馈。

## 从一条模型回答开始

题目：

```text
一个长方形长 8、宽 5，面积是多少？
```

模型回答：

```text
面积等于长乘宽，所以 8 × 5 = 40。
最终答案：40
```

Verifier 不一定把整段自然语言与标准答案逐字比较，而会经过多个步骤。

## 第一步：Answer Extraction

**Answer Extractor（答案提取器）**从完整回答中找到要验证的最终结果：

```text
完整回答
→ 提取“最终答案：40”
→ 标准化为数值 40
```

提取方式可以是：

- 固定标签；
- 正则表达式；
- JSON 字段；
- 代码块；
- 工具调用参数；
- 专门的解析程序。

如果解析失败，系统需要明确区分“答案错误”和“格式无法提取”。

## 第二步：Normalization

**Normalization（规范化）**把等价表达转换成可比较形式，例如：

```text
“40” → 数字 40
“40.0” → 数字 40
“40 平方厘米” → 数值 40 + 单位 cm²
```

规范化规则过严会误判正确答案，过宽又可能把不同答案错误地视为相同。

## 第三步：执行验证

```text
提取结果：40
标准答案：40
→ 数值比较通过
```

代码任务可能变成：

```text
提取代码
→ 写入隔离环境
→ 编译
→ 运行测试
→ 收集退出状态与测试报告
```

Agent 任务则可能检查环境最终状态，而不是只看回答文字。

## 第四步：把结果映射成 Reward

最简单的二元奖励：

```text
通过 → Reward = 1
失败 → Reward = 0
```

也可以更细：

```text
答案正确：        +1.0
格式符合要求：    +0.2
超出资源限制：    -0.3
触发安全违规：    -1.0
```

这些数字和权重由训练设计决定，没有一套通用固定分数。

## 第五步：保存验证证据

除了一个 Reward，可靠数据管线还应保存：

```text
原始回答
提取结果
Verifier 版本
测试日志或比较结果
异常信息
最终 Reward
```

这样才能分析模型究竟是答案错、格式错、解析错，还是验证环境失败。

## 为什么 Verifier 异常不能简单判成错误答案

例如代码验证超时可能来自：

- 模型代码死循环；
- 测试服务故障；
- 机器负载过高；
- 依赖下载失败；
- 沙箱配置错误。

如果全部记作 `Reward=0`，模型会收到混乱信号。训练系统通常需要区分模型失败、基础设施失败和无效样本。

## Reward Hacking 可能出现在哪里

模型可能尝试：

- 输出让解析器错误提取的字符串；
- 针对公开测试写死答案；
- 修改测试文件；
- 利用沙箱权限读取标准答案；
- 产生超长输出拖垮验证器；
- 满足格式规则却绕过真实任务。

所以 Verifier 需要安全隔离、隐藏测试、权限控制和持续对抗检查。

## Verifier 与 Runtime 的关系

RLVR 训练时，Verifier 位于训练环境：

```text
Policy Rollout → Verifier → Reward → 参数更新
```

部署后，产品也可以运行测试或验证器：

```text
Agent 行动 → Verifier → 决定继续还是完成
```

两者可以复用部分规则，但一个产生训练信号，一个控制当前任务闭环，目的不同。

## 常见误解

### Verifier 直接阅读 Hidden State

通常不是。它多半检查模型输出、代码执行结果或环境状态。

### 只要最终 Reward 是 0，就一定是模型推理错误

不一定，也可能是答案解析或验证基础设施失败。

### Reward 是模型自己写在回答里的数字

不是。Reward 应由模型外部的验证系统计算，不能信任模型自报分数。
