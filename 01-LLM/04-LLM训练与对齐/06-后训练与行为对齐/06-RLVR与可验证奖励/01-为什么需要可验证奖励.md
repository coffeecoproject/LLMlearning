# 为什么需要可验证奖励

> [!summary] 一句话理解
> 人类偏好和 Reward Model 擅长判断“哪个回答整体更好”，但在能明确检查对错的任务上，程序验证可以提供更直接、更便宜且更难受表面文风影响的训练信号。

## 从偏好奖励的局限开始

假设模型回答一道数学题：

```text
17 × 8 = 144
```

这个回答格式整齐、语气自信，但结果错误。

如果只让偏好标注者或 Reward Model 阅读文本，它们可能识别错误，也可能被流畅表达影响。对于这种任务，我们其实已有更直接的方法：

```text
程序计算 17 × 8
→ 标准结果是 136
→ 回答错误
```

验证器不需要判断文风，只需执行明确检查。

## 可验证奖励解决什么问题

### 更接近任务结果

代码是否通过测试、数学答案是否匹配、JSON 是否符合 Schema，都可以直接检查结果。

### 可以大规模自动执行

程序可以反复验证大量 Rollout，不必为每条回答等待人工比较。

### 评价标准更一致

同一测试在相同环境下对不同回答使用同一规则，不会因为标注者情绪或文风偏好改变判断。

### 能支持当前 Policy 探索

Policy 可以不断生成新的解法；只要结果可验证，就能立即得到训练 Reward，不必事先为每种新回答制作 Chosen / Rejected。

## 它与 Reward Model 不是谁完全替代谁

| 问题 | 更适合的反馈 |
|---|---|
| 数学最终答案是否正确 | 答案验证器 |
| 代码是否通过测试 | 编译器与测试框架 |
| JSON 是否符合结构 | Schema Validator |
| 解释是否清楚 | 人类偏好或 Reward Model |
| 语气是否合适 | 人类偏好或行为规则 |
| 现实订单是否真正创建 | 外部系统状态验证 |

开放任务往往需要组合：

```text
可验证的硬结果
+ 人类或模型对软质量的判断
```

## 为什么它可能促进推理能力

一道难题只有通过多步分析才容易得出正确答案。训练系统反复奖励最终正确的 Rollout 后，Policy 可能逐渐提高这些行为的倾向：

- 分解问题；
- 尝试不同路线；
- 检查中间结果；
- 发现矛盾后修正；
- 在结束前验证答案。

但 Verifier 通常没有把这些文字步骤逐条教给模型。它只是提供最终结果反馈，模型通过许多尝试发现哪些生成轨迹更容易获得 Reward。

## 可验证不等于绝对真理

Verifier 判断的是：

```text
输出是否满足我们写下的检查条件
```

而不是自动判断：

```text
现实世界中的所有相关事实是否都正确
```

如果测试遗漏边界情况，错误程序也可能通过；如果标准答案写错，正确回答反而会被判错。

所以 Verifier 的可靠性来自规则质量、环境隔离和测试覆盖，不来自“可验证”这个名称本身。

## 对 Agent 设计的意义

Agent 任务中已经存在许多可验证信号：

```text
命令退出状态
单元测试结果
数据库记录
文件内容与差异
API 返回状态
业务验收条件
```

这些信号既可以用于运行时闭环，也可以积累为后续训练或评估数据。

但训练 Reward 和运行时验收仍需区分：训练让模型更倾向采取有效行为；运行时验证证明当前这一次任务实际发生了什么。

## 常见误解

### 可验证奖励完全不需要人类设计

错误。人类仍需定义任务、标准答案、测试、解析规则和安全边界。

### 程序验证一定比 Reward Model 更智能

不是。它通常更窄，只是在明确条件内更直接可靠。

### 有了 RLVR，所有开放问答都能自动训练

不能。很多开放问题没有唯一、廉价、可靠的验证函数。

## 理解检查

2. 可验证奖励为什么能够跟随 Current Policy 生成的新答案？
3. 测试通过为什么仍不等于程序在所有情况下正确？
