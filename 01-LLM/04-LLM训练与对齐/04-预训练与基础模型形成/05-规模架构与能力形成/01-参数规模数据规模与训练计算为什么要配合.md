# 参数规模、数据规模与训练计算为什么要配合

> [!summary] 一句话理解
> 参数量提供容纳复杂规律的空间，训练数据提供学习材料，训练计算让这些材料真正反复改变参数；只有三者相互匹配，规模才可能转化为能力。

## 所属阶段

**预训练阶段。** 这里讨论的是训练 Base Model 时怎样安排模型、数据和计算，不是模型上线后的推理速度，也不是 Agent 怎样调用模型。

## 先连接已经学过的内容

前面已经知道，一次 Training Step 大致经历：

```text
训练 Batch
→ Forward 产生 Logits
→ Loss 衡量预测偏差
→ Backward 产生 Gradient
→ Optimizer 更新参数
```

本篇把观察尺度继续拉远：

```text
一次参数更新
→ 大量 Step
→ 大量训练 Token
→ 参数长期形成可复用规律
```

因此，讨论“模型规模”时不能只看最终有多少参数，还要看这些参数接受了多少有效训练。

## 三个容易混在一起的“规模”

### 参数规模：模型有多少可以被训练的 Weight

例如 `7B` 通常表示大约 70 亿个参数。参数分布在 Embedding、Attention、FFN、输出层等位置。

直觉上可以把参数理解为模型内部可被塑造的巨大调节系统。参数更多，通常能够表示更复杂、更细致的规律，但参数数量不是“知识条目数量”。

```text
100 亿参数
≠ 恰好保存 100 亿条知识
```

同一个参数可能共同参与许多语言、代码和知识模式。

### 数据规模：训练过程中实际使用了多少 Token

这里更关心的是模型真正处理过的训练 Token，而不是磁盘上原始文件有多大。

原始资料经过清理、去重、Tokenizer、采样和 Packing 后，才形成实际训练流。相同资料还可能在不同训练阶段被重复采样。

所以：

```text
原始文件数量
≠ 去重后文本数量
≠ 实际训练 Token 数
≠ 每类数据对 Loss 的有效影响
```

### 训练计算：完成这些 Forward、Backward 和更新需要多少运算

模型越大、训练 Token 越多，通常需要的计算越多。序列长度、架构和训练实现也会影响真实计算量。

训练计算不是一种新的模型能力，而是把训练过程实际执行出来所消耗的运算资源。

## 为什么三者必须配合

### 情况一：参数很多，但训练数据和计算不足

假设有两个教学模型：

```text
模型 A：100 个参数，训练 10,000 个 Token
模型 B：1,000 个参数，也只训练 10,000 个 Token
```

这里的数字只是教学示意。

模型 B 虽然参数更多，但每个参数能够获得的有效训练信号可能不足。它拥有更大的潜在容量，却不代表这些容量已经被充分塑造。

这类似于建了一所很大的图书馆，但只放入少量书籍，也没有足够时间整理目录。

> [!warning] 类比边界
> 参数并不是一个个独立书架，训练也不是把句子原样放入固定位置。这个类比只用于说明“容量存在”与“容量被有效训练”不同。

### 情况二：数据很多，但模型容量不足

```text
模型 C：100 个参数，训练 1,000,000 个 Token
```

它可以反复接触大量规律，但有限参数要同时服务许多语言、知识和任务模式，可能无法充分表示所有复杂关系。

增加数据仍可能有帮助，但收益可能受模型容量限制。

### 情况三：模型和数据都很大，但计算预算不够

如果计算预算只允许模型走完很少一部分训练数据，那么“准备了很多数据”并不等于“模型已经学过这些数据”。

```text
有 1 万亿训练 Token
但训练只处理了其中 1,000 亿
→ 剩余部分没有进入参数更新
```

### 情况四：三者相对匹配

更合理的目标是：

```text
模型具有足够表示容量
+ 数据提供足够多样且有效的学习信号
+ 计算预算足以完成预定训练
→ 更可能把资源转化为较低 Loss 和更强能力
```

这里只能说“更可能”，因为数据质量、架构、优化稳定性和评估方法仍然会影响结果。

## 一个小数字过程

假设教学模型每个 Step 处理 100 个 Token：

```text
1 Step       → 100 Token
1,000 Step   → 100,000 Token
10,000 Step  → 1,000,000 Token
```

如果把模型参数扩大十倍，却仍然只训练 1,000 Step，那么更大的模型未必得到足够机会调整其更多参数。

如果模型和训练 Token 都扩大十倍，完成训练所需的计算通常也会明显增加。

这个例子不是现实训练配方，只用于说明：

> 参数、Token 和计算是同一个训练问题的三个侧面，不能分别孤立比较。

## Chinchilla 研究说明了什么

2022 年的 Chinchilla 研究在给定计算预算下比较模型大小与训练 Token 数，指出当时一些大模型相对“训练不足”：参数做得很大，但训练数据没有同步增加。

研究中的 Chinchilla 使用约 70B 参数，却使用比 280B 参数 Gopher 更多的训练数据，并在许多评测上表现更好。

这不等于“70B 永远胜过 280B”，而是说明：

```text
在有限计算预算下
→ 只扩大参数不一定是最佳分配
→ 模型大小与训练 Token 数需要共同规划
```

> [!source]
> 来源：[Training Compute-Optimal Large Language Models](https://arxiv.org/abs/2203.15556)，Hoffmann 等，2022。核对日期：2026-07-29。

## 参数更多为什么仍然常常有帮助

当数据、计算和训练方法也能配合时，更大的参数规模通常能够：

- 表示更多细致模式；
- 在不同任务之间共享更丰富的内部表示；
- 更有效地利用大量训练数据；
- 在一些任务上表现出更好的迁移和组合能力。

但这是一种经验趋势，不是对每个具体任务的保证。

## 与模型运行的边界

预训练时关心：

```text
多少参数被更新
处理多少训练 Token
完成多少训练计算
```

模型运行时关心：

```text
权重怎样加载
每个 Token 激活多少计算路径
KV Cache 占多少空间
请求延迟与吞吐量
```

MoE 会让“总参数”和“每 Token 激活参数”明显不同，下一篇之后会单独衔接这一点。

## 常见误解

### 参数越多，模型就一定越强

不一定。还需要有效数据、足够训练和合适架构，并且“强”必须由具体评估定义。

### 训练 Token 越多，就一定学到越多事实

不一定。重复、低质量、冲突或不适合训练目标的数据可能带来有限收益，甚至造成负面影响。

### 计算量大就是模型在运行时更慢

这里首先讨论预训练总计算。运行速度还取决于激活参数、硬件、量化、Batch 和 Runtime 优化，不能直接从训练总计算推出。

### 参数规模可以直接换算成智能水平

不能。参数量是结构规模指标，不是通用智能单位。
