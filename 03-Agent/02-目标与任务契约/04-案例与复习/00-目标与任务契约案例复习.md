# 目标与任务契约案例复习

> [!summary]
> 本案例把一句模糊需求依次转成 Goal Draft、澄清问题、用户决定、正式 Goal 和后续验收义务，用来检查整个因果链是否真正理解。

## 用户原始需求

```text
把订单取消功能完善一下。
```

系统先保存 Raw Request，不直接启动代码修改。

## 第一次 Goal Draft

```text
Objective Candidate
补齐订单取消流程，使符合条件的订单可以安全取消。

Success Criteria Candidates
1. 可取消订单能够进入已取消状态。
2. 取消后不会继续发货。
3. 已预占库存得到释放。

Open Questions
1. 哪些订单状态允许取消？
2. 已支付订单是否自动退款？
3. 已进入拣货的订单怎样处理？
4. 是否需要处理历史异常订单？
```

这里所有内容仍是候选，不是正式业务规则。

## 有限只读探索

系统读取现有订单状态机后观察到：

```text
订单状态包含：CREATED、PAID、PICKING、SHIPPED、CANCELLED
库存预占会在支付后建立
项目已经存在退款任务接口
```

这些是带来源的项目观察，可以帮助系统提出更准确的问题，但不能自行决定“PICKING 是否允许取消”。

## 用户确认

```text
1. CREATED 和 PAID 可以取消
2. PAID 取消后创建退款任务
3. PICKING 和 SHIPPED 不允许取消
4. 取消必须释放库存预占
5. 本次不修复历史异常订单
```

## 正式 Goal v1

```text
Objective
为 CREATED 和 PAID 订单建立安全取消流程，并阻止不可取消状态继续处理取消请求。

Success Criteria
1. CREATED 订单取消后进入 CANCELLED。
2. PAID 订单取消后进入 CANCELLED 并创建一次退款任务。
3. CREATED 和 PAID 订单取消后释放库存预占。
4. PICKING 和 SHIPPED 订单取消请求被拒绝，状态保持不变。
5. 重复取消请求不会重复退款或重复释放库存。
6. 原有下单、支付和发货回归测试通过。

Scope
订单状态转换、取消服务、库存释放和退款任务创建。

Non-goals
不处理历史异常订单；不更换支付或库存系统。
```

## 怎样进入后续 Agent

```text
Goal v1
→ Discovery 寻找全部取消入口和业务路径
→ Plan 形成任务和依赖
→ Tool Policy 限制允许修改的项目范围
→ Implementation 产生 Candidate
→ Verification 为六条 Criteria 建立证据
→ Acceptance 判断是否完成
```

## 如果用户后来改变要求

用户说：

```text
PICKING 状态也允许取消，但要通知仓库停止拣货。
```

这会改变 Scope、业务路径、工具权限和成功条件，因此应形成 Goal v2，而不是只在当前 Prompt 后面追加一句话。

## 常见失败

### 模型替用户决定

草稿直接写“PAID 自动退款”并执行，没有确认。

### 成功条件只写实现动作

```text
增加 cancelOrder 函数
```

这不能证明退款、库存和状态行为正确。

### Scope 过早缩成文件列表

只允许修改 `OrderController`，导致库存和退款路径被遗漏。

### Goal 改变但旧证据继续使用

v1 的测试不能证明新增的 PICKING 取消流程。

## 理解检查

1. 哪些内容来自项目观察，哪些必须由用户确认？
2. 为什么“创建退款任务”既属于成功条件，也会产生新的验证义务？
3. 为什么重复取消必须作为负向场景？
4. 用户允许 PICKING 取消后，哪些下游对象可能失效？
5. 如果只实现 Goal Intake 而没有 Goal Manager，会缺少什么权威边界？

## 专题完成标准

完成本专题后，应能够：

- 把用户原话、模型草稿和正式 Goal 分开；
- 写出 Objective、Success Criteria、Scope 和 Non-goals；
- 只向用户询问会改变任务契约的重要问题；
- 解释 Goal、Task、Plan 和 Workflow 的不同；
- 设计 Goal revision 和下游失效传播；
- 画出最小 Goal Intake 与 Goal Manager 的职责边界。
