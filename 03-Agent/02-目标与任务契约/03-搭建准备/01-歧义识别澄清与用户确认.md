# 歧义识别、澄清与用户确认

> [!summary]
> Goal Intake 不应追问所有不确定细节，而应优先询问那些会改变目标、范围、风险、权限或验收结果的问题。

## 五类重要歧义

| 类型 | 例子 |
|---|---|
| 目标歧义 | “优化支付”到底是性能、体验还是正确性 |
| 范围歧义 | 是否包含历史订单、移动端和后台任务 |
| 成功歧义 | “正常”由什么结果和证据判断 |
| 权限歧义 | 是否允许修改数据库、发送消息或部署 |
| 外部事实缺失 | 第三方平台是否保证事件 ID 唯一 |

## 哪些问题应该询问用户

优先询问满足以下条件的问题：

```text
不同答案
→ 会改变 Goal、Scope、Non-goals、权限或验收标准
```

例如：

```text
已支付订单取消后是否自动退款？
```

不同答案会改变业务路径和工具权限，因此必须确认。

下面这种问题通常可以留给 Discovery 或 Plan：

```text
具体应该把新类放在哪个文件？
```

它是技术实现选择，不一定需要用户决定。

## 一次不要问太多

模型很容易列出十几个问题。合理系统应按影响排序：

1. 阻止形成 Goal 的关键问题；
2. 涉及不可逆动作或高风险的决定；
3. 会显著改变 Scope 的问题；
4. 可以在 Discovery 中解决的技术未知项；
5. 不影响当前工作的低价值细节。

通常先问前一到三项，其余记录为 Open Questions。

## 用户确认的对象

用户不应只点击一个含义模糊的“确认”。界面应展示：

- 最终 Objective；
- Required Success Criteria；
- Scope；
- Non-goals；
- 关键假设；
- 尚未解决但允许进入 Discovery 的问题；
- 可能需要的高风险权限。

## 谁可以确认

不同内容可能需要不同身份：

```text
普通产品偏好
→ 当前用户

财务规则或真实业务事实
→ 具有业务权限的人

生产部署或数据删除
→ 具有操作权限的人
```

“有人回答了”不等于“有权确认”。确认记录应包含身份、范围、Goal Draft revision 和时间。

## 模型应该怎样处理不知道

模型应允许返回：

```text
UNKNOWN
NEEDS_USER_DECISION
NEEDS_PROJECT_DISCOVERY
NEEDS_EXTERNAL_FACT
```

这些状态比编造一个顺畅答案更有价值。
