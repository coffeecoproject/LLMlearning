# Goal 为什么是 Agent 的入口

> [!summary]
> Goal 告诉 Agent 要把现实从什么状态改变成什么状态；简单任务可以直接使用用户请求，持续或高风险任务则需要把 Goal 独立保存并逐步补全完成边界。

## 从一个模糊需求开始

用户说：

```text
优化一下支付功能。
```

这句话可以对应完全不同的目标：

- 缩短支付页面加载时间；
- 修复重复扣款；
- 增加新的支付方式；
- 改善支付失败提示；
- 降低第三方支付手续费。

如果 Agent 直接开始搜索和修改代码，它必须自行猜测“优化”的含义。模型可能猜得合理，却仍然不是用户真正想要的结果。

## Prompt 与 Goal 的区别

**Prompt** 是某次模型调用收到的输入。它可以包含问题、指令、历史和工具说明。

**Goal** 是 Agent 持续追踪的任务目标。简单 Agent 可以只在当前请求中使用它；持续 Agent 会把它保存为线程状态；高可靠系统还会把它保存为带版本的正式任务契约，使不同 Worker 线程和进程重启仍受同一目标约束。

```text
Prompt
→ 本轮让模型看到什么

Goal
→ 当前任务为什么存在；控制越严格，完成边界越需要显式化
```

同一个 Goal 在不同阶段会产生不同 Prompt：

```text
Discovery Prompt
→ 寻找与重复扣款相关的代码和未知问题

Implementation Prompt
→ 根据已确认范围修改幂等处理

Verification Prompt
→ 检查成功条件是否都有证据
```

对于跨多轮的持续任务，不能把某一轮 Prompt 当成 Goal 的唯一保存位置。

## Goal 怎样影响后续系统

```text
Goal
├── 决定需要探索哪些业务场景
├── 限制 Plan 可以包含哪些工作
├── 限制工具可以影响哪些范围
├── 决定哪些变更属于预期产物
├── 产生必须执行的验证义务
└── 为 Acceptance 提供判断标准
```

如果 Goal 不完整，后面的每个环节都可能在错误边界内运行。

## Goal 不负责什么

Goal 不需要提前包含：

- 每一个要读取的文件；
- 每一条实现步骤；
- 模型的详细推理过程；
- 所有未来可能发现的技术事实；
- 一份永远不能调整的执行计划。

这些内容分别属于 Discovery、Plan、Context 和运行状态。

## 最准确的理解

```text
用户需求
→ 可能模糊、口语化、会变化

Goal
→ 可以从当前请求，逐步增强为持久目标或正式任务契约

Agent Loop
→ 在 Goal 边界内不断观察和行动

Acceptance
→ 判断 Goal 是否真的满足
```

> [!warning]
> 一个控制严谨的 Agent 仍然可能可靠地完成错误 Goal。控制系统只能保证按既定边界执行，不能替用户决定真正想要什么。
