# 成功条件怎样变得可验证

> [!summary]
> 可验证的成功条件描述任务结束时应观察到什么，并能够进一步映射到具体检查和证据，而不是只使用“正常、优化、完善”等模糊形容词。

> [!info] 层级定位
> 基础 Agent 需要一个最小停止或检查条件；把 Success Criteria 正式映射到检查、Evidence 和验收义务属于高可靠扩展。

## 从模糊到可检查

```text
模糊：支付功能正常

更具体：
1. 相同支付事件重复提交两次，只产生一条扣款记录
2. 首次合法支付仍然成功
3. 并发重复请求不会产生两次余额变化
```

这里没有提前规定必须用哪种锁或数据库实现。它定义的是外部可观察结果。

## 一条成功条件需要回答什么

```text
给定什么前提
→ 发生什么动作
→ 应观察到什么结果
→ 用什么类型的证据判断
```

例如：

```text
前提：订单尚未发货且库存已预占
动作：用户取消订单
结果：订单进入已取消，库存预占被释放
证据：订单状态检查 + 库存记录检查 + 自动化场景测试
```

## 成功条件和测试不是同一个对象

```text
Success Criterion
→ 用户或业务希望得到的可观察结果

Verification Obligation
→ 为证明这条标准必须执行的检查义务

Evidence
→ 某次检查对确切版本产生的真实观察
```

如果把成功条件直接写成“运行 test_payment.py”，系统可能只保证脚本通过，却没有确认脚本是否覆盖真实业务目标。

## 正向、负向和回归条件

高风险任务通常需要三类：

- 正向路径：新的预期行为成功；
- 负向或恢复路径：错误、重复或异常输入被正确处理；
- 回归路径：原本正常的行为没有被破坏。

重复扣款例子中，只检查“重复请求不再扣款”还不够，还必须检查首次支付仍然能够扣款。

## 什么时候需要用户确认

技术团队可以提出候选检查，但下面这些通常属于用户或业务决定：

- 哪些订单类型必须覆盖；
- 历史数据是否处理；
- 多长延迟可以接受；
- 哪些失败需要人工介入；
- 哪个风险可以延期。

## 最小质量检查

一条标准应尽量满足：

```text
可观察
可判定
与 Objective 直接相关
不偷偷指定未经确认的业务取舍
能够找到证据来源
```

> [!warning]
> “代码已修改”“模型认为完成”“已有测试通过”都不能自动替代业务成功条件。
