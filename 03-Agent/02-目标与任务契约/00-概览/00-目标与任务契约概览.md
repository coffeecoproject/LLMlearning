# 目标与任务契约概览

> [!summary]
> Agent 至少需要知道当前要完成什么；最小实现可以直接使用本次用户请求，持续或高风险任务才需要把目标独立保存，并逐步增强为可确认、可修订和可验收的任务契约。

## Goal 有不同控制深度

下面是本教程为了比较控制深度使用的学习分类，不是行业统一命名。

```text
Prompt-bound Goal
→ 直接把用户请求作为当前任务目标

Thread Goal
→ 把 Objective 和运行状态持久化到某个线程

Goal Contract
→ 把 Objective、Success Criteria、Scope、Non-goals、revision 和验收关系结构化
```

三者都可以出现在 Agent 中。Goal Intake 不是“Agent”成立的必要条件，而是从模糊需求形成高可靠 Goal Contract 的增强模块。

## 在可选高可靠路径中的位置

```text
用户原始需求
→ 形成 Goal Draft
→ 识别歧义与缺失条件
→ 必要时进行有限只读探索
→ 用户确认关键业务含义
→ 创建正式 Goal
→ 受控 Agent Run 获得正式执行依据
```

这是高可靠控制型 Agent 可以采用的顺序，不是通用 Agent 的固定生命周期。简单任务可以直接把用户请求作为目标；持续 Agent 可以先保存一个 Thread Goal；当需求模糊、影响范围广或验收风险较高时，再考虑完整 Goal Intake。它回答的是“究竟要完成什么”，而正式 Discovery、Planning 和 Tool Use 回答的是“为了完成它，需要了解什么以及怎样行动”。

## 为什么称为任务契约

正式 Goal 不只是把用户原话保存下来，还需要至少区分：

```text
Objective
→ 要改变或实现什么

Success Criteria
→ 出现哪些可观察结果才算成功

Scope
→ 本次任务必须覆盖或允许影响什么

Non-goals
→ 哪些事情明确不属于本次任务
```

它们共同约束后续的搜索范围、计划、工具权限、实际变更和最终验收。

## 高可靠任务契约的一种说明性结构

```text
Raw Request
    ↓
Goal Intake
    ├── 生成 Goal Draft
    ├── 识别歧义
    ├── 提出澄清问题
    └── 展示待确认内容
            ↓
Human Confirmation
            ↓
Goal Manager
    └── 创建或修订正式 Goal
            ↓
Workflow / Agent Runtime
```

Goal Intake 可以使用 LLM 帮助理解需求；Goal Manager 才拥有正式 Goal 的创建和修订权威。

## 真实实现观察：Codex CLI

Codex CLI 当前已经提供持久化的 Thread Goal：它保存 Objective、状态、可选 Token 预算以及 Token/时间使用量，并可以跨 Turn 继续工作。但它没有把 Success Criteria、Scope、Non-goals、Goal revision 和 Evidence 关系拆成同等级的正式字段，也没有强制执行独立 Goal Intake。

因此 Codex 属于“持续 Agent”实现，而本专题的可选扩展部分研究怎样构建更严格的 Goal Contract。详细对照见 [[01-Codex-Thread-Goal与高可靠Goal契约|Codex Thread Goal 与高可靠 Goal 契约]]。

## 关键边界

- LLM 可以提出 Goal Draft，但不能自行确认用户真实意图；
- `Goal Intake` 是本教程使用的可选架构名称，不是行业统一规定的 Agent 标准组件；
- 简单 Agent 可以直接使用用户请求，Goal Intake 不应被描述为所有 Agent 的必经步骤；
- Goal 负责定义目标边界，不负责提前写死全部执行步骤；
- Success Criteria 是验收输入，不是模型生成的一句漂亮结果描述；
- Discovery 可以发现新事实，但不能偷偷改变 Goal；
- Goal 改变需要新 revision，并检查计划、上下文、产物和证据是否已经过期；
- 形式合法不等于语义充分，非空字段仍可能表达一个很差的 Goal。
