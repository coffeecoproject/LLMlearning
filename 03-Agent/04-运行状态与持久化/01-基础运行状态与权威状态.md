# 基础运行状态与权威状态

> [!summary]
> 基础运行状态是 Agent Runtime 用来回答“任务现在进行到哪里”的结构化记录；权威状态则要进一步说明，当多份记录不一致时，哪个系统有资格回答某个具体问题。

> [!info] 层级定位
> **基础 Agent**只需在当前循环中记录状态、最新结果和下一步。持久版本号、跨系统权威核对、原子写入、幂等恢复与 Acceptance 状态属于持续或高可靠实现。

## 它位于执行主线的哪里

```text
读取当前运行状态
→ 构建本次模型上下文
→ 模型提出下一步
→ Runtime 校验并执行允许的动作
→ 获得真实工具结果
→ 形成 Observation
→ 更新运行状态
→ 进入下一轮或停止
```

运行状态是 Agent Loop 每一轮的输入之一，也是每一轮的产物之一。它不是任务开始时写一次、结束时再读一次的静态备注。

## 先从一个可观察的冲突开始

假设 Agent 正在“修复订单重复扣款”。某次模型调用返回：

```text
我已经修复了问题，并且所有测试都已通过。
```

但真实环境显示：

```text
文件确实发生了修改
但并发测试返回 failed
```

此时不能把 Run 写成“已完成”。模型输出只能证明“模型提出了完成声明”，不能证明测试真的通过，更不能证明 Goal 已经满足。

这个冲突揭示了两个核心问题：

1. Agent 至少要保存哪些运行信息？
2. 对于“测试是否通过”这个问题，谁的记录有最终权威？

## 基础运行状态至少要回答什么

不同 Agent 的字段名称不会完全一致。对一个需要连续执行和恢复的单 Agent，一份基础状态通常至少要能回答下列问题：

| 问题 | 可能的状态内容 | 为什么必要 |
|---|---|---|
| 这是哪个任务 | `goal_id`、`run_id` | 避免把不同任务的事件混在一起 |
| 整体处于什么状态 | 已创建、进行中、等待、阻塞、失败、取消、待验收、已接受 | 决定循环是否允许继续 |
| 当前进行到哪里 | 当前 Phase、Task 或 Step | 为下一步决策提供位置 |
| 刚才真实发生了什么 | 最近 Observation、工具结果引用 | 避免依赖模型自己的回忆 |
| 还有什么待处理 | 待执行动作、待审批请求、待回答问题 | 防止遗漏或重复执行 |
| 已经消耗多少 | 步数、重试数、时间、Token 或费用 | 执行预算与停止规则 |
| 这是哪一版状态 | 版本号或修改时间 | 发现旧读取覆盖新写入的冲突 |

这是一份说明性清单，不是所有 Agent 都必须使用的统一 Schema。简单任务可以合并字段；长任务或高风险任务则可能还需要 Goal Revision、产物、Evidence 和 Acceptance 记录。

## 权威状态不是“唯一一张真相表”

**权威状态（Authoritative State）**是对某个具体问题拥有最终解释权的记录。一个 Agent 通常会同时连接多个权威来源，而不是用自己的数据库替代所有现实。

| 要回答的问题 | 通常应优先查看的权威来源 |
|---|---|
| Run 是进行中还是已取消 | Agent Runtime 拥有的 Run 状态存储 |
| 文件现在的内容是什么 | 当前文件系统，必要时结合 Git |
| 测试现在是否通过 | 在正确条件下实际运行得到的测试结果 |
| 支付或退款是否成功 | 支付服务商或业务数据库的可核对状态 |
| 高风险动作是否得到批准 | 审批系统中当前有效的决定 |
| Goal 是否真正被接受 | 验收规则指定的 Acceptance 决定者 |

因此，“权威”必须连同问题一起说。Agent Runtime 可以权威地记录“我上次调用了支付查询工具”，但它不能仅凭这条旧记录永久代表支付系统的当前状态。

## 模型输出只是状态变更建议

模型可能生成：

```text
当前步骤已完成。
请将 Run 改为 completed。
```

这些 Token 在逻辑上是 **Proposed State Change（状态变更建议）**，不是已经发生的状态转换。真正的写入链路应当是：

```text
模型提出动作或完成申请
→ Runtime 检查当前状态是否允许
→ 执行需要的工具或验证
→ 记录真实结果
→ 根据规则决定新状态
→ 由拥有写入权的程序持久化
```

模型不应直接拥有无条件的状态写入权，原因不是“模型永远错”，而是模型生成的是基于当前上下文的提案，而不是对全部外部现实的原子交易。

## 一次合法状态更新怎样发生

以“运行并发支付测试”这一步为例。

### 第一步：读取当前状态

```text
Run：running
当前 Step：检查并发回调
最近 Observation：已增加第一版幂等校验
测试重试数：0
状态版本：12
```

Runtime 先读取状态版本，是为了避免在它处理期间其他执行者已经更新了同一 Run。

### 第二步：模型提出动作

```text
run_test(name="concurrent_payment")
```

这只是候选 Tool Call。Runtime 需要检查工具是否可用、参数是否合法、当前阶段是否允许执行，以及是否还有预算。

### 第三步：环境返回原始结果

```text
exit_code: 1
failed_case: second callback charged again
```

这是 Tool Result。Runtime 可以将其解释并记录为 Observation：

```text
并发支付测试失败；第二次回调仍产生扣款。
```

Observation 是环境结果在 Agent 任务中的语义角色，不应伪造一个与原始结果相反的结论。

### 第四步：计算新状态

根据真实结果，Runtime 可以将新状态计算为：

```text
Run：running
当前 Step：检查数据库事务边界
最近 Observation：并发支付测试失败
测试重试数：1
状态版本：13
```

这里保持 `running`，而不是被模型的早先判断改成 `completed`。

### 第五步：持久化后才向前推进

Runtime 在持久化新 Observation、资源消耗和新状态后，再开始下一轮。这样即使进程随后中断，恢复时也不会回到“从未运行过测试”的旧认知。

## 为什么不能只依赖对话历史

对话历史可以保存用户和模型说过什么，但它不自动提供下列能力：

- 不能保证模型的陈述与当前环境一致；
- 不能自动区分建议动作和已成功执行的动作；
- 不能稳定表示等待审批、取消和预算等机器状态；
- 对话历史被截断、摘要或压缩后，关键执行事实可能丢失；
- 无法安全防止两个执行者同时覆盖对方的更新。

所以更可靠的关系是：

```text
对话与事件历史
+ 结构化运行状态
+ 对现实环境的必要核对
→ 构建本轮上下文
```

结构化状态也不会替代对话历史：它们回答的问题不同。状态记录当前执行事实，历史帮助解释事实是怎样形成的。

## 冲突时怎样判断

当两份记录不一致时，不要先问“哪个存储系统更高级”，而要按顺序问：

1. **我们现在要回答的具体问题是什么？**
2. **哪个系统对这个事实拥有权威？**
3. **当前读到的记录是否可能过期？**
4. **能否安全地重新读取或验证真实状态？**
5. **核对结果是否需要反向更新 Run 状态？**

例如，旧日志记录“支付请求返回成功”，但恢复后查询支付服务商得到“交易不存在”。对于“交易当前是否存在”这个问题，应当优先使用当前可核对的外部状态，并把旧日志保留为“当时发生过什么”的证据，而不是悄悄删除旧日志。

> [!warning]
> 如果重新查询本身会产生副作用，或者外部系统只能提供最终一致的延迟状态，就不能机械地覆盖本地记录。此时需要把状态标记为“待核对”或“结果未知”，并按外部系统的幂等和对账机制处理。

## 一个容易被忽略的中断边界

假设 Agent 向外部系统发起退款：

```text
外部退款已经成功
→ Agent 还未来得及写入新状态
→ 进程崩溃
```

恢复后，本地旧状态仍然可能显示“尚未退款”。如果 Agent 只根据本地状态直接再执行一次，就可能产生重复副作用。

因此权威状态不只是“存一个字段”的问题，还必须和幂等键、外部查询、事件记录、Checkpoint 以及恢复策略配合。这些机制会在后续笔记中展开。

## 与相邻概念的边界

| 概念 | 本篇中的责任 |
|---|---|
| Goal | 定义最终要实现什么；不等于当前运行进度 |
| Run State | 记录这次执行当前进行到哪里 |
| Event | 记录某件事曾经发生；后续将与 Snapshot 对比 |
| Observation | 把环境反馈变成 Agent 可用的任务信息 |
| Context | 本次 Model Call 实际收到的 Token；只是状态的选择性表示 |
| Persistence | 让需要的状态和事件跨调用、跨 Turn 或跨重启保留 |
| Acceptance | 按成功条件判断 Goal 是否真正满足 |

## 常见误解

### 误解一：保存完整对话就等于保存了状态

对话保存了交互内容，但不保证能稳定查询 Run 状态、待处理副作用、预算和状态版本。

### 误解二：Agent 自己的数据库就是所有事实的权威来源

Agent 数据库可以权威地管理 Run，但文件、支付、邮件和其他外部业务事实仍由相应环境拥有。

### 误解三：模型说“完成”后就可以直接写成 completed

模型声明只是 Completion Request。Runtime 还要根据真实产物、验证结果和当前规则决定是否进入验收或继续修复。

### 误解四：尽可能多地持久化信息一定更可靠

保存过多失效推测和重复信息，可能产生冲突与错误恢复。持久化设计要先说明所有者、权威来源、生命周期和可否重建。

## 理解检查

1. 模型返回“工具执行成功”，但 Runtime 没有收到工具结果。Run 状态应该怎样处理？
2. Agent 数据库记录某文件的内容为 A，当前工作区中文件内容为 B。对于“文件现在是什么”，应优先使用哪一份？
3. 为什么记录状态版本号仍不能代替外部现实核对？
4. 为什么 Run 的 `completion_requested` 与 `accepted` 应当分开？

<details>
<summary>参考答案</summary>

1. 不应记录为工具已成功。应保留为待执行、执行结果未知或失败，再根据工具的可查询性和幂等性决定重试或核对。
2. 当前文件系统中的 B；Agent 数据库的 A 可保留为过去记录，并触发状态重新核对。
3. 版本号只能帮助发现本地状态之间的并发写入冲突，不能证明外部环境没有发生变化。
4. 前者只表示模型或执行器申请结束，后者表示指定的验收方已根据成功条件接受结果。

</details>

## 本篇停止点

如果你能解释下面三句话，就已经掌握了本篇的基础机制：

1. 模型输出只是动作或状态变更建议；
2. Runtime 根据真实工具结果和合法转换更新 Run State；
3. 不同事实可能由不同系统拥有权威，恢复时必须与当前现实核对。

下一步可以继续学习 Snapshot 与 Event Log，回答“当前状态和历史过程应该怎样同时保存”。
