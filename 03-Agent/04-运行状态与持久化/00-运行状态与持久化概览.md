# 运行状态与持久化概览

> [!summary]
> 运行状态是 Agent 对“任务现在进行到哪里”的结构化记录；持久化则让这些记录在下一轮模型调用、上下文压缩或进程重启后仍然能够恢复。

## 本专题的两层边界

### Agent 基础结构

程序在内存中知道当前请求、最新 Tool Result 和是否继续，就已经拥有最小运行状态；它不一定能跨进程或跨 Turn 恢复。

### 持续与高可靠理想结构（选读）

持久 Run、Snapshot、Event Log、Checkpoint、版本冲突、权威状态核对和审计用于长任务、可恢复任务与高风险副作用。

## Agent 基础结构中的位置

```text
当前用户请求
→ 程序在内存中记录当前消息、步骤数和最新 Tool Result
→ 组装下一次模型输入
→ 模型决策与工具执行
→ 更新这些临时变量
→ 继续或停止
```

最小状态甚至可以只是消息数组、循环计数器和几个程序变量。Agent 每执行一步，都可能读取并更新它们。

## 持续与高可靠结构中的位置（选读）

```text
持久 Goal
→ 创建或恢复 Run 与版本化状态
→ 根据状态构建本轮上下文
→ 执行动作并记录 Event、Observation 与 Artifact
→ 原子更新 Snapshot
→ 支持跨 Turn、进程重启、核对与审计
```

## 先看一个最小状态

假设任务是“修复订单重复扣款”，一次运行可能记录：

```text
Goal：修复重复扣款，并保证正常支付不受影响
Run 状态：进行中
当前动作：检查支付回调处理
最近 Observation：并发测试发现第二次回调仍然扣款
已经完成：定位回调入口、增加第一版幂等校验
下一步：检查数据库事务边界
重试次数：1
```

这份记录回答的是“现在是什么情况”，而不是复述所有对话。

## 从简单到深入的三层状态

### 第一层：基础运行状态

最小或持续 Agent 首先需要：

```text
目标是什么
任务是否正在运行
当前做到哪一步
刚才发生了什么
下一步准备做什么
是否已经失败、等待或完成
还剩多少步骤、时间或费用预算
```

这一层足以支持基本循环、暂停和继续。

### 第二层：过程与事件记录

为了知道“为什么变成现在这样”，系统还会记录：

```text
用户输入
模型调用（Model Call）及其响应
Tool Call
工具返回结果
文件修改
错误、重试和取消
状态转换与时间
```

当前状态和事件历史不是同一件事：

```text
当前状态 Snapshot
= 现在的结果

事件记录 Event Log
= 事情怎样一步步发生
```

### 第三层：高可靠任务状态

高风险或长任务可以继续增加：

```text
正式 Scope 与成功条件
Goal Revision
Candidate 产物
Evidence 验证证据
Acceptance 验收结论
Provenance 信息来源
```

这些是高可靠控制能力，不是所有最小 Agent 都必须具备的对象。

## Codex CLI 可以怎样对应理解

以当前 Codex CLI 的公开结构为例：

```text
Thread
→ 一个持续的任务与对话容器

Turn 与 Item
→ 用户消息、模型响应、工具调用和执行事件

本地状态数据库
→ 保存 Thread 索引、运行元数据、工具关系等结构化状态

Rollout JSONL
→ 保存按时间追加的详细线程事件

持久 Goal
→ 保存 Objective、状态、预算和使用进度

工作区与 Git
→ 保存真实文件修改和版本状态
```

因此，Codex 的“能够恢复线程”不是只依赖聊天记录，也不是只依赖一个数据库；它需要把线程索引、详细事件和真实工作区重新组合起来。

## 先按生命周期区分状态

| 生命周期 | 典型内容 | 通常由谁保存 |
|---|---|---|
| 单次 Model Call | 当前 Prompt、流式响应片段 | Agent Runtime 临时持有 |
| 单次模型推理 | Hidden State、QKV、KV Cache | 模型 Runtime 临时持有 |
| 当前 Turn / Run | 工具 Future、取消信号、待处理动作、重试计数 | Agent Runtime 内存，可按需 Checkpoint |
| 跨 Turn 恢复 | 用户消息、Item、Goal、状态转换、工具结果 | JSONL、数据库或事件存储 |
| 项目真实产物 | 代码、Git 状态、测试报告、构建产物 | 文件系统、Git、Artifact 存储 |

持久化不是执行结束后的最后一步，而是贯穿运行过程：用户消息、工具调用、工具结果和状态转换可能在发生时就被追加记录；当前网络连接、工具 Future 和模型 Hidden State 则没有必要成为长期记录。

## 持久化不等于全部进入内嵌数据库

不同载体适合保存不同事实：

```text
数据库
→ 可查询的 Goal、Run、状态、索引和关系

Event Log / JSONL
→ 按时间追加的完整执行事件

文件系统与 Git
→ 代码、文档、版本和 Diff

Artifact Store
→ 测试报告、截图、日志包和构建结果

内存
→ 当前循环、连接、Future 和临时上下文
```

真正的设计问题不是“要不要使用 SQLite”，而是：

> 哪项事实必须跨进程恢复、由谁拥有、哪份记录具有权威性，以及怎样与工作区现实核对。

## 状态、上下文和记忆不是同一件事

```text
状态 State
→ Agent 当前真实进行到哪里

上下文 Context
→ 本轮实际发送给模型的 Token

工作记忆 Working Memory
→ 当前任务中以后可能再次取用的信息

长期记忆或持续学习
→ 跨任务保留和更新经验，属于后续模块
```

关系是：

```text
外部状态与事件记录
→ Context Builder 选择本轮相关部分
→ 形成模型上下文
→ 模型提出下一步
→ Runtime 校验并更新状态
```

本地保存了某条信息，不代表下一轮一定会把它完整发送给模型。

## 什么值得持久化

判断标准不是“信息是否出现过”，而是：

- 进程重启后是否还必须知道；
- 重复执行是否可能产生副作用；
- 后续决策是否依赖它；
- 是否需要审计或证明；
- 能否从工作区或外部系统安全地重新获得。

临时搜索提示、已经失效的猜测和可以廉价重建的中间文本，不一定都要成为权威状态。

## 谁能修改状态

模型可以提出：

```text
“把当前步骤标记为完成”
“任务已经满足目标”
```

但这只是 **Proposed State Change（状态变更建议）**。真正写入状态前，Agent Runtime 应检查：

- 当前状态是否允许这样转换；
- 工具是否真的执行成功；
- 是否已经取得需要的验证证据；
- 是否需要用户或独立验收器确认。

否则模型一句“已经完成”就可能直接改写系统事实。

## 持久化深度不是可靠性等级的同义词

```text
保存了完整对话
≠ 保存了明确任务状态

保存了任务状态
≠ 结果已经通过验证

能够恢复线程
≠ 能够从正确位置安全恢复业务动作
```

例如系统恢复后仍然要核对真实文件、Git、数据库或外部服务，不能只相信退出前的模型判断。

## 阅读路线

- **只看框架**：理解状态回答“现在进行到哪里”，持久化负责“以后还能恢复”；
- **理解机制**：区分当前状态、事件历史、模型上下文和工作区现实；
- **继续深入**：学习 Snapshot、Event Log、版本冲突和高可靠状态；
- **为搭建做准备**：先设计最小运行状态，再决定数据库和文件格式。
