# 控制循环与事件协议

> [!summary]
> Runtime 需要把模型输出转换成有限、可校验的事件类型，避免通过解析自然语言中的“我完成了”来改变系统状态。

> [!info] 两层边界
> **基础 Agent**只需可靠区分最终回答与 Tool Call，并校验工具名和参数。下面的完整事件集合、状态转换事件和 Completion Request 属于持续或高可靠控制协议。

## 一组说明性事件

```text
MESSAGE
TOOL_CALL_REQUEST
USER_INPUT_REQUEST
PLAN_PROPOSAL
COMPLETION_REQUEST
WORKER_FAILURE
```

具体系统可以使用不同名称，但未知类型必须显式拒绝或降级，不能随意猜测。

## 为什么普通文本不够

模型可能输出：

```text
测试已经通过，任务完成。
```

如果 Runtime 搜索“完成”两个字就关闭 Run，会遇到：

- 模型引用了一段旧日志；
- 文本只是假设；
- 测试并未真实执行；
- 句子出现在错误说明中；
- Prompt Injection 伪造完成标记。

## 事件需要绑定什么

至少应能追溯：

```text
runId
userTurnId（产品存在该对象时）
modelCallId
attemptId（需要时）
contextManifestId 或输入版本
eventId
eventType
payload
```

这样旧 Model Call 返回的结果不会悄悄推进已经改变的 Run。

## 严格处理顺序

```text
接收模型或适配器事件
→ 检查大小和格式
→ 按 Schema 解码
→ 检查身份和版本
→ 检查当前状态是否允许
→ 路由到对应处理器
→ 保存结果和审计事件
```

格式正确只是第一关。

## 流式输出怎样理解

流式 Token 或中间 Item 可以用于界面展示和观察，但不要把每个片段都当成权威状态变化。

```text
stream item
→ 运行观察

accepted typed event
→ 才可能触发受控处理
```

一次模型响应完成，不应自动产生 `Turn Completed`，更不应自动让外部 Run 进入 `COMPLETED`。只有 Agent Loop 不再需要继续动作并产生最终 Agent Message 时，用户 Turn 才结束；高可靠 Run 还可能继续进入独立验收。
