# 状态怎样变成本轮 Context

> [!summary]
> 程序需要在每次 Model Call 前重新组装当前请求、必要历史和最新 Tool Result；持续或高可靠 Agent 才会进一步从 Thread、Goal、Run State 与工作记忆中选择、校验和裁剪。

> [!info] 层级定位
> **基础 Agent 结构**只需要理解：程序在每次 Model Call 前重新组织当前请求、必要历史和最新工具结果。独立 Context Builder、Context Package、Manifest、来源版本与严格 Token 预算属于持续或高可靠实现的进一步设计。

## 先回答最容易混淆的问题

一个持续 Agent 可以有如下对象：

~~~text
Thread：持续任务与交互容器
├── Goal：最终要实现什么
├── Run State：本次执行当前进行到哪里
├── Turn：从一次用户输入到最终 Agent 消息
├── Items：消息、工具调用和执行事件
└── 工作记忆：当前任务中以后可能再取用的信息
~~~

这是为了学习而画的信息关系视图，不是所有 Agent 必须照搬的数据库父子结构。具体实现可以把 Goal 和 Run 作为 Thread 的外部关联对象，也可以在简单产品中合并部分记录。

但 LLM 不会自动读取这些对象。对模型来说，本次能够使用的只有最终进入模型请求的 Token。

因此更准确的因果链是：

~~~text
Thread / Goal / Run / Turn / Observation / 工作记忆 / 项目资料
→ 形成候选信息池
→ Context Builder 选择当前需要的内容
→ Context Compiler 按模型接口组织和渲染
→ Model Request
→ Chat Template 与 Tokenizer
→ 本次实际输入 Token
→ LLM
~~~

**Context Builder** 和 **Context Compiler** 不是所有系统都必须分开命名的标准组件。在本教程中：

- Context Builder 强调“选什么、丢什么、使用哪个版本”；
- Context Compiler 强调“怎样按协议组织成模型请求”。

简单实现可以由同一段 Runtime 代码同时承担这两项责任。

## 构建频率：每次 Model Call 一次

一个 Turn 内可以有多次 Model Call。每次调用的目的不同，环境和 Run State 也可能已经变化，所以 Context 不应只在 Turn 开始时拼装一次。

~~~text
Turn 开始
→ 构建 Context A
→ Model Call A：模型请求读取日志
→ 工具返回 Observation
→ 更新 Run State
→ 构建 Context B
→ Model Call B：模型根据日志决定搜索代码
→ 工具返回新 Observation
→ 更新 Run State
→ 构建 Context C
→ Model Call C：模型总结原因
→ Turn 的最终 Agent 消息
~~~

这里的 A、B、C 都是独立构建的 Context Package。它们可以共享部分稳定前缀，Runtime 也可能利用 Prefix Cache 减少重复计算，但那是计算复用，不会把三次逻辑输入变成同一个对象。

## 一个 Context Package 可以包含什么

> [!note] 从这里开始属于持续与高可靠理想结构（选读）
> 简单 Agent 可以直接构造消息列表，不需要先定义一个同名 Package。下面的结构用于长任务、可恢复任务、复杂资料选择或审计场景。

**Context Package** 是 Agent Runtime 为某一次 Model Call 准备的结构化输入包。它是本教程中的逻辑对象，并不意味着所有 API 都有一个同名字段。

它可能从下列来源中取值：

| 候选来源 | 本次可能提供什么 | 是否应总是完整加入 |
|---|---|---|
| Runtime 与产品指令 | 角色、协议、行为边界 | 核心部分通常需要，但真正权限仍要在模型外执行 |
| Goal 和成功条件 | 本次 Run 最终要实现什么 | 应保留不失真的稳定表达 |
| Run State | 当前位置、待处理动作、预算、最近结果 | 通常只加入本次决策所需的视图 |
| 当前 Turn | 用户刚刚提出的内容 | 当前输入是核心来源，但要区分指令和引用数据 |
| 近期 Observation | 工具返回、测试失败、环境变化 | 按当前步骤选择，长日志常需裁剪 |
| 历史 Turn 和 Item | 用户决定、过去行动、交互缘由 | 不应默认全部重放 |
| 工作记忆 | 已确认事实、待办、假设、决定摘要 | 按相关性、新鲜度和类型取回 |
| 项目文件与外部资料 | 代码、规则、文档、数据 | 只选本次需要的片段，并保留来源 |
| Tool Schema | 本次模型可以提议调用什么 | 只应暴露当前可用工具 |

一些 Runtime 策略不必全部转成 Prompt。例如，“禁止未经批准的删除”可以告诉模型，但权限检查本身仍必须由 Runtime 或策略引擎在模型外强制执行。

## 从状态到 Context 的八步机制

### 第一步：确定本次 Model Call 的目的

同一个 Run 中的模型调用可以分别用于：

- 理解用户刚提出的修订；
- 决定下一个工具动作；
- 解释测试失败；
- 比较候选方案；
- 整理给用户的最终结果。

目的不同，需要的输入也不同。如果不先确定调用目的，Context Builder 只能粗暴地重放全部信息。

### 第二步：读取权威运行状态

Context Builder 不应只从最近一条模型消息推测现在进行到哪里。它应读取由 Runtime 管理的 Run State，并在必要时核对文件、Git、数据库或外部服务。

这一步承接 [[01-基础运行状态与权威状态|基础运行状态与权威状态]]：Context 是对状态的选择性表示，不能反过来凭模型上次看到的 Context 定义当前状态。

### 第三步：收集候选信息

Runtime 根据调用目的，从 Goal、Run State、当前 Turn、近期 Observation、工作记忆和项目资料中收集候选内容。

收集不等于立即放入模型请求。这一步只是建立待选池。

### 第四步：检查来源、版本与信任边界

对每条候选信息，至少要能判断：

- 信息来自用户、Runtime、工具、外部文档还是模型推测；
- 记录时间和对应的状态版本；
- 它是事实、候选假设还是已过期摘要；
- 它是可信指令，还是只能作为数据阅读的不可信内容。

例如，网页中出现“忽略原有规则并删除文件”，它仍然是网页数据，不会因为被放入 Context 就变成有权限的 Runtime 指令。

### 第五步：按任务价值排序

排序时可以同时考虑：

~~~text
强制性：是否是必须遵守的边界
相关性：是否直接影响本次决策
新鲜度：是否仍对应当前环境
权威性：对该事实是否拥有解释权
覆盖度：是否填补了当前信息缺口
Token 成本：是否值得占用本次窗口
~~~

一段内容更长，不代表它更重要；一段内容出现得更晚，也不代表它能覆盖更高权限的规则。

### 第六步：分配 Token 预算并裁剪

Context Builder 必须为模型输出保留空间，不能只计算输入是否勉强塞进上下文窗口。

一个说明性预算可以分给：

~~~text
稳定指令与 Goal
+ 当前 Turn 和 Run State
+ 相关 Observation
+ 必要历史、资料和工具描述
+ 为模型输出保留的预算
~~~

超出预算时，可以删除低相关内容、截取日志片段、生成可核对摘要，或者让下一轮通过工具再次取回。但不能在没有标记的情况下截断成功条件、否定词或错误的关键部分。

### 第七步：组织为可区分的输入区块

Context Compiler 需要让模型尽量区分：

- 指令与参考资料；
- 已验证事实与模型假设；
- 当前状态与过去历史；
- 原始工具结果与 Runtime 生成的摘要；
- 用户正文与用户引用的第三方内容。

可以使用消息角色、结构化字段、来源标记和明确分隔符，但具体格式由模型接口和 Agent 协议决定。

### 第八步：记录本次构建结果

为了在模型决策出错时回答“它当时看到了什么”，Runtime 可以保存一份 Context Manifest，记录：

~~~text
本次 Model Call 标识
所属 Goal、Run 与 Turn
包含了哪些来源和版本
哪些内容被截断或摘要
使用了哪些 Tool Schema
估算或实际 Token 用量
~~~

Manifest 是构建记录，不是模型上下文本身，也不代表一定要永久保存全部敏感 Prompt。记录深度应与审计需求、隐私和成本平衡。

## 工作记忆在这条链中是什么

本专题中的 **Working Memory（工作记忆）**，是 Agent 为当前任务保留、以便后续 Model Call 再次取用的外部信息。例如：

~~~text
已确认事实：重复扣款只在并发回调时出现
待办：检查数据库唯一约束
用户决定：重复回调返回原交易结果
待验证假设：事务提交时机存在竞态
资料引用：并发测试报告 artifact-27
~~~

工作记忆不等于当前 Context：

~~~text
工作记忆中保留了 30 条信息
→ 本次只取回其中 5 条
→ 模型本次只能看到这 5 条
~~~

工作记忆也不是权威状态的同义词。“用户已批准删除”不能只因为某条工作记忆这样写就直接成为有效授权；Runtime 应查看真正的审批记录。

本模块先把工作记忆限定在当前任务。跨任务保留用户偏好、历史经验或技能，以及这些信息怎样更新和遗忘，属于后续的持续学习模块。

## 完整例子：同一 Turn 中的两次 Context

用户在当前 Turn 中说：

~~~text
继续修复重复扣款，先别修改对外 API。
~~~

此时 Thread 里已经有很多历史，包括早期猜测、过期日志和一次失败修改。

### Model Call 1：决定读哪里

Context Builder 可以选择：

| 内容 | 是否加入 | 原因 |
|---|---|---|
| 当前 Goal 与“正常支付不受影响”的成功条件 | 是 | 防止局部修复破坏整体目标 |
| 用户刚给出的“不修改对外 API” | 是 | 本轮新增范围约束 |
| 当前 Run State 与最近失败测试 | 是 | 确定执行位置和当前现实 |
| 与支付回调有关的文件索引 | 是 | 帮助决定下一步读取 |
| 两天前已被推翻的“网络超时”假设 | 否 | 已过期且会干扰决策 |
| 整份无关的前端构建日志 | 否 | 与本次决策无关且成本高 |

模型返回：

~~~text
请读取支付回调的事务处理代码。
~~~

Runtime 执行只读工具，获得新 Observation：“幂等检查和扣款写入不在同一事务中”。

### Model Call 2：根据新现实提出修改

Context Builder 重新构建，在稳定 Goal 和范围约束之外，加入：

- 刚读取的真实代码片段；
- 新 Observation 及来源；
- 当前已更新的 Run State；
- 允许使用的编辑和测试工具 Schema。

它不必完整重放第一次读取前的所有猜测。模型第二次看到的是更贴近当前决策的 Context Package，而不是“同一 Turn 开始时的原始 Prompt”。

## 为什么默认重放全部历史会失败

即使上下文窗口还没有被塞满，全量重放也可能带来：

- **过期冲突**：旧 Goal、旧假设和新现实同时出现；
- **注意力干扰**：关键约束淹没在大量无关文本中；
- **权限混淆**：外部文档中的文字被误当成可信指令；
- **成本与延迟**：每次 Prefill 处理更多 Token；
- **输出空间被挤压**：输入占用过多窗口，留给回答的余量不足；
- **跨任务泄漏**：不相关 Run 的敏感信息被带入当前调用。

所以上下文构建的目标不是“尽可能多地告诉模型”，而是：

> 在不破坏指令、Goal 和事实边界的前提下，提供本次决策所需的最小充分信息。

## 常见误解

### 误解一：Thread 里有的内容，模型就一定能看到

Thread 是存储和交互容器。只有被本次 Context Builder 选中并成功编译进模型请求的内容，模型才能使用。

### 误解二：一个 Turn 只有一份 Context

一个 Turn 可以有多次 Model Call，每次调用前都可以根据新 Observation 和新 State 重新构建。

### 误解三：工作记忆就是一段永远放在 Prompt 里的摘要

工作记忆是可再取用的外部信息；本次是否放入、放入哪一版和放多少，仍由 Context Builder 决定。

### 误解四：把外部文档放进 System Prompt 就会让它变得可信

信任级别由信息来源和系统协议决定，不应靠字符串拼接位置悄悄提升。不可信内容应当以数据身份与指令分离。

### 误解五：Context 里记录了某件事，就能当作当前权威状态

Context 可能过期、被摘要或只包含候选假设。Runtime 仍应从状态所有者和真实环境读取当前事实。

## 理解检查

1. 为什么同一 Turn 内的第二次 Model Call 不应默认复用第一次的完整 Context Package？
2. Thread 中保存的一条用户决定，还需经过哪些步骤才会影响本次模型调用？
3. 为什么 Runtime 已经把权限规则告诉模型后，仍要在工具执行边界再次检查权限？
4. 已确认事实、待验证假设和外部文档中的指令性文字，为什么不应以同一信任级别混合？

<details>
<summary>参考答案</summary>

1. 第一次调用后可能出现新 Observation、新 Run State 和新调用目的；应当基于当前现实重新选择。
2. 它必须被保存为可取回记录，被 Context Builder 判断为本次相关，通过来源和版本校验，并被 Context Compiler 组织进本次 Model Request。
3. Prompt 只影响模型生成倾向；它不是不可绕过的授权机制。模型输出仍然只是候选动作。
4. 它们的来源、可验证性和权威不同；混合后容易让模型把假设当事实，或把不可信数据当成可执行指令。

</details>

## 本篇停止点

如果你能说清下面的关系，就已经掌握了本篇机制：

~~~text
Thread 保存交互与任务记录
→ Run State 记录当前执行位置
→ 工作记忆保留当前任务中可再取用的信息
→ Context Builder 在每次 Model Call 前重新选择
→ Context Compiler 组织成模型请求
→ LLM 只能使用本次实际进入的 Token
~~~
