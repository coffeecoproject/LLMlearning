# Retrieval、摘要与 Compaction

> [!summary]
> Retrieval 负责从外部信息中找回当前相关部分，摘要负责把选定内容变短，Compaction 负责重组不断增长的上下文；三者都可能丢失信息，因此必须保留来源、版本和重新取回原文的路径。

> [!info] 层级定位
> **基础 Agent**可以只保留近期消息和最新 Tool Result。只有当历史变长、资料无法一次放入窗口或任务需要跨 Turn 持续时，Retrieval、摘要与 Compaction 才成为常见工程增强；严格来源和转换审计属于更高可靠层。

## 四个相邻概念先分开

| 概念 | 核心动作 | 主要风险 |
|---|---|---|
| Retrieval（检索） | 从外部集合中选择相关记录或片段 | 漏掉真正需要的信息 |
| Summary（摘要） | 把一段内容压缩成更短表达 | 遗漏、误写或抹平不确定性 |
| Compaction（上下文压缩整理） | 对累积上下文做删除、摘要、引用替换和重组 | 关键约束在多轮整理中逐渐失真 |
| Truncation（截断） | 超出预算时机械删除部分 Token 或消息 | 不理解语义地切掉关键内容 |

它们可以组合，但不能互相替代。

例如：

~~~text
从 200 条历史事件中检索 12 条
→ 将其中 8 条重复日志摘要为 1 条
→ 保留 4 条原始关键事件
→ 用引用替换完整测试报告
→ 得到压缩后的 Context Package
~~~

这是 Retrieval、摘要与 Compaction 共同工作，不是单纯从左侧删掉旧消息。

## Retrieval：需要时再取回

Retrieval 的候选来源可以包括：

- Thread 中的历史 Turn 和 Item；
- Run Event Log；
- 工作记忆；
- 文件、代码索引和项目文档；
- Artifact Store 中的测试报告与截图；
- 远端业务系统中的当前记录。

常见检索线索包括：

~~~text
对象标识：goal_id、run_id、file_path、artifact_id
结构化元数据：类型、状态、时间、版本、作者
关键词：支付回调、并发、唯一约束
语义相似度：寻找含义接近的记录
关系：某 Observation 属于哪个 Step 或 Candidate
~~~

对权限、状态和当前文件等关键事实，应优先使用精确标识、结构化查询或权威系统读取。语义相似度适合帮助发现相关资料，但不应独自决定授权是否存在。

## Retrieval 不是“搜索到就直接塞进 Context”

取回结果还要经过：

1. 是否属于当前 Goal 和 Run；
2. 是否有权读取；
3. 来源是否可信；
4. 版本是否仍然有效；
5. 是否与当前状态冲突；
6. 本次是否值得占用 Token；
7. 是否需要只保留片段或引用。

检索系统返回“相关度 0.92”只说明匹配算法认为文本相近，不证明内容真实、最新或有权限。

## 摘要：有损的表示转换

摘要不是原文的等价副本。下面原始记录：

~~~text
并发测试共运行 100 次：
98 次通过；
第 37 次和第 81 次出现第二次扣款；
正常支付测试全部通过；
测试环境数据库隔离级别为 READ COMMITTED。
~~~

如果摘要成：

~~~text
支付测试基本通过。
~~~

虽然更短，却丢失了最重要的失败事实。

更可靠的任务摘要可以写成：

~~~text
并发测试 100 次中有 2 次重复扣款，成功条件尚未满足；
正常支付测试通过；
结果来自 report-27，环境隔离级别为 READ COMMITTED。
~~~

好的摘要应尽量保留：

- 对 Goal 和成功条件有决定作用的结果；
- 否定、失败、例外和不确定性；
- 数量、版本和时间等关键限定；
- 来源引用；
- 尚未解决的冲突；
- 下一步仍需要原文核对的部分。

## 哪些内容不适合只保留摘要

以下信息通常需要保留原始记录或可访问引用：

- 用户批准与撤销；
- 精确成功条件和 Scope；
- 有副作用工具的请求与结果；
- 代码 Diff；
- 测试失败的关键原始输出；
- 法律、合规或审计要求的原文；
- Evidence 和 Acceptance 结论；
- 任何摘要后可能改变行动含义的否定或数字。

这不代表每次都要把原文全部送入模型。可以在外部持久化原文，Context 中加入相关片段和引用。

## Compaction：重新组织不断增长的上下文

随着 Turn、Tool Call 和 Observation 增加，Context 候选池会不断膨胀。Compaction 可以采用：

~~~text
保留稳定 Goal、关键规则和当前状态
→ 移除重复和已失效消息
→ 把已结束阶段压缩为可核对摘要
→ 将大型产物替换成引用
→ 保留当前阶段的原始 Observation
→ 为输出和后续工具结果留出预算
~~~

Compaction 可以在达到窗口上限之前触发。即使窗口还有空间，也可能因为以下原因提前整理：

- 减少注意力干扰；
- 降低 Prefill 成本和延迟；
- 删除过期假设；
- 隔离不再需要的敏感信息；
- 给新的工具结果和输出留出稳定余量。

## 一条可靠的 Compaction 流程

### 第一步：保护不可丢失内容

先标记：

- 当前有效指令；
- Goal、成功条件、Scope 与 revision；
- 当前 Run State；
- 待处理审批和未知副作用；
- 关键失败与冲突；
- 用户尚未回答的问题。

### 第二步：按信息类型选择策略

~~~text
稳定规则
→ 保留当前有效版本

重复对话
→ 合并为决定摘要

长日志
→ 保留关键片段、统计和原始引用

过期假设
→ 删除或标记失效

已结束阶段
→ 形成带来源的阶段摘要

大型产物
→ 保存外部 Artifact 引用
~~~

### 第三步：验证摘要

至少检查：

- 是否保留所有未满足的成功条件；
- 是否把失败误写成成功；
- 是否遗漏用户限制；
- 是否区分事实和假设；
- 引用是否仍可访问；
- 摘要对应哪个状态版本。

高风险任务可以使用确定性字段检查、第二个验证步骤或人工复核；不能只让生成摘要的同一次模型调用直接批准自己。

### 第四步：记录转换

Context Manifest 应记录：

~~~text
哪些原始记录被替换
使用了哪个摘要
摘要对应的来源和版本
哪些内容被删除
为什么删除
是否可以重新取回
~~~

## 多次摘要为什么会逐渐失真

如果每次都只摘要上一次摘要：

~~~text
原始事件
→ 摘要 A
→ 摘要 B
→ 摘要 C
~~~

细节可能像反复压缩图片一样逐渐消失。更稳妥的方式是：

~~~text
摘要保留原始来源引用
→ 关键决策时重新读取原始事件
→ 用当前状态重新生成或校验摘要
~~~

摘要是导航和压缩工具，不应变成不可追溯的新权威真相。

## Retrieval 与 Compaction 怎样配合

压缩后的 Context 不需要永久携带所有细节，只要保留可恢复路径：

~~~text
当前摘要：并发测试仍有 2 次重复扣款
来源：artifact-27
相关文件：payment_callback.go@version-18
必要时：通过只读工具重新读取报告和代码
~~~

下一次需要分析失败细节时，Retrieval 再取回对应片段。

这形成：

~~~text
外部原始记录
↔ 可检索索引
↔ 当前工作记忆或摘要
→ 本次 Context
~~~

## 一个完整例子

某 Run 已经历 15 次工具调用，历史中包含：

- 6 次代码搜索；
- 3 次文件读取；
- 2 次失败修改；
- 3 份测试报告；
- 1 次用户范围修订。

为下一次“决定是否申请完成”的 Model Call，Context Builder 不应重放全部过程。它可以：

1. 保留当前 Goal、成功条件和用户最新 revision；
2. 从 Run State 读取当前 Candidate；
3. 检索最新代码 Diff 和三份测试报告；
4. 保留最新报告的关键原始结果；
5. 把早期搜索过程压缩成“定位路径”的阶段摘要；
6. 删除已经推翻的两个旧假设；
7. 引用完整日志，而不全部内联；
8. 记录本次裁剪和摘要来源。

如果最新报告仍有失败，就不能因为阶段摘要写着“修复接近完成”而进入 Acceptance。

## 常见误解

### 误解一：向量检索最相似的内容就是最正确的内容

相似度不是权威性、权限或新鲜度。关键事实仍要核对来源。

### 误解二：摘要只是缩短文字，不改变含义

摘要是有损转换，可能丢掉失败、否定、数字和条件。

### 误解三：Compaction 只在窗口满时才需要

注意力干扰、成本、隐私和新旧冲突都可能让提前整理更合理。

### 误解四：旧内容已经摘要，所以可以删除所有原始记录

高价值事实、审批、Evidence 和副作用结果通常需要保留原始记录或可验证引用。

### 误解五：机械 Truncation 可以代替 Context Builder

Truncation 只按长度删除；它不知道 Goal、权限、来源和任务价值。
