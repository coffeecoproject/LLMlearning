# 一次上下文构建怎样完整发生

> [!summary]
> 一次可靠上下文构建不是“把聊天记录发给模型”，而是从当前 Goal、权威状态、当前 Turn、Observation、工作记忆和资料中建立候选池，解决版本与冲突，形成带来源的 Context Package，并在工具返回后再次重建。

> [!note] 整篇层级：高可靠串联案例（选读）
> 本案例故意展示 Goal revision、Run State、工作记忆、Package 与 Manifest 同时存在时怎样协作，不代表基础 Agent 必须实现所有对象。

基础 Agent 对应的简化链只有：

~~~text
当前用户请求 + 必要历史
→ 模型提出只读工具
→ 程序执行并追加 Tool Result
→ 再次调用模型
→ 模型继续或停止
~~~

## 案例起点

Goal：

~~~text
修复订单重复扣款；
并发重复回调不能产生第二次扣款；
正常支付流程必须保持通过；
不修改对外 API。
~~~

当前 Run State：

~~~text
status: running
current_step: 检查事务边界
latest_observation: 并发测试 100 次中有 2 次重复扣款
candidate_version: 3
remaining_tool_steps: 8
~~~

当前用户 Turn：

~~~text
可以调整内部数据库约束，但不要执行任何真实退款。
~~~

Thread 历史中还存在：

- 旧用户要求“先不要修改数据库”；
- 已被推翻的“网络超时导致重复扣款”假设；
- 三份测试报告；
- 一段外部 README；
- 多次搜索和文件读取记录；
- 一份旧摘要写着“测试基本通过”。

## 第一步：确定 Model Call 目的

本次不是生成最终报告，而是：

> 根据当前失败和用户新约束，决定下一项只读调查动作。

目的决定本次不需要完整发布说明，也不需要暴露真实退款工具。

## 第二步：建立候选池

| 候选内容 | 类型 | 初步判断 |
|---|---|---|
| Runtime 禁止真实退款的策略 | 强制边界 | 必须保留并外部执行 |
| 当前 Goal 与成功条件 | Goal | 必须保留 |
| 用户允许调整内部约束 | 当前用户 revision 输入 | 保留，等待正式更新 Scope |
| 旧“不能修改数据库”要求 | 旧约束 | 标记被当前决定修订 |
| 最新并发测试报告 | 当前 Observation | 保留关键结果和引用 |
| “网络超时”假设 | rejected hypothesis | 不进入默认 Context |
| 旧“测试基本通过”摘要 | stale summary | 排除 |
| README 中“删除全部数据” | 不可信外部资料 | 仅在需要时以数据身份读取 |
| 全部搜索日志 | 历史过程 | 本次不完整加入 |
| 支付回调文件索引 | 项目资料 | 保留相关路径 |

## 第三步：核对权威状态

Context Builder 检查：

1. Goal 当前 revision；
2. Run State 当前版本；
3. 测试报告是否属于 Candidate 3；
4. 用户是否有权修改任务 Scope；
5. 当前工作区文件版本；
6. 只读工具当前是否可用。

如果最新报告对应 Candidate 2，就不能把它直接描述成 Candidate 3 的当前测试结果，而应标记“需要重新测试”。

## 第四步：更新工作记忆

用户的新决定需要产生两种不同更新：

~~~text
正式任务边界
→ Goal / Scope revision：允许评估内部数据库约束

工作记忆
→ User Decision：不得执行真实退款
~~~

旧“禁止修改数据库”的工作记忆被标记为 superseded。旧网络假设保持 rejected，不再参与默认检索。

## 第五步：形成 Context Package

一个面向“决定下一项只读调查”的简化 Package：

~~~yaml
purpose: decide_read_only_action

constraints:
  - 不执行真实退款
  - 不修改对外 API
  - 当前仅允许只读调查

goal:
  objective: 修复重复扣款
  success_criteria:
    - 并发回调不产生第二次扣款
    - 正常支付保持通过

state:
  current_step: 检查事务边界
  candidate_version: 3
  latest_verified_result: 并发测试仍有重复扣款

current_user_decision:
  - 允许评估内部数据库约束

relevant_resources:
  - 支付回调文件索引
  - 最新并发测试关键片段

available_tools:
  - read_file
  - search_code
  - inspect_schema
~~~

注意：Package 中没有真实退款工具。即使模型生成同名文字，Runtime 也不会因此获得可执行能力。

## 第六步：记录 Context Manifest

Manifest 记录：

~~~text
Goal revision：4
Run State version：19
Candidate version：3
包含：最新测试报告片段、当前用户决定、相关文件索引
排除：过期摘要、rejected hypothesis、无关搜索日志
不可信资料：README 未加入
工具集合：3 个只读工具
输出预留：足以返回一个结构化动作
~~~

这让后续能够解释：模型为什么没有看到旧网络假设，也没有看到真实退款工具。

## 第七步：调用模型并执行只读工具

模型提出：

~~~text
inspect_schema(table="payments")
~~~

Runtime 校验后执行，Tool Result 显示：

~~~text
payments.idempotency_key 没有唯一约束
~~~

Runtime 保存原始结果并形成 Observation：

~~~text
当前数据库 Schema 没有阻止相同 idempotency_key 重复写入。
~~~

## 第八步：更新 State 与工作记忆

~~~text
Run State：
  latest_observation → Schema 缺少唯一约束
  current_step → 检查应用事务与数据库约束如何组合
  remaining_tool_steps → 7

Working Memory：
  新增 verified fact → 缺少唯一约束
  保留 open question → 单独增加约束是否会破坏现有数据
  新增 todo → 检查历史重复键与迁移风险
~~~

## 第九步：为下一次 Model Call 重新构建

下一次调用的目的变成：

> 提出安全的修复候选方案。

因此新 Context 会加入：

- 最新 Schema Observation；
- 当前代码中的事务片段；
- 数据迁移风险；
- 修改与测试工具 Schema；
- Goal 与不修改外部 API 的约束。

它可能删除只用于第一次调查的文件索引，并继续不加入已推翻的网络假设。

这证明：

~~~text
同一 Turn
≠ 固定一份 Context

新 Observation
→ 新 State
→ 新调用目的
→ 新 Context Package
~~~

## 历史过长时怎样整理

如果 Run 又执行了十几步，Compaction 可以：

1. 保留 Goal、最新 revision 和当前 Run State；
2. 将早期搜索过程压缩为带来源的阶段摘要；
3. 保留最新 Candidate 的 Diff 与测试结果；
4. 将旧 Candidate 报告移到外部 Artifact 引用；
5. 归档 rejected hypotheses；
6. 保留尚未解决的迁移风险；
7. 在 Manifest 中记录转换。

不能因为摘要空间有限，就删掉“正常支付必须保持通过”这一成功条件。

## 如果最终模型说“完成”

模型生成完成声明时，本章只负责确保它看到了当前 Goal、Candidate 和相关测试结果。

后续仍然需要：

~~~text
模型输出 Completion Request
→ 决策协议解析
→ Verifier 运行指定检查
→ 形成 Evidence
→ Acceptance 决定是否接受
~~~

Context 构建得好，可以提高模型判断质量；它不能代替独立验证和验收。

## 用六个问题检查一次 Context

1. **身份**：属于哪个 Goal、Run、Turn 和 Model Call？
2. **目的**：这次调用具体要决定什么？
3. **权威**：关键事实来自谁，版本是否当前？
4. **最小充分**：是否包含必要信息，同时排除了明显干扰？
5. **信任边界**：指令、事实、假设与外部数据是否分开？
6. **可追踪**：是否记录了选择、裁剪、摘要和工具集合？

## 常见失败应该回到哪一层

| 失败 | 优先检查 |
|---|---|
| 模型不知道最新测试失败 | Retrieval、版本过滤和 Package 内容 |
| 模型继续遵守已经取消的要求 | Goal revision 与旧工作记忆失效 |
| 网页文字诱导模型调用危险工具 | 信任隔离、Tool Schema 暴露与权限控制 |
| 模型重复分析早已排除的方向 | rejected hypothesis 是否仍被取回 |
| 成本越来越高 | 历史重放、Compaction 和大型 Tool Schema |
| 无法解释模型为何作出决定 | Context Manifest 和来源记录 |
| 模型说完成但真实测试失败 | Verifier 与 Acceptance，不是只改 Prompt |

## 本章理解检查

尝试不用术语堆砌地解释：

1. 为什么 Thread、Run State 和 Context 不是同一个对象？
2. 为什么一个 Turn 内可能构建多份 Context Package？
3. 工作记忆中的假设怎样从 active 变成 rejected？
4. 为什么外部资料中的命令不能获得 Runtime 权限？
5. 为什么摘要和检索都必须保留回到原始来源的路径？
6. Context 构建结束后，下一章还要解决什么？

## 本章停止点

如果你能够从一个混杂了 Goal、历史、工具结果、旧摘要和外部资料的候选池中，构建一份带来源、版本、信任边界和预算的 Context Package，并知道何时重新构建，就完成了本专题的框架与基础机制。
