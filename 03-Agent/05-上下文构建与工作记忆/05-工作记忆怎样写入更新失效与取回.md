# 工作记忆怎样写入、更新、失效与取回

> [!summary]
> 工作记忆是当前任务中可再次取用的外部信息集合；可靠实现不仅要保存内容，还要保存类型、来源、适用范围、版本和失效条件，并在每次取回后重新判断是否仍然可用。

> [!note] 整篇层级：持续 Agent 与高可靠结构（选读）
> 最小 Agent 可以只依赖当前消息列表和短期摘要。独立工作记忆、Memory Manager、类型化记录、版本与失效传播主要服务于长任务、跨 Turn 恢复和复杂上下文治理。

## 工作记忆为什么存在

一个 Run 可能经历多次 Model Call、工具执行和用户 Turn。如果每次都重新阅读全部历史，成本高且容易受到过期信息干扰。

工作记忆可以保留：

~~~text
已经确认的重要事实
用户做出的任务决定
当前待办和开放问题
尚未验证的假设
关键 Artifact 与 Observation 引用
已经排除的方向
~~~

它提供的是当前任务中的可再取用信息，不是模型参数中的永久记忆。

## 工作记忆不是一个自由文本记事本

如果只保存：

~~~text
支付问题应该已经解决，接着测试一下。
~~~

后续很难判断：

- “应该已经解决”是事实还是猜测；
- 根据哪次修改得出；
- 对应哪个文件版本；
- 哪些测试仍未执行；
- 这条记录是否已经过期。

因此一条工作记忆至少应表达：

~~~yaml
memory_id: memory-14
run_id: run-4
type: hypothesis
content: 事务边界可能导致并发重复扣款
source_refs:
  - obs-41
status: active
created_at: 2026-08-04T11:00:00+08:00
valid_for:
  code_version: commit-or-worktree-version-18
invalidation:
  - transaction_code_changed
~~~

这是说明性结构，不是统一 Schema。

## 六种常见工作记忆

| 类型 | 例子 | 典型变化 |
|---|---|---|
| Verified Fact | 并发测试 100 次中有 2 次重复扣款 | 新版本测试后重新核对 |
| User Decision | 不修改对外 API | 用户明确 revision 后失效 |
| Todo | 检查数据库唯一约束 | 完成、取消或被新计划替代 |
| Hypothesis | 事务边界存在竞态 | 被验证、推翻或过期 |
| Open Question | 重复回调应返回什么响应 | 用户回答后关闭 |
| Artifact Reference | 测试报告 artifact-27 | 新 Candidate 或新报告出现后更新 |

把类型分开很重要。Hypothesis 不能因为被保存得很久就自动升级为 Verified Fact。

## 谁可以提出写入，谁负责真正写入

模型可以提出：

~~~text
请记住：问题可能位于事务边界。
~~~

这仍然只是 **Memory Write Proposal（工作记忆写入建议）**。Runtime 应检查：

- 是否与当前 Goal 和 Run 有关；
- 应归类为事实、假设、决定还是待办；
- 是否有来源；
- 是否包含敏感信息；
- 是否已经存在等价或冲突记录；
- 应绑定哪个状态或 Artifact 版本；
- 是否需要用户确认。

真正的写入由 Runtime 或专门的 Memory Manager 完成。

## 哪些时机适合写入

### 获得关键 Observation 后

~~~text
测试报告显示并发情况下仍重复扣款
→ 写入带报告引用的 Verified Fact
~~~

### 用户作出影响后续执行的决定后

~~~text
用户确认“不修改对外 API”
→ 写入 User Decision
→ 同时检查是否需要形成 Goal revision
~~~

工作记忆可以帮助后续取回，但正式 Goal 约束仍应由 Goal 所有者更新，不能只存在 Memory 中。

### 阶段切换或 Compaction 前

在删除大量历史前，将关键决定、未解决问题和产物引用整理为可核对记录。

### 发现假设被推翻时

不应只添加一个新假设并保留旧假设继续 active。应将旧记录标记为 rejected 或 superseded。

## 哪些内容不值得直接写入

- 每一句模型分析；
- 没有后续用途的临时措辞；
- 可以廉价重新读取的大段原文副本；
- 未经处理的敏感凭证；
- 与当前 Run 无关的其他用户数据；
- 模型内部推理文本或隐藏 Reasoning Token；
- 没有来源、类型和适用范围的“结论”。

工作记忆的目标不是把上下文窗口复制到数据库，而是保存后续决策仍需要的任务信息。

## 更新不应等于静默覆盖

假设工作记忆中有：

~~~text
memory-9
type: hypothesis
content: 重复扣款由网络重试造成
status: active
~~~

后来代码和日志证明问题出在事务边界。可靠更新可以是：

~~~text
memory-9
status: rejected
resolution_ref: obs-41

memory-14
type: verified_fact
content: 幂等检查与扣款写入不在同一事务中
source_ref: obs-41
status: active
~~~

这样既不会让旧假设继续影响下一轮，也保留了它为何失效的解释。

## 什么会触发失效

### Goal 或 Scope revision

用户改变目标后，旧计划、待办和资料可能不再相关。

### 外部对象版本改变

代码、文件、数据库 Schema 或远端资源变化后，基于旧版本形成的事实需要重新核对。

### 新 Observation 推翻旧判断

最新测试失败可以使“所有测试通过”的旧记录失效。

### 时间或业务有效期到期

价格、库存、权限、令牌和日程等信息可能具有明确有效期。

### Approval 被撤销

旧工作记忆不能继续声称用户已经批准。

### Run 结束

当前 Run 的临时假设和待办通常不应自动进入下一个任务。是否跨任务保留需要另一套长期记忆与治理规则。

## 失效不一定意味着删除

常见状态可以包括：

~~~text
active：当前可用于决策
resolved：问题已经解决
rejected：假设已被推翻
superseded：被新版本替代
stale：可能过期，需要刷新
archived：保留历史但不参与默认检索
~~~

删除会丢掉因果历史；保留状态则可以解释为什么某条信息不再使用。敏感数据到期或用户要求删除时，则需要按数据治理规则真正删除或脱敏。

## 取回工作记忆的完整链路

~~~text
确定本次 Model Call 目的
→ 按 Goal、Run 和权限过滤
→ 按类型过滤
→ 排除 rejected、superseded 和无效记录
→ 检查版本、时间和来源
→ 按相关性排序
→ 去重和解决冲突
→ 选择少量记录进入 Context Package
~~~

取回不是“语义最相似的前 5 条”这么简单。对于用户批准、当前状态和文件版本等关键事实，应使用精确关系和权威记录核对。

## 工作记忆与 Run State 怎样分工

| 问题 | 更适合由谁回答 |
|---|---|
| Run 是否处于 waiting | Run State |
| 当前还剩多少预算 | Run State |
| 最近一次测试原始结果 | Observation / Artifact |
| 哪个假设尚待验证 | 工作记忆 |
| 用户当前批准是否有效 | Approval Store |
| 某个旧方向为什么被排除 | 工作记忆与事件引用 |
| Goal 是否已经 accepted | Acceptance State |

工作记忆可以保存指向权威记录的引用，但不应复制并取代它们的写入权。

## 一个跨 Model Call 的例子

### Model Call 1

模型根据日志提出假设：

~~~text
网络重试可能导致重复扣款。
~~~

Runtime 保存为 active hypothesis，并绑定日志来源。

### Tool Call

Runtime 运行隔离网络重试的测试，结果仍然出现重复扣款。

### 状态更新

~~~text
旧 hypothesis → rejected
新 verified fact → 网络重试不是必要条件
新 todo → 检查事务边界
~~~

### Model Call 2

Context Builder 只取回：

- 已确认“网络重试不是必要条件”；
- 当前 Todo；
- 最新失败报告引用；
- Goal 与当前 Run State。

旧假设可以保留在历史中，但不会继续以 active 身份误导模型。

## 工作记忆污染

污染可能来自：

- 模型把猜测写成事实；
- 外部网页中的恶意内容被保存成指令；
- 其他 Run 的信息进入当前任务；
- 摘要丢失否定词；
- 旧用户决定未随 revision 失效；
- 同一事实存在多个互相冲突的 active 版本。

因此 Memory Manager 需要来源、类型、状态、Scope、版本和写入策略，而不能只依赖向量相似度数据库。

## 常见误解

### 误解一：工作记忆越多，Agent 越聪明

过多过期、冲突和无关记录会降低判断质量，并增加泄漏风险。

### 误解二：模型决定记住什么就足够

模型可以建议，但 Runtime 仍需分类、去重、校验和控制敏感数据。

### 误解三：一条工作记忆写入后可以永久使用

它可能随 Goal、代码、时间、用户决定或外部状态变化而失效。

### 误解四：工作记忆就是长期学习

本章只讨论当前任务内的外部记忆；跨任务积累、遗忘和行为适应属于持续学习。

## 理解检查

1. 为什么工作记忆必须区分事实、假设、决定和待办？
2. 新 Observation 推翻旧假设时，为什么不应只增加一条新记录？
3. 工作记忆中写着“用户已批准”，为什么仍需查询审批系统？
4. Run 结束后，哪些内容不应自动进入下一个任务？

## 本篇停止点

如果你能解释“模型只提出写入建议，Runtime 保存带来源和失效条件的记录，Context Builder 每次只取回当前有效的小部分”，就掌握了工作记忆的基础生命周期。
