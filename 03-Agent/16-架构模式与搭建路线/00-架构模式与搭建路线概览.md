# 架构模式与搭建路线概览

> [!summary]
> Agent 架构不应从“选择最流行框架”开始，而应从任务需要的目标、状态、工具、失败恢复和验收边界开始，再选择最小可用模式。

## 常见模式地图

```text
单次 Tool Use
→ 一次模型调用选择或填写工具

Agent Loop / ReAct（Reasoning and Acting，推理与行动）
→ 根据 Observation 反复决定下一步

Planner–Executor
→ 计划与执行分开，并允许重新规划

Workflow + Agent
→ 确定性阶段包围局部动态决策

Graph / State Machine
→ 显式表示阶段、依赖和转换

Durable Agent Runtime
→ 持久状态、恢复、证据、权限和审计
```

这些模式可以组合，不必互相排斥。

## 从 Codex 到控制型 Agent

```text
Codex CLI
→ 持久化 Thread Goal + 同线程 Agent Loop + 工具验证与完成审计

CodeClosure 式增强
→ Goal Intake + Goal Contract + 阶段权威 + Candidate/Evidence + 独立 Acceptance
```

这不是“普通 Agent 与特殊 Agent”的区别，而是控制深度不同。搭建时应从任务风险出发，只增加真正需要的层级。

## 本专题要解决的问题

- 如何根据任务的不确定性和风险选择模式；
- 为什么 Workflow + Agent 往往比完全自由循环更容易控制；
- 何时需要 Planner、Graph、事件驱动或持久执行；
- 框架库、模型供应商和领域控制层怎样解耦；
- 如何从一个工具扩展到可靠闭环；
- Code Agent、Research Agent 和业务 Agent 的控制重点有什么不同；
- CodeClosure 一类外部控制 Runtime 属于哪种模式。

## 建议搭建顺序

```text
1. 定义一个可验证 Goal
2. 接入一个只读工具
3. 建立显式 Agent Loop 和最大步数
4. 持久化 Run 与 Observation
5. 增加一个受控写工具
6. 建立独立 Verification 与 Acceptance
7. 增加恢复、权限和审计
8. 建立评估集和成本指标
9. 最后判断是否需要多 Agent
```
