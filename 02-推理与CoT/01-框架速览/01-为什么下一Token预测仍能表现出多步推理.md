# 为什么下一 Token 预测仍能表现出多步推理

> [!summary]
> 模型的基本动作仍是预测下一个 Token，但它可以先生成中间步骤，再把这些步骤作为后续生成的上下文，于是复杂问题能够沿多个生成时刻逐步展开。

## 先连接已经学过的生成过程

在 [[01-LLM/02-单请求推理与生成/02-生成主线/06-完整生成循环串联复习/01-一次回答怎样完整生成|一次回答怎样完整生成]] 中，我们已经知道：

```text
现有上下文
→ Transformer 计算
→ Output Layer 得到下一个 Token 的候选概率
→ Runtime 选出一个 Token
→ 把它接回上下文
→ 继续下一轮
```

推理并没有把这条主线换掉。变化是：模型不一定马上给最终答案，而可能先生成一些对后续有帮助的中间内容。

## 一个直白例子

问题：

```text
17 × 24 等于多少？
```

### 直接回答

```text
408
```

模型仍做了内部计算，只是没有把中间过程写成输出 Token。

### 展开中间步骤

```text
17 × 20 = 340
17 × 4 = 68
340 + 68 = 408
```

这里可以把生成过程理解为：

```text
问题
→ 先生成“17 × 20 = 340”
→ 这段文字进入后续上下文
→ 再生成“17 × 4 = 68”
→ 两个中间结果都进入后续上下文
→ 最后生成“340 + 68 = 408”
```

真实模型按 Token 而不是按整行生成；上面的分行只是为了便于观察。

## 中间 Token 为什么可能有帮助

### 1. 把一个困难跳跃拆成多个较小判断

直接从题目跳到 `408`，需要在较短的生成路径中完成全部关系处理。展开后，模型可以依次处理乘以 `20`、乘以 `4` 和相加。

如果没有这种分解，较复杂问题中的多个条件更容易在一次跳跃里被遗漏。

### 2. 形成一个可继续读取的文本工作区

已经生成的 `340` 和 `68` 会出现在后续上下文里，模型之后可以再次通过 Attention 读取它们。

这里的“工作区”只是帮助理解的比喻。它不是一个独立的精确计算器，也不保证模型一定正确读取或使用其中的信息。

### 3. 增加运行阶段可使用的计算步骤

每生成一个新 Token，模型都要进行下一轮计算。中间 Token 越多，通常意味着模型在这次请求上使用了更多生成步骤，也就是更多 **Test-time Compute（测试时计算）**。

但“计算更多”只代表机会增加，不代表每一步都有效。

## 它不是怎样工作的

### 不是把一条完整答案藏在某处再逐字抄出

模型会根据当时已有的上下文持续预测后续 Token。后面的句子会受到前面已经生成内容的影响。

### 不是生成后再回头修改旧 Token

旧 Token 一旦生成，就已经成为固定历史。模型不能把它从过去直接改掉，只能继续生成类似“前面算错了，重新计算”的修正文本。

### 不是只要写得长就一定会推理得更好

如果第一步写错，错误也可能继续进入后续上下文并被放大。较长的过程还可能出现重复、偏题或为错误答案补理由。

## 与模型内部计算的区别

即使模型只回答 `408`，Transformer 内部也会产生多层 Hidden State，并不是“完全没有计算”。

因此应当区分：

```text
模型内部计算
→ 每次生成 Token 时，Transformer 内部进行的表示变换

外显中间步骤
→ 被模型真正生成、能够进入后续上下文的文字 Token
```

CoT 主要指第二种，不能被当成第一种的完整录像。

## 准确的因果链

```text
模型已经从训练中学到一定的问题结构和步骤模式
→ 运行时遇到问题
→ 生成一个中间步骤
→ 中间步骤成为新上下文
→ 后续 Token 可以利用它继续展开
→ 多步任务有机会被拆解完成
```

如果模型本身没有学会相关关系，单纯要求它“慢慢想”并不能凭空创造可靠能力。

## 常见误解

> [!warning] 误解：下一 Token 预测只能模仿句子，不能产生多步行为
> 下一 Token 预测是模型每一步的输出方式，不等于整个回答只有一步。连续许多次预测可以形成有依赖关系的多步序列。

> [!warning] 误解：写出了步骤，就证明这些步骤是真实内部思考
> 输出步骤确实会影响后续生成，但不一定完整、忠实地反映模型内部形成答案的原因。

> [!warning] 误解：推理模型不再使用自回归生成
> 常见推理模型仍然逐 Token 生成，只是可能使用更多中间 Token、更多运行时计算或额外的搜索与验证机制。

## 理解检查

1. 为什么已经生成的中间结果会影响后续答案？
2. 模型发现前面写错后，能否直接改掉已经生成的旧 Token？
3. 为什么增加中间 Token 可能有帮助，却不能保证正确？
