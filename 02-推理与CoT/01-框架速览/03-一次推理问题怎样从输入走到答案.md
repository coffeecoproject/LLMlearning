# 一次推理问题怎样从输入走到答案

> [!summary]
> 一次推理回答仍经过上下文整理、Tokenizer、Prefill 和逐 Token Decode；所谓“中间推理”，是在最终答案前先生成能够被后续 Token 继续读取的内容。

> [!note] 阅读层级
> 本篇属于“理解机制”。只看框架时，阅读 [[00-推理与CoT框架速览概览|推理与 CoT 框架速览概览]] 和 [[00-CoT中间推理文本概览|CoT 中间推理文本概览]] 即可，不必把 Prefill、KV Cache 和 Decode 细节作为下一专题的前置条件。

## 先看完整路径

以问题 `17 × 24 等于多少？` 为例：

```text
1. 上层应用整理本次请求的上下文
2. Runtime 使用配套 Tokenizer 把文本变成 Token ID
3. 模型对已有输入执行 Prefill
4. Output Layer 给出下一个 Token 的 Logits
5. Runtime 选择下一个 Token
6. 新 Token 接到序列末尾，KV Cache 保存可复用的注意力中间结果
7. 模型继续 Decode，逐个生成后续 Token
8. 到达最终答案和停止条件
9. Runtime 或上层应用把允许展示的内容返回给用户
```

CoT 没有绕过其中任何一层。

## 第一步：上层应用整理上下文

进入模型的通常不只是用户看到的一句话，还可能包括：

```text
系统指令
对话历史
用户当前问题
产品定义的特殊结构或控制信息
```

这一层决定模型“这次看到了什么”，但它还不是模型推理本身。

## 第二步：Tokenizer 把文本离散化

Tokenizer 把整理后的文本转成 Token ID 序列。模型不会直接接收汉字字符串，而是接收这些离散编号，再通过 Embedding 形成初始向量表示。

这与普通回答完全相同，推理模式并不需要一套脱离 Tokenizer 的输入通道。

## 第三步：Prefill 理解已有输入

**Prefill** 是模型并行处理本次已经存在的输入 Token，建立它们的 Hidden State，并为注意力生成可复用的 KV Cache。

此时模型还没有把整段未来回答一次性写完。它只是基于现有上下文，准备预测回答的第一个 Token。

## 第四步：开始逐 Token Decode

假设模型先生成：

```text
可以拆成
```

这些字会被分成一个或多个 Token。每生成一个 Token，它就加入已生成序列，下一轮模型可以通过 Attention 读取它。

接下来可能继续生成：

```text
17 × 20 = 340，17 × 4 = 68
```

直到得到：

```text
所以结果是 408。
```

## KV Cache 在这里做什么

KV Cache 保存过去 Token 在各层 Attention 中已经计算出的 Key 和 Value，使模型生成下一个 Token 时不必从头重复计算全部历史。

它的作用是**提高生成效率**，不是替模型验证推理是否正确，也不是额外塞进上下文的一段文字。

```text
上下文 Token
→ 决定模型在语义上能够读取什么

KV Cache
→ 保存这些历史 Token 的部分可复用计算结果
```

## 先生成的步骤怎样影响后面

当 `340` 和 `68` 已经生成，它们就属于后续 Token 的历史上下文。后面的计算可以关注这些位置，然后生成 `408`。

因此，中间过程的作用不是“写给用户看完再交回模型”，而是在同一次自回归生成中自然成为后续输入。

## 模型能否回头修改前面的步骤

不能直接改写已经生成的旧 Token。

如果模型后来发现错误，只能继续追加：

```text
前面的计算有误，重新计算……
```

这会形成新的文本，但错误内容仍然留在历史上下文中。后面的 Token 既能看到修正，也能看到旧错误，因此修正并非一定成功。

## 三种常见运行路线

### 路线 A：直接回答

```text
问题
→ Prefill
→ Decode“408”
→ 停止
```

### 路线 B：单条 CoT

```text
问题
→ Prefill
→ Decode 中间步骤
→ 中间步骤持续进入上下文
→ Decode 最终答案
→ 停止
```

### 路线 C：外部多路径与验证

```text
问题
→ 生成候选 A、B、C
→ 外部系统保存并比较候选
→ 规则、工具或模型进行验证
→ 选择候选或再次调用模型修正
→ 返回答案
```

路线 C 可能包含多次独立模型调用，不再只是一次回答内部的一条生成路线。

这些调用可以串行，也可以并行；无论怎样调度，每一条候选内部仍然逐 Token Decode。路径并行与 Token 串行并不冲突。

## “推理内容”一定会展示给用户吗

不一定。

产品可以采用不同设计：

- 直接展示模型生成的中间文本；
- 只展示压缩后的说明；
- 内部使用额外推理 Token，但只返回最终答案；
- 根本不要求模型生成可见 CoT。

因此，从界面只看到最终答案，不能推断模型内部没有进行额外运行时计算；看到一段详细解释，也不能推断它就是完整、忠实的内部推理轨迹。

对于闭源模型，如果官方没有公开具体实现，就应当把内部 Token 格式、搜索方式和训练方案标记为未知，而不能根据界面表现倒推。

## 本例中的三个系统边界

| 层 | 本例中负责什么 |
|---|---|
| LLM | 根据当前 Token 上下文计算下一个 Token 的分布 |
| 模型 Runtime | 执行 Prefill、Decode、采样、KV Cache 和停止控制 |
| 上层应用或 Agent | 整理消息，必要时组织多次调用、工具验证与状态管理 |

本模块先研究前两层以及轻量的外部推理控制；长期任务和工具闭环留到 Agent 模块。

## 常见误解

> [!warning] 误解：模型先在内部想完整段答案，再一次性交给 Output Layer
> 自回归模型通常逐 Token 形成输出，先前生成的内容会改变后续预测条件。

> [!warning] 误解：KV Cache 保存了另一份更聪明的推理内容
> KV Cache 是计算复用结构，它对应已有 Token 的注意力 Key 和 Value，不负责增加事实或纠正答案。

> [!warning] 误解：推理模式一定会改变 Logits 的采样公式
> 产品可能调整采样与预算，但核心差异也可能主要来自模型训练、特殊上下文结构和允许生成更多中间 Token。不能仅凭“推理模式”名称断定底层实现。

## 理解检查

1. CoT 在生成过程中从什么时候开始影响后续 Token？
2. Prefill 和 Decode 分别处理什么？
3. KV Cache 为什么能提速，却不能保证答案正确？
4. 为什么界面没有显示 CoT，不等于模型没有使用额外推理计算？

## 本节小结

```text
推理问题进入系统
→ 仍被 Tokenizer 转换
→ 仍经过 Prefill
→ 仍由模型和 Runtime 逐 Token Decode
→ 中间 Token 可以延长计算路径
→ 搜索与验证可以在外层增加多路径控制
→ 最终是否正确仍需评估
```
