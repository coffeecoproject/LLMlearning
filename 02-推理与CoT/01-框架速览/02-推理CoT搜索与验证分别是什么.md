# 推理、CoT、搜索与验证分别是什么

> [!summary]
> 推理是要观察的能力或行为，CoT 是一条外显中间文本路径，搜索是在多条可能路径中探索，验证则负责检查步骤或结果；四者可以组合，但不是同一个概念。

## 为什么必须先分开

日常讨论常把下面几件事都说成“模型在思考”：

- 模型直接算出答案；
- 模型写出一段步骤；
- 系统让模型尝试五种解法；
- 程序检查答案是否正确；
- Agent 调用工具后重新规划。

如果不分层，就很难判断能力究竟来自模型本身、更多生成步骤，还是模型外部的控制系统。

## 1. 推理：要解释的能力或行为

**Reasoning（推理）**通常指：根据已有条件建立关系，经过一个或多个中间变化得到结论。

例如：

```text
所有参加会议的人都需要登记。
小林参加会议。
因此，小林需要登记。
```

“推理”是一个上位概念。它可以根据最终表现来判断，也可以研究中间过程，但它本身不是某一种固定的输出格式。

## 2. CoT：一条外显的中间文本路径

**Chain of Thought（思维链，CoT）**指模型在最终答案前生成的一系列中间推理步骤。

例如：

```text
17 × 24
= 17 × 20 + 17 × 4
= 340 + 68
= 408
```

这是一条从问题走向答案的路径。它的 Token 会成为后续生成的上下文。

但一条 CoT 仍可能从头到尾只有一条路线，没有比较其他可能答案。

## 3. 搜索：探索多条候选路径

**Search（搜索）**是尝试、保留、比较或回溯多条候选路径。

例如同一道题，系统可以让模型产生：

```text
候选 A：17 × 20 + 17 × 4 = 408
候选 B：17 × 25 - 17 = 408
候选 C：错误地得到 398
```

然后再比较这些候选。

### 模型只能向前生成，为什么还能出现分支

“只能向前生成”约束的是每一条路径，不是整个系统只能保留一条路径。

```text
共同问题 P
├── P → A1 → A2 → 答案 A
├── P → B1 → B2 → 答案 B
└── P → C1 → C2 → 答案 C
```

外部系统可以复制同一个问题起点，分别启动多次生成。每条路径内部仍然逐 Token 向前，但路径之间可以串行执行，也可以并行执行。

如果只在一次回答中连续写出“方案 A、方案 B、方案 C”，它们并不是三个完全隔离的分支：生成 B 时已经能看到 A，生成 C 时已经能看到 A 和 B。

搜索策略通常由**推理控制器或上层系统**组织，包括生成几条路径、保留哪条路径以及何时停止。模型 Runtime 可以负责批处理、并行调度和 KV Cache 复用，但狭义 Runtime 通常不自行决定搜索目标和淘汰规则。

## 4. 验证：检查步骤或结果

**Verification（验证）**是判断某个步骤或最终结果是否满足标准。

验证者可以是：

| 验证方式 | 示例 |
|---|---|
| 确定性规则 | 计算器重新计算 `17 × 24` |
| 测试程序 | 运行代码测试，检查是否通过 |
| 数据查询 | 查询真实订单状态 |
| 另一个模型或评分器 | 对候选证明进行评价 |
| 人类 | 审阅开放性方案是否合理 |

“模型自己说我检查过了”只是又生成了一段文字，不自动构成可靠验证。

## 放在同一个例子里

问题：

```text
找出 17 × 24 的结果。
```

```text
推理目标
→ 从 17 和 24 的关系得到乘积

CoT
→ 写出 17 × 20、17 × 4、最后相加的一条路径

搜索
→ 同时尝试拆成 20+4、25-1 等多条路径

验证
→ 用确定性计算重新检查最终值是否等于 408
```

## 四者怎样组合

| 组合 | 可能的运行方式 |
|---|---|
| 推理，不输出 CoT | 模型直接返回答案 |
| 推理 + 一条 CoT | 沿一条中间步骤生成到底 |
| 多条 CoT + 简单选择 | 采样多个答案，按多数一致结果选择 |
| 搜索 + 评价 | 逐步扩展候选，评价并保留较好的分支 |
| 搜索 + 外部验证 | 用测试、计算器或规则筛掉错误分支 |

因此，**CoT 不是搜索，搜索也不等于验证**。

## 与内部 Hidden State 的边界

每次生成时，模型内部都会形成 Hidden State。它们参与当前 Token 的预测，但并不等于一段人类可读的 CoT。

更准确的分层是：

```text
内部 Hidden State
→ 模型内部的连续向量计算

CoT Token
→ 模型已经输出的中间文字

搜索控制
→ 外部系统组织多条生成路径

验证信号
→ 检查路径或结果是否满足标准
```

## 与 Agent 的边界

本模块会学习模型调用之间怎样采样、搜索和验证，但暂不展开 Agent 的权限、长期状态和工具执行闭环。

当系统需要持续执行“读文件 → 修改 → 测试 → 根据结果再决定”，就已经开始进入后续 Agent 模块。

## 常见误解

> [!warning] 误解：只要让模型输出三种方案，就已经完成搜索
> 产生候选只是第一步。搜索还需要保留状态、评价候选、决定扩展或停止。

> [!warning] 误解：多数答案一致就证明答案正确
> 多数一致只能利用不同路径之间的一致性。如果它们共享同一个错误，多数结果仍然可能错误。

> [!warning] 误解：验证一定可靠
> 验证效果取决于检查标准。数学计算器可以很确定，但开放性方案的模型评分仍可能带有概率性错误。

## 研究来源怎样对应四层

- [Chain-of-Thought Prompting](https://arxiv.org/abs/2201.11903)：关注中间推理步骤怎样诱发复杂任务表现；
- [Self-Consistency](https://arxiv.org/abs/2203.11171)：采样多条 CoT，再选择较一致的最终答案；
- [Tree of Thoughts](https://arxiv.org/abs/2305.10601)：把单路径生成扩展为带评价与回溯的搜索；
- [Language Models Don't Always Say What They Think](https://arxiv.org/abs/2305.04388)：提醒外显 CoT 可能不忠实反映答案形成原因。

## 理解检查

1. 一条很长的 CoT 为什么仍不一定属于搜索？
2. 程序运行测试与模型说“测试应该能通过”有什么区别？
3. 如果系统生成五条候选并用计算器检查，它分别使用了哪些层？
