# 推理投入与搜索宽度怎样组合

> [!summary]
> Reasoning Effort 决定每条候选路径投入多少推理计算，Search Width 决定同时探索多少条路径；前者近似“每条走多充分”，后者近似“同时试多少条路”。

## 两个独立方向

```text
Reasoning Effort
= 每条路径投入多少计算

Search Width
= 探索多少条候选路径
```

“推理深度”常被用作前者的直观比喻，但严格说更合适的名称是“推理投入”或“测试时计算预算”。一条路径生成得更长，不一定就真正更深入。

## 二维关系

| | 一条路径 | 多条路径 |
|---|---|---|
| Low | 快速生成一个答案 | 快速采样多个浅投入候选 |
| Medium | 一条中等投入路径 | 多条中等投入路径 |
| High | 一条较高投入路径 | 多条高投入路径，成本通常最高 |

这个表表达的是系统组合方式，不代表某个 API 一定直接提供六种按钮。

## 四种常见策略

### 1. 一条低投入路径

适合简单、低风险或容易立刻验证的问题。

```text
问题 P → low 路径 A → 答案
```

### 2. 一条高投入路径

给一个复杂问题更多内部推理机会，但仍然可能从错误起点一路生成到底。

```text
问题 P → high 路径 A → 答案
```

### 3. 多条低或中等投入路径

先得到不同候选，再通过一致性、评分或验证选择。

```text
问题 P
├── medium A
├── medium B
└── medium C
     ↓
评价与验证
```

这种策略可能比单条超长路径更容易发现不同假设，但代价取决于路径数量。

### 4. 先宽后深

先用较低投入快速产生多个方向，再只对少数有希望的候选追加高投入：

```text
第一轮：A、B、C、D
→ 评价后保留 B、D
→ 第二轮：对 B、D 使用更高投入
→ 验证最终候选
```

这是一种外部推理控制策略，不是 Reasoning Effort 参数单独完成的。

## 谁负责哪一层

| 系统部分 | 典型责任 |
|---|---|
| 模型 | 在一条上下文路径中逐 Token 生成 |
| 推理控制器 / Agent | 决定路径数、何时扩展、淘汰和验证 |
| 模型 Runtime | 批处理并执行多个生成请求，管理 KV Cache 等资源 |
| Verifier / 工具 | 提供候选是否正确的外部证据 |

Runtime 可以让多条路径更高效地运行，但“应该建立几条、保留哪条”通常属于上层策略。

## 第三个方向：验证强度

只讨论“投入 × 宽度”仍不完整。系统还要问：怎样判断候选好坏？

```text
一条高投入路径
→ 如果没有验证，仍可能自信地错

多条候选路径
→ 如果评价器偏差相同，也可能共同选错
```

因此完整设计更接近：

```text
每条路径的推理投入
× 路径数量
+ 验证质量
```

详见 [[05-候选评价与Verifier|候选评价与 Verifier]]。

## 简易成本关系

下面只是帮助理解，不是精确计费公式：

```text
模型生成成本
≈ 路径数量 × 每条路径平均 Token 与计算量
```

例如，3 条中等投入路径不一定比 1 条高投入路径便宜；只有实际模型、Token 使用量、并行资源和定价才能决定。
