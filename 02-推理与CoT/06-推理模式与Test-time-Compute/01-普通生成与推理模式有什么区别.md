# 普通生成与推理模式有什么区别

> [!summary]
> 两者通常都经过 Tokenizer、Transformer、Output Layer 和逐 Token 解码；主要差别在模型经过了怎样的训练、请求怎样触发相应行为，以及回答前投入了多少推理阶段计算。

## 先看共同主线

无论是普通回答还是推理回答，Decoder-only LLM 的基本运行路径仍然是：

```text
上下文
→ Tokenizer
→ Embedding 与 Position
→ Transformer Blocks
→ Output Layer 与 Logits
→ 选择下一个 Token
→ 把新 Token 接回上下文继续生成
```

因此，“推理模式”不代表模型突然脱离了 Next Token Prediction，也不代表运行时多出一个独立 Encoder。

## 一个直白例子

问题：

```text
17 × 24 等于多少？
```

普通生成可能很快给出：

```text
408
```

推理模式可能在最终答案前使用更多中间 Token，例如先处理：

```text
17 × 20 = 340
17 × 4 = 68
340 + 68 = 408
```

关键不在于用户一定能看到这些文字，而在于这些中间 Token 能继续成为后续 Token 的条件，给模型提供一个可继续读取的临时工作区。

## 差别主要来自三个方面

### 1. 模型能力与训练

模型需要在训练或后训练中学会：面对某类任务时，怎样生成、利用和改进中间推理过程。

如果模型没有形成相应能力，仅靠加一个“请深入思考”的指令，不会凭空创造可靠推理能力。

### 2. 请求与模板怎样触发行为

不同产品可能通过不同方式控制：

- API 中的 `reasoning.effort` 一类参数；
- 模型专用的 Chat Template；
- 模型能够识别的控制 Token；
- 系统提示和产品侧策略。

这些属于接口和模型约定，不是所有模型都使用同一种开关。

### 3. 一条调用投入多少运行计算

推理模式通常允许模型在最终回答前使用更多推理阶段 Token，因此可能在复杂任务上得到更充分的处理时间。

但更多 Token 不自动等于更正确。模型也可能在错误前提上进行更长的推导。

## 普通模式并非“完全不推理”

“普通生成”和“推理模式”不是有无推理能力的绝对分界：

- 普通模型也可能直接完成简单推理；
- 普通模式也可以在提示后输出 CoT；
- 推理模型处理简单问题时也可能很快回答；
- 推理模式强调的是更稳定地分配额外推理计算，而不是首次产生逻辑能力。

## 推理内容和最终回答仍是连续生成吗

从模型的自回归视角看，它们都以 Token 形式向前产生。产品可以在输出协议中把它们区分为不同部分：

```text
内部或受控的推理阶段 Token
→ 最终回答 Token
```

用户界面只展示最终回答，并不意味着前面没有使用推理 Token；界面展示了“思考摘要”，也不意味着它公开了原始完整推理轨迹。

## 常见误解

### 误解一：推理模式改变了 Logits 的基本含义

没有。每一步仍然由当前 Hidden State 经过 Output Layer 得到下一 Token 的 Logits。不同之处主要是上下文、模型行为和推理预算影响了这条生成路径。

### 误解二：推理模式会自动建立多个并行分支

不一定。一次高预算推理仍可能只沿一条路径生成。多路径属于 [[00-采样搜索与验证概览|采样、搜索与验证]] 的另一层控制。

### 误解三：推理模式等于把 CoT 全部展示给用户

不等于。推理发生、推理 Token 被生成或消耗、用户看到推理文字，是三个不同问题。
