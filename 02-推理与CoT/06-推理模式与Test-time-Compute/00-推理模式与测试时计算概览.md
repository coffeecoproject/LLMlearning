# 推理模式与 Test-time Compute 概览

> [!summary]
> 推理模式通常不是换掉 Transformer 的基本生成结构，而是让经过相应训练的模型在给出最终答案前投入更多运行阶段计算；Reasoning Effort 控制的是每条调用的推理投入，外部 Search Width 控制的是探索多少条候选路径。

## 为什么需要单独学习这一部分

普通对话和复杂推理都通过自回归方式逐 Token 生成，但复杂问题往往需要更多中间处理。

系统可以从两个不同方向增加计算：

```text
单条路径投入更多计算
→ Reasoning Effort / 推理投入

同时探索更多路径
→ Search Width / 搜索宽度
```

二者可以组合，却不是同一个参数。

## 四个容易混淆的概念

| 概念 | 一句话理解 | 不应误解为 |
|---|---|---|
| 推理模式 | 让模型在最终回答前使用更充分的推理阶段计算 | 换成了另一套 Encoder |
| Reasoning Token | 模型在推理阶段生成或消耗的 Token | 必然原样展示给用户 |
| CoT | 以 Token 序列表达的中间推理步骤 | Transformer 的全部内部计算 |
| Reasoning Effort | 一次调用愿意投入多少推理计算的控制项 | 自动创建多少条搜索分支 |

`<think>...</think>` 则只是部分模型或 Chat Template 用来组织推理文本的格式，不是所有推理模型共同遵守的底层协议。

## 放回完整系统看

```text
Agent / 应用
→ 组织上下文，选择模型、推理投入和是否建立候选分支

模型 Runtime
→ 执行请求，调度生成，管理 KV Cache 等资源

推理模型
→ 沿每条路径逐 Token 产生推理阶段内容和最终回答

验证器 / 工具
→ 检查候选结果，向控制器返回证据
```

狭义 Runtime 可以高效执行多个分支，但通常不是它自行决定“应该搜索几条思路”。这个策略更常由推理控制器、Agent 或应用层组织。

如果这里仍容易混淆“推理到底在模型、Runtime 还是 Agent”，先阅读 [[04-推理CoT搜索与验证分别在哪一层实现|推理、CoT、搜索与验证分别在哪一层实现]]。

## Test-time Compute 是什么

Test-time Compute 可以直译为“测试时计算”或“运行时推理计算”：模型训练完成后，在实际回答一个问题时投入的计算。

它可能增加在：

- 单条路径中的推理 Token；
- 多条候选路径；
- 候选评价和外部验证；
- 工具调用与多轮修正。

其中后两项通常已经进入外部推理系统或 Agent，而不只是模型自身的一次生成。

一个便于理解、并非精确计费公式的关系是：

```text
总运行计算
≈ 搜索路径数 × 每条路径的平均推理投入
  + 评价、验证和工具执行
```

## 先记住的边界

- 推理模式仍可能出错；
- `high` 通常更慢、更耗 Token，但不保证更正确；
- `high` 不等于更长的可见 CoT；
- `high` 不等于自动并行更多路径；
- 普通模型也可以输出 CoT，推理模型也可以只向用户展示最终答案；
- 闭源模型如何实现内部控制，若官方没有公开，就不能根据界面名称反推具体结构。
