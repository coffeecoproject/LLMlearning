# 成本、延迟与能力边界

> [!summary]
> 增加推理 Token、候选路径和验证步骤可以提高复杂任务成功的机会，但会增加延迟与资源消耗，也无法补回缺失事实或保证验证标准正确。

## 能提高什么

更多测试时计算可能让系统：

- 分解更多中间步骤；
- 检查早期假设和约束；
- 尝试不同候选路径；
- 调用验证器筛掉部分错误；
- 在代码、数学等可验证任务中迭代修正。

它提高的是“找到并保留好结果的机会”，不是把概率模型变成确定正确的系统。

## 成本来自哪里

### 更多推理 Token

单条调用在最终回答前使用更多计算，通常增加完成时间和资源消耗。

### 更多候选路径

即使路径可以并行执行，总 GPU 计算和显存压力仍会增加。并行主要减少等待时间，不会让计算免费消失。

### 更多评价和验证

调用评分模型、测试程序、搜索工具或真实数据库都会产生额外成本，也可能需要新的模型调用。

## 延迟要分两种感受

```text
看到第一段用户可见输出的等待
≠ 得到最终已验证结果的总时间
```

如果推理内容不流式展示，用户可能等待较久才看到最终回答。多路径并行可以缩短相对于串行搜索的时间，但最终仍要等待最慢候选或验证步骤完成。

## 为什么更多计算仍然可能失败

### 缺少关键事实

模型没读到真正相关的代码或数据时，推理再长也不能凭空获得事实。

### 错误前提被不断放大

模型可能从错误理解出发，生成一段更长、更自洽的错误推导。

### 多条路径存在相关错误

A、B、C 来自同一模型和相同缺失上下文，可能共同重复同一误解。

### 验证器也有边界

测试可能不完整，规则可能写错，模型评分器也可能偏向看似流畅的错误答案。

## 什么时候先补上下文，而不是提高档位

出现以下情况时，首先应该改善真实信息输入：

- 问题依赖未读取的项目文件；
- 需要最新外部事实；
- 关键约束只存在数据库或业务规则中；
- 模型对需求的理解尚未确认；
- 候选都在猜测同一个未知事实。

这时更有效的路径通常是：

```text
读取事实 / 调用工具
→ 更新上下文
→ 再进行适当推理
→ 使用独立验证
```

## 一个实用判断顺序

1. 当前上下文是否包含必要事实？
2. 问题能否被拆成可验证的中间结果？
3. 一条中等投入路径是否已经足够？
4. 如果不够，应提高单条投入还是增加候选宽度？
5. 谁来验证最终结果，验证标准是否覆盖真实目标？

## 最终边界

```text
Reasoning Effort
→ 增加每条调用的推理机会

Search Width
→ 增加探索不同路径的机会

Verifier
→ 增加筛错所依据的证据

三者都不能单独保证正确
```

要把概率模型用于高风险、长周期任务，仍需进入 Agent 模块继续学习状态管理、工具执行、权限、恢复和验收闭环。

1. 并行为什么能降低等待，却不能消除总计算成本？
2. 为什么缺少事实时不应只提高 Reasoning Effort？
3. 为什么验证器本身也需要验证边界？
