# 推理与 CoT 边界复习

> [!summary]
> 模型可以用更多中间 Token 展开单条推理路径，上层系统还可以增加候选搜索和外部验证；这些方法提高的是找到正确结果的机会，而不是把概率生成自动变成确定正确的执行系统。

## 把完整框架串起来

```text
用户问题与上下文
        ↓
LLM 内部计算
        ↓
直接答案，或生成一条 CoT
        ↓
可选：推理控制器建立多条候选路径
        ↓
可选：Verifier、工具或人类检查结果
        ↓
选择、修正或再次生成
        ↓
最终回答
```

无论中间是否加入 CoT、搜索和验证，每一条模型生成路径内部通常仍然逐 Token 向前生成。

## 五个角色分别负责什么

| 角色 | 框架职责 | 不负责什么 |
|---|---|---|
| LLM | 根据当前上下文计算并生成下一 Token | 不天然保证事实和任务结果正确 |
| CoT | 把一条推理路径表达为中间文本 | 不是模型内部计算的完整录像 |
| 模型 Runtime | 执行 Prefill、Decode、采样和资源管理 | 通常不自行决定任务级搜索目标 |
| Agent 或推理控制器 | 组织多次调用、候选、工具和验证循环 | 不会因为组织了循环就自动覆盖全部风险 |
| Verifier、工具或人类 | 根据某种标准检查步骤或结果 | 只能检查标准覆盖到的内容 |

这些角色可能部署在同一个程序或服务器中，但理解时应按职责区分。

## 六组不能混为一谈的概念

### 内部计算不等于 CoT

Transformer 内部会形成 Hidden State。CoT 是模型生成出来的中间文本，不能被当作全部内部因果过程。

### CoT 不等于搜索

一条 CoT 仍是一条向前路径。搜索需要保存、扩展和比较多个候选状态。

### 搜索不等于验证

搜索增加候选数量；验证提供检查依据。多个候选彼此一致，也可能只是共同犯错。

### 推理模式不等于更长的可见解释

推理模式可能投入更多 Reasoning Token 或其他测试时计算，但产品可以只展示摘要或最终答案。

### 验证不等于评估

```text
验证（Verification）
= 检查当前这次答案、代码或任务结果

评估（Evaluation）
= 用一组任务和指标衡量模型或系统的整体表现
```

一次答案通过验证，不代表模型在所有相似任务上都可靠；某个评测分数较高，也不保证当前答案一定正确。

### 推理系统不等于 Agent 系统

推理系统重点增加中间计算、候选和验证。Agent 还需要处理工具执行、权限、持久状态、失败恢复、长期目标和验收闭环。

## 为什么推理仍然会失败

```text
上下文缺少关键事实
→ 模型只能在不完整信息上推理

早期中间步骤错误
→ 后续 Token 可能沿错误继续生成

候选路径缺乏多样性
→ 多次生成可能重复同一种错误

验证条件不完整
→ 系统可能通过已有检查却遗漏真实风险

投入过多计算
→ 可能出现重复、偏离和过度推理
```

因此，合理顺序通常是：

```text
先保证问题和事实输入足够清楚
→ 再选择合适的推理投入
→ 必要时增加候选搜索
→ 使用尽可能独立且覆盖目标的验证
```

## 一个判断框架

面对一个任务，可以依次问：

1. 问题和所需事实是否已经进入上下文？
2. 单条直接生成是否足够，还是需要中间步骤？
3. 是否存在多种可能路径，值得进行搜索？
4. 最终结果能否用计算器、测试、规则、数据库或人类判断验证？
5. 验证标准是否真的覆盖用户目标？
6. 任务是否已经涉及长期状态、工具、权限和失败恢复？如果是，就开始进入 Agent 层。

## 框架层完成标准

只了解框架时，你不需要掌握搜索公式、Tensor 形状、Reasoning Effort 的内部参数或特定 Runtime 的调度实现。

只要能够解释下面这条因果链，就可以结束本模块的框架路线：

```text
LLM 仍然逐 Token 生成
→ CoT 为单条路径增加可继续读取的中间步骤
→ 搜索在外层增加候选路径
→ 验证用外部标准检查结果
→ 更多计算提高成功机会但不保证正确
→ 长任务可靠执行还需要 Agent 的状态与控制闭环
```
