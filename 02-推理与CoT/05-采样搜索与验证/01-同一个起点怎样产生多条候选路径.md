# 同一个起点怎样产生多条候选路径

> [!summary]
> 外部控制器保存共同问题的上下文，然后从这个起点启动多次独立生成；每条生成仍然向前，但整个系统因此形成多个分支。

## 一个共同起点

假设问题是：

```text
17 × 24 等于多少？
```

把当前共同上下文记为 `P`：

```text
P = 系统指令 + 用户问题
```

推理控制器可以用 `P` 启动三次生成：

```text
P
├── A1 → A2 → 答案 A
├── B1 → B2 → 答案 B
└── C1 → C2 → 答案 C
```

模型没有从 A 倒退到 B。A、B、C 是三条分别从 `P` 出发的新生成。

## 每条路径内部发生什么

路径 A 内部仍然是：

```text
P
→ 生成 A1
→ A1 加入路径 A 的上下文
→ 生成 A2
→ A2 加入路径 A 的上下文
→ 生成答案 A
```

路径 B 不需要读取 A 的后缀：

```text
P
→ 生成 B1
→ 生成 B2
→ 生成答案 B
```

所以，“向前生成”与“存在分支”并不冲突。

## 一次回答列三个方案为什么不同

如果只调用一次模型：

```text
问题
→ 写方案 A
→ 写方案 B
→ 写方案 C
```

那么生成 B 时，A 已经属于上下文；生成 C 时，A 和 B 都属于上下文。后面的方案可能被前面的方案锚定。

真正的隔离分支则是：

```text
调用 A 只看到 P
调用 B 只看到 P
调用 C 只看到 P
```

## 回溯不是倒放 Token

假设路径 A 已经走到错误的 `A2`：

```text
P → A1 → A2（错误）
```

控制器可以丢弃这个分支，再从保存的 `P → A1` 启动一次新生成：

```text
P → A1 → A3（新的尝试）
```

“回溯”指恢复较早的分支状态并重新向前生成，不是让模型逆向修改旧 Token。

## 候选状态由谁保存

外部系统通常保存类似状态：

```text
候选 A：当前前缀、评分、是否完成
候选 B：当前前缀、评分、是否完成
候选 C：当前前缀、评分、是否完成
```

模型负责生成或评价，控制器负责候选生命周期。

## KV Cache 是可选优化

三条路径共享 `P`。模型 Runtime 可能复用 `P` 对应的 KV Cache，再为每条路径保存独立后缀：

```text
公共前缀 KV
├── A 的新增 KV
├── B 的新增 KV
└── C 的新增 KV
```

这可以减少重复计算，但不是实现分支的必要条件。即使三次请求都从头 Prefill，也仍然是多路径生成。

## 理解检查

1. 为什么路径 B 不需要从路径 A 倒退得到？
2. 一次回答连续写三个方案为什么不完全独立？
3. KV Cache 复用改变了搜索逻辑，还是只改变了执行效率？
