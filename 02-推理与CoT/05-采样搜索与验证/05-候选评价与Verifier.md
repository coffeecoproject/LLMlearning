# 候选评价与 Verifier

> [!summary]
> Verifier（验证器）接收候选步骤或结果，输出“是否满足标准”或一个评分，帮助搜索系统筛选路径。

## 验证器可以检查什么

### 最终结果

```text
模型答案：408
→ 计算器重新计算
→ 结果一致
```

这属于 Outcome Verification（结果验证）。它不需要知道模型怎样得到 `408`。

### 中间步骤

```text
步骤 1：17 × 20 = 340
步骤 2：17 × 4 = 68
步骤 3：340 + 68 = 408
```

如果系统逐步检查每一项，就属于 Process Verification（过程验证）。这要求验证器能读取中间步骤。

## 验证器有哪些来源

| 类型 | 示例 | 可靠性特点 |
|---|---|---|
| 确定性程序 | 计算器、编译器、单元测试 | 标准明确时较强 |
| 真实系统查询 | 数据库、订单状态、传感器 | 提供外部事实证据 |
| 模型评分器 | 判断证明或文章质量 | 灵活但仍有概率性 |
| 人类 | 审阅开放方案 | 成本高，判断也可能不一致 |

## 评价与验证不完全相同

搜索中的“评价”可能只是判断哪个分支更有希望：

```text
A：值得继续
B：可能死路
C：信息不足
```

它不一定证明 A 正确。

验证通常要求候选满足更明确的标准，例如测试通过或等式成立。

## 模型自检的边界

让同一个模型说“请检查你的答案”可以产生新判断，但它可能继续受到原错误影响。

```text
模型生成答案
→ 同一模型生成“检查通过”
```

这比没有检查多一步，却仍不等于独立证据。能运行程序时，应优先使用真实执行结果。

## 谁组织验证，谁执行检查

一次 Verification 通常由不同部分共同完成：

```text
Agent 或推理控制器
→ 决定检查什么、何时检查以及失败后怎么办

Verifier 或工具
→ 实际运行测试、计算、查询或评分

模型 Runtime
→ 如果 Verifier 是模型，负责执行这次模型调用
```

因此，具备 Verification Loop 不等于验证范围必然完整。系统可能真实运行了已有测试，却仍然遗漏未被想到的并发、兼容或业务边界。
