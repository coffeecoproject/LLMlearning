# 采样、搜索与验证概览

> [!summary]
> 单次生成只能沿一条 Token 路径向前；搜索系统可以复制同一个上下文起点，生成、评价和筛选多条路径，再用验证降低只相信一次生成的风险。

## 这部分解决什么问题

一条 CoT 可能从第一步就走错。如果系统只运行一次模型，就只能继续沿这条路径生成，或者在后面追加修正文字。

搜索与验证增加了两种能力：

```text
搜索
→ 不只保留一条可能路径

验证
→ 不只依赖模型自己声称“答案正确”
```

## 最小主线

```text
共同问题 P
├── 生成候选 A
├── 生成候选 B
└── 生成候选 C
        ↓
评价、比较或验证
        ↓
选择、修正或继续扩展
        ↓
最终答案
```

每条候选内部仍然逐 Token 向前生成。

## 必须先区分的三个角色

| 角色 | 主要责任 |
|---|---|
| LLM | 根据当前分支上下文生成下一个 Token，或评价一个候选 |
| 推理控制器 | 建立分支、保存候选、决定扩展和停止 |
| 模型 Runtime | 高效执行请求，负责批处理、调度和缓存复用 |

推理控制器可以是专门程序，也可以位于 Agent 或模型服务内部。它不一定是 vLLM 这类狭义 Runtime 的组成部分。

## 两种最常见的搜索宽度

### 完整回答级

```text
同一道题独立生成 5 次
→ 得到 5 个最终答案
→ 按一致性或验证结果选择
```

这是 Self-Consistency 一类方法的基本方向。

### 中间步骤级

```text
先产生几个局部想法
→ 评价并保留部分想法
→ 从保留位置继续扩展
→ 必要时回到较早分支
```

这是 Tree of Thoughts 一类方法的基本方向。

## 搜索不一定需要可见 CoT

如果系统只比较最终答案：

```text
A → 408
B → 408
C → 398
```

它不需要读取中间步骤。

如果系统要评价“把 24 拆成 20+4”这个局部想法，它就必须获得某种系统可见的中间状态。但这个状态仍然可以不展示给最终用户。

3. 路径并行为什么不改变每条路径内部的 Token 串行？
