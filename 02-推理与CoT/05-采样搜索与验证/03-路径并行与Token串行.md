# 路径并行与 Token 串行

> [!summary]
> 多条候选路径可以同时执行，但每条自回归路径内部仍要等前一个 Token 生成后才能确定下一个 Token。

## 两种时间关系同时存在

```text
路径之间
→ 可以并行

路径内部
→ Token 仍然串行
```

例如：

```text
时间 1：A1   B1   C1
时间 2：A2   B2   C2
时间 3：A3   B3   C3
```

同一行可以由 Runtime 一起调度，但 `A2` 必须建立在 `A1` 已生成的基础上。

## 也可以串行执行路径

```text
先生成完整 A
→ 再生成完整 B
→ 再生成完整 C
```

搜索的定义是保留和比较多条路径，不要求它们物理上同时运行。

## 与普通 Batch 的区别

| 情况 | 为什么放在一起 |
|---|---|
| 不同用户 Batch | 提高服务器吞吐量 |
| 同一问题多候选 | 提高这个问题找到好路径的机会 |

推理控制器先决定要生成 A、B、C；Runtime 可以再把它们作为一个 Batch 高效执行。

## 并行不会让一条路径一次生成完整答案

即使 A、B、C 同时运行，每一条仍然是：

```text
当前上下文
→ 下一个 Token
→ 更新上下文
→ 再生成下一个 Token
```

因此增加路径数主要增加“搜索宽度”，不会消除自回归生成的串行依赖。

## 资源与延迟

并行通常可以缩短用户等待多个候选的总时间，但会同时占用更多计算和 KV Cache 空间。串行占用的瞬时资源较少，但总等待时间可能更长。

实际系统还可能分批：

```text
第一批生成 8 条候选
→ 淘汰 6 条
→ 第二批只扩展剩余 2 条
```

## 常见误解

> [!warning] 误解：并行候选意味着一个模型 Forward 同时预测一条路径的所有未来 Token
> 并行发生在多条序列之间；一条序列未来的 Token 仍依赖它刚生成的 Token。

> [!warning] 误解：Runtime 决定哪些候选更有价值
> Runtime 主要高效执行请求。保留和淘汰规则通常来自推理控制器、Verifier 或上层系统。

## 理解检查

1. A、B、C 同时运行时，A2 为什么仍要等待 A1？
2. 同一问题多候选与不同用户 Batch 的目的有什么不同？
3. 路径串行执行为什么仍然可以构成搜索？
